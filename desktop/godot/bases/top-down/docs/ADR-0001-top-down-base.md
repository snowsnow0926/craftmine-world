# ADR-0001：2D 俯视底座的工程结构、状态归属与接口

- 状态：已采纳
- 日期：2026-09-09
- 范围：`desktop/godot/bases/top-down/**`（不影响共享协议、UI、Rust 核心、第一人称与横版底座）

## 背景

计划要求交付第二个底座（2D 俯视），它要能和第一人称底座共用同一套创作工作台：
AI 能读工程、改场景和脚本、构建、跑独立检查、形成候选再应用；玩家从示例创建新世界时
必须从初始进度开始，不能继承示例作者已经领过的奖励。同时这次短流程不能扩成大型 RPG。

需要在下面几件事上先定死结构，否则后面每个底座都会重新发明一遍：

1. 一个"世界"到底是工程、场景还是存档；
2. 运行时状态由谁持有，谁有权改；
3. 构建、保存、运行三方用什么格式交接；
4. 怎么保证"示例作者的进度"永远进不了新世界。

## 决策

### D1 一个世界 = 一个独立 Godot 工程

每个世界是从模板复制出来的完整 Godot 工程（有自己的 `project.godot`、`world.json`、
`scripts/base/**` 副本、`data/**`、`assets/**`、`scenes/**`）。

理由：

- Godot 的资源根是 `res://`，跨工程引用不可移植；共用目录会让世界之间产生隐式依赖。
- 计划要求"可创建工程""两个小镇实例状态独立""作品可复用"；独立工程让这些边界天然成立。
- 新世界可以直接用编辑器打开，也可以被构建服务当成普通工程处理，不需要额外解释。

代价：底座代码在每个世界里有一份副本。用 `tools/new-world.mjs` 生成、
`tools/check-sync.mjs` 校验，保证副本不漂移。

### D2 运行时状态由一个自动加载单例持有

`Game`（`core/scripts/game.gd`）是唯一的权威状态持有者，内含 `WorldState`。
商店、任务、采集、探针、将来的 UI 都改同一个对象，不存在第二份状态。

理由：计划明确要求"运行时是实时游戏状态的来源""模型不能填写检查结果"。
一个状态对象 + 一个提交路径，才能保证验收看到的就是玩家看到的。

`WorldState` 按稳定 id 存取，逐字段严格校验，版本号在存档里。

### D3 世界数据尽量外置成 JSON，而不是写死在脚本里

商品、价格、库存、任务需求与奖励、NPC 台词、地图、初始进度都是 JSON。
脚本只实现规则，不实现内容。

理由：这是让真实模型"新增商品、调整规则、创建任务"的前提——改数据不需要动底座代码，
也让 diff 可读、可回滚。地图用字符行 + 图例，避免二进制 `tile_map_data`。

### D4 碰撞用地图数据生成，而不是手摆碰撞体

`collision` 层里带 `solid: true` 的字符会被合并成矩形，挂到场景的 `StaticBody2D` 上。

理由：地图改了碰撞就跟着改，不会出现"画了墙但没碰撞"或"拆了墙还挡路"；
合并矩形也让形状数量可控（示例大地图 48 个形状）。

### D5 每个动作自己重新做几何检查

`Shop.buy`、`Npc.talk`、`QuestManager.deliver`、`GatherZone.gather` 都要求
调用时与目标区域真实重叠，而不是相信调用方（UI 焦点、探针、脚本）已经判断过。

理由：验收要求"离开交互范围不能购买"。如果只靠 UI 判断，任何直接调用都能绕过；
把检查放在状态变更前，绕过成本就变成"必须真的走进区域"。

### D6 一次性奖励用双账本

`quests[id].rewarded` 和 `grantedRewards["<id>#reward"]` 同时写、同时校验。

理由：单一标志位一旦被新代码路径漏写或被旧存档覆盖，就会重复发奖。
两个独立账本让"只改一边"的实现失败关闭（fail closed），而且两者都在存档里，
跨重启仍然成立。

### D7 新世界只从 `initialProgress` 开始，创建工具硬性拒绝已领奖励的模板

`new-world.mjs` 写盘后立即检查模板的 `initialProgress`：出现 `rewarded: true` 或非空
`grantedRewards` 就直接失败退出。

理由：计划要求"从示例创建新世界时使用初始进度，不能继承作者已领的奖励"。
把它做成工具里的硬检查，而不是文档里的约定，才不会在后续复制流程里被绕过。

### D8 内部测试接口与游戏共用代码路径

探针只在 `--probe` 时启用，通过 `probe.gd` 调用 `Shop.buy` 等真实方法；
`move` 只提供输入向量，位移与碰撞由真实物理产生。

理由：验收要求"不允许模型绕过真实碰撞、伤害和库存逻辑直接填写预期结果"。
共用路径意味着探针不可能比玩家更容易通过。

### D9 每实例一个 `user://` 目录

`application/config/custom_user_dir_name = "craftmine-topdown-<worldId>"`，
进度再按 `worldId` 的哈希分目录，文件内还带 `worldId`。

理由：三个层次（工程目录名、目录哈希、文件内身份）共同保证两个实例不会互相覆盖，
也让"两个小镇实例状态独立"可以被真实验证，而不是靠约定。

## 后果

- 底座代码有 N 份副本（N = 世界数）。`check-sync.mjs` 兜住漂移，但升级底座时
  需要重新生成或迁移世界，属于 GD6 的迁移话题，本次不做自动迁移。
- 存档是完整状态而非增量；示例规模下没问题，大世界需要重新设计。
- 场景切换是重新加载，不是热更新；计划已接受"进度正确性优先于少一次加载"。
- 本底座不提供 OS 级隔离；那属于 GD0 的 AppContainer 工作，这里不声称解决。

## 未决

- 世界之间的作品复用与兼容标签（GD6）。
- 底座版本升级时的世界迁移。
- 地图层的自动碰撞与 TileSet 物理层之间的关系（目前只用合并矩形）。
