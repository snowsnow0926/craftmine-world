# craftmine world / 最中幻想：自扩展与验收方案

更新日期：2026-09-09。本文回答一个问题：**玩家的创造力是无限的，怎么让系统能力也跟得上，而不是被开发者的产出速度卡住。**

## 1. 要解决的问题

玩家一天能想出几十个需求，宿主能提供的能力却是有限的。只有三种应对：

| 档 | 谁造能力 | 上限 | 需要什么 |
| --- | --- | --- | --- |
| **A. 预判手写** | 开发者 | 开发者的产出速度 | 开发者本人 |
| **B. 模型写扩展** | 模型写，宿主装配 | 模型的速度 | 扩展自带测试 + 冻结回归 |
| **C. 模型改内核** | 模型改可替换部件 | 最高 | 冻结内核 + 回归 + 自动回滚 |

A 是过渡期的正确做法，但有天花板：开发者一周加 3–5 个能力，玩家一周提 50 个需求。**终局必须是 B，再往后开 C 的一扇窄门。**

一旦走到 B/C，系统就要**脱离人运行**。于是出现本文的核心约束：

> **脱离人手之后，谁来判断「这次扩展是对的」？**

---

## 2. 第一原则：LLM 提意见，机器做判定

裁判必须满足三个条件，LLM 都不满足：

| 要求 | 为什么 | LLM |
| --- | --- | --- |
| 确定性 | 同一份代码跑两次必须同一结论 | ❌ 每次可能不同 |
| 不可说服 | 代码不能靠"讲道理"让裁判放行 | ❌ 一段巧妙解释就能骗过 |
| 可复现 | 三个月后能重新验证当时为什么通过 | ❌ 对话已不在 |

但 LLM 在另外三件事上非常有用：

| 角色 | 干什么 | 用 LLM 合适吗 |
| --- | --- | --- |
| 实现者 | 写能力、写代码 | ✅ 现在就是 |
| 对抗评审者 | 独立找实现者的问题（看不到实现者的推理） | ✅ 很有用 |
| **测试翻译官** | 把玩家说的需求翻译成机器能跑的断言 | ✅ **最关键的一环** |
| **裁判** | 执行断言、给出通过/不通过 | ❌ 必须是确定性代码 |

**关键设计：让评审 LLM 输出「可执行的断言」，而不是输出「结论」。**

- ❌ 「我觉得这个实现有问题」——无法验证它的判断
- ✅ 「这条需求要求按 G 后所有怪物血量恢复，我写了这条断言」——机器一跑就有客观结论

于是 LLM 的价值落在**把自然语言变成机器可判的东西**，而不是代替机器做判断。

> **可以变的是「谁来提意见」，不可变的是「提完意见后那条线」。**

### 2.1 已经有的实测证据

2026-09-09 做「工具闭环」时，实现由一个代理完成、验收由另一个代理独立评审，结果评审找到 **7 个问题，其中 2 个是阻断级**：

1. 讨论消息会误入执行循环，把"聊天"变成世界改动；
2. 闭环候选跳过了源码运行验证，跑不通的代码也能拿到「候选就绪」。

这两个问题**实现者自己的 11 个测试全都没抓到**（当时全绿）。评审还指出其中几个测试"换个坏实现也能通过"。

结论：**对抗评审能显著提高发现率，但它给的是「发现」，不是「判定」。**

---

## 3. 架构

```
玩家说需求
   ↓
实现者 LLM 写能力 / 代码
   ↓
测试翻译官 LLM（独立上下文，看不到实现过程）
   输入：需求原文 + 能力契约
   输出：可执行的验收断言（不是意见）
   ↓
人审一次 → 断言冻结（哈希进证据链）
   ↓
确定性验证器执行冻结断言  ← 真正的裁判
   ↓
对抗评审 LLM 追加人类没想到的角度
   ↓
通过 → 装载；不通过 → 自动回滚
```

## 4. 阶段

四个阶段有严格的前置关系：**上一层的裁判没跑起来，不许开下一层。**

### 阶段 E1 — 外置裁判

**目标**：让「好不好」脱离人也能判。

**交付物**

1. **10 条冻结真实需求集**（见 §5），每条都要有可执行断言。
2. **需求 → 断言的翻译流程**：LLM 翻译 → 人审一次 → 冻结。
3. **确定性断言执行器**：复用已有的 `app/harness/acceptance.mjs` 与 `app/behavior-verify.mjs`。
4. **指标落盘**：通过率、首次通过率、修复率、耗时中位数/P90、token 中位数/P90、评审发现数。
5. **影子运行**：同一批需求跑两遍，指标可复现。

**机器可验收**

- 注入「命令有效但世界没变」的旧 bug（刷新怪物），必须判失败。**已有回归测试。**
- 断言文件有哈希，实现者改动断言会被发现。
- 每条断言都要有一个「故意写错的实现」能把它打红，否则该断言不算数。

**退出条件**：10 条需求全部有可执行断言，且能自动判对错。

**风险**：断言写太松 → 用「故意注入错误候选」逐条验证断言的有效性。

### 阶段 E2 — L2 扩展 ABI（把 A 推到 B）

**目标**：模型自己造能力，开发者不参与。

**交付物**

1. **扩展包格式** `craftmine.extension/1`：声明（新命令/事件/资源类型的 schema）+ 实现 + **自带测试** + 版本 + 依赖 + 生命周期（注册/注销）。
2. **扩展沙箱**：独立 Worker，无文件系统、无网络，只能通过声明的宿主 API 访问。
3. **装载流程**：模型提议 → 影子副本构建 → 自带测试 + 冻结回归全绿 → 生成候选扩展版本 → **人一键接受/回退**。
4. `capabilities.catalog` 自动包含已装载扩展。
5. **卸载语义**：引用已卸载扩展的模块必须**显式失败**，不能静默失效。
6. **对抗评审强制接入装载流程**（§2 的角色分工）。

**红线**：扩展不能改内核、不能改判定面、不能碰存档格式。

**机器可验收**

- 用第一个真实扩展走完整流程（建议：吸血 `life.steal` 或中毒 `status.poison`）。
- 故意提交一个自带测试造假的扩展 → 必须被拒。
- 卸载扩展 → 相关模块报明确错误，存档不丢。
- 评审 LLM 发现的每个问题都要转成一条冻结断言。

**退出条件**：≥3 个模型自写扩展上线且稳定运行。

### 阶段 E3 — L3 的第一扇窄门：渲染扩展层

**目标**：玩家想要的视觉表现（粒子/特效），模型自己加。

**为什么先做这个**

1. 玩法能力在 E2 就能覆盖，不需要动内核；
2. 玩家最想要而宿主完全没有的，恰恰是**粒子/特效**；
3. 渲染扩展只画东西，不改存档、不改碰撞、不改输入，**风险最低**；
4. 它正好把 L3 的流水线跑通一遍：写 → 沙箱装载 → 冻结回归 → 自动回滚。

**交付物**

1. **渲染扩展点**：每帧拿到世界状态，产出额外几何/粒子。
2. **沙箱 + 帧预算 + 自动降级**：超时或异常只关掉该扩展，游戏继续跑。
3. **冻结回归**：视觉断言（关键帧截图哈希、不崩溃、帧率下限）+ 行为断言。
4. **自动回滚**到上一个能启动的版本。

**红线**：不能改存档格式、不能改碰撞、不能改输入、不能改判定面。

**机器可验收**

- 模型写一个 `effect.burst` 粒子扩展并成功装载。
- 故意写一个死循环或超预算的扩展 → 自动关掉且游戏继续。
- 回滚后一切恢复。

**退出条件**：≥1 个模型自写渲染扩展稳定运行，且没有破坏任何回归。

### 阶段 E4 — 内核可替换部件（远期）

**前置**：E1 / E2 / E3 全部达标。

**范围**：只碰低风险区——后处理着色、新 HUD 组件、新渲染 pass。

**永远不碰**：存档格式、物理内核、输入内核、权限模型、回滚逻辑、测试集与指标定义。

**机制**：冻结最小核 + 可替换部件 + 自带测试 + 失败自动回退到能启动的内核 + 第一个改动必须人审。

## 5. 冻结需求集（E1 的第 1 项交付）

10 条需求，覆盖从「改世界」到「多模块协作」的完整形状。每条都必须是**玩家真会说的话**。

| # | 需求原话 | 覆盖形状 | 验收要点（机器可判） |
| --- | --- | --- | --- |
| 1 | 在我前面种三棵树 | 纯造世界 | 物体数 +3，位置在前方，有碰撞 |
| 2 | 把那棵树变高一点 | 改参数 | 只有目标对象变化，其他对象哈希不变 |
| 3 | 开门要消耗一块木头 | 条件 + 扣料 | 木头不足时门不开；开一次扣一块；重复开不重复扣 |
| 4 | 让我能砍树，砍完掉木材 | 交互 + 掉落 | 攻击命中后目标消失、背包 +N |
| 5 | 用三块木头做一扇门 | 制作 + 防重复 | 不足不生成；实扣 3 块；重复不重扣；重启后一致 |
| 6 | 怪物被杀了，按 G 复活到出生点 | 按键 + 复活 | 按 G 后所有目标血量满、位置回到出生点（**已有回归**） |
| 7 | 加个体力条，跑动消耗、站着恢复 | 通用资源 | 资源值随行为增减，夹在 0..max |
| 8 | 怪物追我并攻击，远程的保持距离射击 | 多模块 AI | 近战怪靠近、远程怪停在射程外；接触扣血 |
| 9 | 命中时闪红、击退，死亡倒地 | 反馈 + 平滑移动 | 命中瞬间颜色变化；位移用 duration 而非瞬移；血量归零后模型消失 |
| 10 | 做个商店，用木头换血瓶 | 面板 + 交易 | 木头不足时拒绝；成功时扣木头加血瓶；面板显示当前数量 |

**每条需求的断言都要能被一个「故意写错的实现」打红**，否则该断言无效。

## 6. 成本分层

不能让每个小改动都跑 LLM 评审，按频率和风险分层：

| 操作频率 | 风险 | 用谁 |
| --- | --- | --- |
| 改数值、挪位置（每天几十次） | 低 | 确定性验证 |
| 写新玩法代码（每天几次） | 中 | 确定性验证 + 对抗评审 |
| **装载新能力扩展**（每周几次） | 高 | 确定性验证 + 断言翻译 + 对抗评审 + **人审** |
| 改内核（L3） | 极高 | 上面全部 + 冻结回归 + 自动回滚 |

---

## 7. 三个风险与对策

| 风险 | 表现 | 对策 |
| --- | --- | --- |
| **同源盲区** | 评审者和实现者是同一模型、同样提示，会犯同样的错 | 不同提示角色、尽量不同模型；评审者**看不到**实现者的思考过程 |
| **评审者被说服** | 模型很擅长解释，可能说服评审放行 | 评审只看**需求 + 产物 + 运行证据**，不接受口头解释 |
| **评审者本身也会错** | 漏报、误报 | 它的输出必须是可执行断言，能被机器复核 |

---

## 8. 现在就开始的第一批任务

1. 把 §5 的 10 条需求写成冻结文件（含原话与验收要点）。
2. 写「需求 → 断言」的翻译提示词，跑一遍，产出候选断言，人审后冻结。
3. 断言执行器复用 `app/harness/acceptance.mjs` + `app/behavior-verify.mjs`，指标走 `app/harness/metrics.mjs`。
4. 逐条做「注入错误候选」验证断言有效性。
5. 跑两遍，确认指标可复现。

---

## 9. 不做什么

- **不让 LLM 当最终裁判**（它可以提意见，不能下判决）。
- **不让扩展改判定面**：验证器、权限模型、回滚逻辑、存档格式、测试集、指标定义。
- **不在 E1 完成前开 E2**：没有裁判的扩展装载等于随机漫步。
- **不做公开插件市场、云记忆、多 Agent 并写世界**（沿用 HARNESS_DEVELOPMENT_PLAN §21）。
