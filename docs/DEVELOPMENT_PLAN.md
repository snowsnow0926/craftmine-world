# craftmine world / 最中幻想：产品梳理与开发计划

更新日期：2026-09-08。

开发状态：本地创作 Alpha 0.4 已进入细粒度几何、创作记忆与基础玩法模块阶段，详见 [本轮设计与验证](ALPHA_0_4.md) 和 [模块记忆方案](MODULE_MEMORY_PLAN.md)。下文保留长期目标；任意玩法源码开发、外部素材、多人和社区仍待后续。

本文依据交接提示词、原型源码与产品讨论整理，并已纳入用户补充的“空白世界 → 输入我想要有树 → LLM 开发并生成树”的起点。已确认的方向与建议的实施方案分别标明；下文里程碑描述目标，当前完成情况以实现记录为准。面向体验的简明说明见 [产品想法](PRODUCT_VISION.md)。

## 1. 我们要交付什么体验

**让创作者从一个可以走动的空白 3D 世界开始，通过自然语言逐步创造场景和玩法，由 Agent 实际开发，再应用新版本继续体验。**

创作者可以从游戏外开始制作，也可以在游戏内继续修改。一次创作的成果应能保存、继续开发，并逐步具备供别人游玩和复用的能力。

长期面向借助 AI 创作游戏的人。第一阶段的使用者是项目发起者本人，运行环境为 Windows 本机，先验证个人创作流程。这是用户本轮确认的范围。

产品同时具有三个部分：

| 部分 | 用户能做什么 | 第一阶段的重点 |
| --- | --- | --- |
| 开发工作区 | 描述需求、讨论设计、执行任务、查看候选和版本 | 接入真实开发任务，并与游戏内入口共享上下文 |
| 游玩／创造工作区 | 实际游玩、搭建、对准对象提出修改 | 旧版本持续可玩，新版本由用户主动应用 |
| 素材工作区 | 生成或导入、预览、绑定、体验与撤回 | 保留现有外观与行为分离；真实素材接入在核心闭环之后 |

现有 3D 方块运行器作为可复用的技术起点。新项目的初始内容采用空白可行走世界；现有森林、河流和小屋保留在旧原型中作为参考。平台能力围绕项目、任务、版本、资产及运行接口组织，后续可以接其他运行器。

## 2. 已确认的边界

- 正式名称：英文 **craftmine world**，中文 **最中幻想**。
- 第一阶段在 Windows 本机使用，先服务用户本人。
- 用户希望从基础移动和空白世界起步，通过“我想要有树”这样的自然语言添加原本不存在的内容。
- 保留开发、游玩、素材三个工作区，共享项目和相关上下文。
- 用户接受重新载入游戏区域或显示更新进度。
- 讨论与执行分开；随口讨论不能自动修改项目。
- 候选就绪后由用户主动应用，兼容更新应保留应用瞬间的最新进度。
- 多人共创、可复用内容及社区生态是后续方向。

## 3. 当前原型能作为哪些基础

| 能力 | 当前事实 | 下一步需要补齐 |
| --- | --- | --- |
| 第一人称 3D 世界 | 有限方块世界、移动、搭建、采集及输入控制 | 验证本机基线，提取基础操作并制作空白世界起点 |
| 开发对话 | 本地中文预设解析器，返回配置补丁 | 真实 Agent 读取项目、修改文件并执行检查 |
| 候选更新 | 配置有基准版本，应用前保持旧配置 | 可追溯的源码版本、独立构建产物及载入流程 |
| 状态保留 | 配置应用时捕获最新快照 | 跨游戏代码版本的状态格式与恢复协议 |
| 回退 | 恢复规则和外观配置，另有完整世界归档 | 游戏代码版本回退及兼容检查 |
| 素材 | 三种程序化树木样式 | 真实文件进入游戏、稳定资产身份及绑定版本 |
| 卡带 | 受限 JSON 配置及世界内容 | 在第二个兼容项目中验证复用 |

当前工作台与运行器在同一个页面中直接调用；`build.py` 把两者合成为单 HTML。接入真实开发时，需要让游戏产物独立更新，同时保持工作台、任务和存档可用。

附带的 42 项测试记录使用过兼容渲染路径和测试存储替身。它们是历史证据。本机目前只验证过更名后的构建与 JavaScript 语法，浏览器完整验收仍待执行。

## 4. 第一阶段：本地创作 Alpha

目标是交付一条可反复使用的真实开发闭环：

```mermaid
flowchart LR
    A[在游戏内外提出需求] --> B[固定源码基准与现场上下文]
    B --> C[Agent 在开发副本中修改]
    C --> D[实际检查、构建与启动验证]
    D --> E[候选就绪，等待用户应用]
    E --> F[保存最新进度并载入候选]
    F --> G[恢复兼容状态，继续体验]
    D -->|失败或取消| H[保留当前版本和进度]
    F -->|载入失败| H
```

从提出需求到候选就绪，当前游戏仍可游玩。用户输入文字时游戏控制暂停，避免打字变成角色移动；关闭对话后可继续玩。执行进度来自实际事件，检查结果与玩法验收分别展示。

### 范围建议

- 一位使用者、一个本地项目、一个运行器、一次一个执行任务。
- 首次启动进入空白世界。建议只提供平地、天空、基础光照、移动、环顾、跳跃和碰撞，不预置树木、房屋和采集玩法。
- 首个内容开发任务是添加一棵真实 3D 树，随后能指向这棵树继续修改并保存。优先使用程序化几何或方块构造，精细 AI 3D 模型服务放到后续。
- 一个真实 Agent 执行适配器，能够读取项目、修改文件、运行受控检查并提交候选。
- 一个待处理候选；应用或丢弃后再执行下一项修改。执行期间仍能继续讨论和记录后续想法。
- 任务可查看阶段、实际日志、失败原因，并可取消。丢弃候选与取消运行中的任务是两个操作。
- 候选展示修改内容、验证证据、已知限制及存档影响。
- 完成一次兼容更新、一次版本回退、一次执行失败、一次取消和一次应用失败恢复。

这一阶段暂缓多人、账号与云同步、公开市场、付费系统、任意引擎适配和大量玩法内容。真实 AI 图片与 3D 模型生成在核心闭环稳定后单独交付。

## 5. 建议的工程结构

第一版建议以浏览器承载工作台和游戏画面，配合 Windows 本机开发服务运行。这样可以继续使用现有网页原型；是否封装为桌面安装包，等个人创作流程成立后再决定。此处是实现建议，尚未锁定框架、后端语言或模型供应商。

| 职责 | 管理的内容 | 关键约束 |
| --- | --- | --- |
| 工作台 | 对话入口、任务视图、候选操作、素材入口 | 游戏重新载入时仍然可用 |
| 本地项目服务 | 源码基准、任务记录、构建产物、存档与备份 | 明确当前版本，持久记录应用结果 |
| Agent 执行器 | 开发副本、文件改动、受控命令、实际日志 | 修改范围限于当前游戏项目，不获得工作台服务与凭据的写入权 |
| 游戏运行器 | 渲染、输入、玩法、对象及运行快照 | 通过明确协议输出现场上下文和保存状态 |

现有 `voxel-runtime.js` 是运行器参考起点，需让基础地面与按需添加的对象分开组织，避免新项目自动生成固定树林。`workshop.js` 中的任务、持久化与版本职责逐步拆出。允许局部重构，不要求一次全部更换渲染器或前端框架。旧原型和存档保持独立、可恢复，新世界使用明确的项目身份。

开发副本用于隔离版本改动，本身不构成安全沙箱。运行游戏的页面不得直接获得开发服务的命令权限；具体页面隔离、服务认证、来源检查和文件／命令限制需在接入执行器前实现并验证。第一版使用受信任的个人项目，不宣称支持任意不可信社区代码。

### 需要建立的最小数据约定

- **项目**：稳定项目 ID、模板／运行器版本和当前已应用版本。
- **任务**：用户原话、讨论／执行意图、基准源码版本、状态、实际日志与取消结果。
- **现场上下文**：游戏版本、玩家位置、所指对象 ID、对象对应的数据／源码入口及修改范围。截图可补充。
- **候选**：任务 ID、基准版本、修改摘要、源码差异、构建标识、验证记录及状态兼容声明。
- **存档**：独立于游戏构建保存，记录状态格式版本；工作台掌握应用前最新快照。

首先让新创建的对象具备稳定 ID，并验证真实的对象上下文映射。旧原型的树木已有 `tree-001` 等固定 ID，可供参考；新生成的树需要自己的身份、场景记录与实现定位，才能理解后续的“把这棵树变高一点”。

## 6. 按验收结果推进的里程碑

| 阶段 | 实际工作 | 完成标准 | 依赖 |
| --- | --- | --- | --- |
| M0 本机基线 | 建立本地版本管理；适配测试环境；运行原型；验证画面、输入、保存与重启；定位 Agent 接入可行性 | 有当前环境的验证记录、可恢复基线和明确的接入选择 | 无 |
| M1 空白世界与候选通路 | 提取最小可行走世界；分离工作台与游戏产物；建立对象、任务、候选及存档记录；用人工变更验证载入 | 初始世界没有树；基础移动可用；独立候选可添加对象并保留最新进度；失败可恢复 | M0 |
| M2 一句话创造第一棵树 | 接入真实执行适配器；传递上下文；修改开发副本；检查与构建；生成树的候选；再修改同一棵树 | 输入“我想要有树”，无需复制代码，应用后世界里出现真实 3D 树；后续指向修改有效 | M1 |
| M3 闭环可靠性 | 补齐取消、失败、过期候选、兼容回退、重启恢复和任务限制；整理启动与配置步骤 | 正向体验故事和关键故障案例全部通过，用户能重复完成下一轮创作 | M2 |

M1 的人工候选只用于验证应用机制，应明确标识。M2 必须真实联调；没有模型授权时只能报告已验证的通路，不能把它计作真实 Agent 已接通。

每个阶段交付源码、启动步骤、验证记录和未完成项。先完成 M0 的实测再估后续工期，避免在渲染、模型接入和存档兼容尚未验证时承诺日期。

### 正式开发的第一个切片：M0

1. 建立本地 Git 基线和必要忽略规则，保留原始交接包；不涉及远程推送。
2. 让既有测试识别 Windows 的浏览器路径，明确 UTF-8 文件读写；为本轮结果使用独立报告位置。
3. 通过固定本地地址启动原型，检查实际渲染路径、移动／碰撞、聊天输入切换和方块操作。
4. 使用真实浏览器存储验证刷新、关闭浏览器后重开、存档导出／导入。人工操作项单独列出，不用替身结果代替。
5. 检查本机可用的 Agent 执行能力与授权方式，选择一条能修改文件和运行检查的通路，记录配置方式、任务限制及缺失条件。
6. 优先修复影响可玩性、数据保存或后续候选载入的阻塞问题。

M0 完成后再锁定服务技术和最小运行协议。初次接入优先复用适合本机的现成执行能力，只有缺少必要能力时才补充工具循环。

## 7. 第一阶段的验收故事

**核心需求：在空白世界中输入“我想要有树”，由 LLM 实际开发并把树加入世界。**

这是用户给出的首个体验目标。旧原型虽已有固定树林，新起点应为空白；验收必须证明树来自实际的项目内容变更，不能仅打开旧森林开关或增加“树”关键词分支。

1. 用户打开项目，进入只有基础地面和操作的世界，确认初始没有树并记录玩家位置。
2. 用户通过游戏内入口提交执行需求，任务关联当时的代码基准和现场上下文。
3. Agent 修改隔离副本中的真实项目文件，并留下源码差异、命令结果与构建产物。
4. 用户在等待期间继续移动。当前世界尚未出现候选树；已有编辑能力时，也验证等待期间新增的编辑可被保留。
5. 工作台显示候选、已执行的验证和需要用户试玩确认的部分。
6. 用户点击应用，系统取得此刻的最新进度，备份后载入候选；保留最新兼容状态，树出现在可接近的空地，有可观察的三维形体和基础碰撞。
7. 用户走近、绕行并指向这棵树，说“把这棵树变高一点”，再次完成开发和应用，确认对象身份与修改范围正确。
8. 关闭并重新打开项目，确认树、最新修改与玩家进度仍在。若后续有背包、采集与手动搭建，也必须进入相应回归检查。
9. 对兼容版本执行回退，验证回退行为；候选引入不兼容状态时，先说明影响并提供有备份的明确恢复路径。

### 必须独立验证的异常情况

- 编程或构建失败：显示实际错误，旧游戏和进度可继续使用。
- 运行中取消：终止执行进程及其子进程，阻止迟到结果生成可应用候选；请求取消不等于已取消成功。
- 候选基准过期：拒绝应用，要求重新验证或重新制作。
- 候选加载失败：恢复旧产物和应用前快照，版本记录与实际运行保持一致。
- 保存或备份失败：不能显示应用成功并丢弃旧状态。
- 工作台或服务重启：识别中断任务，不把未完成构建认作可用版本；恢复最近已确认版本。
- 超出任务时长或步骤限制：停止任务并保留日志；不进行无限重试。可用时记录实际用量。

## 8. 版本与存档要分别管理

| 操作 | 改变什么 | 进度处理 |
| --- | --- | --- |
| 应用兼容游戏版本 | 源码／构建和长期规则 | 恢复应用瞬间的最新兼容状态 |
| 回退兼容游戏版本 | 恢复旧源码／构建 | 尽量保留当前进度，需要状态兼容检查 |
| 恢复完整存档 | 恢复记录时的世界与个人进度 | 明确会回到过去，恢复前另存当前状态 |
| 应用不兼容游戏版本 | 新代码无法直接读取当前状态 | 阻止静默应用，说明影响并提供备份、迁移或新开测试存档路径 |
| 安装世界卡带 | 切换世界内容与规则 | 延续当前语义：归档旧世界，新世界不携带旧个人位置与背包 |

新增玩法如果引入旧版本无法识别的方块或对象，回退时也需要兼容检查。第一阶段不承诺任意代码更新都能无损迁移。

## 9. 核心闭环之后

| 顺序 | 下一项产品能力 | 验收方式 |
| --- | --- | --- |
| A | 一种真实素材进入游戏 | 导入或生成真实文件，预览并绑定对象；替换和撤回外观时保留玩法；记录来源、版本与使用位置 |
| B | 一次跨项目复用 | 将稳定世界／对象／玩法整理成内容包，在第二个兼容项目中安装，展示依赖、影响和撤回方式 |
| C | 少量外部创作者试用 | 完成适合试用者的启动、配置、恢复和问题记录流程，验证他人能否独立完成创作 |
| D | 多人和社区 | 分别规划联机游玩、共同开发、版本发布权限和内容发现 |

具体先接 AI 图片还是 3D 模型，应根据届时运行器支持和用户的首个素材需求决定。本轮不为素材生成服务、公开市场或商业模式提前锁定供应商。
