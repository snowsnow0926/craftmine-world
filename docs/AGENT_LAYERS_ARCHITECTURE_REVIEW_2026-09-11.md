# 最中幻想：Agent 分层与架构评估

> 本文保留 e61bae85 基线的历史评估。后续造物 Alpha 已完成的修正与真实验收见[中文开发记录](IMMERSIVE_DEVELOPMENT_2026-09-11.md)，请勿将历史发现直接视为 preview.10 的当前缺陷。

日期：2026-09-11

源码基线：`e61bae85ca3c87553d4be28a138d0766912f515f`，包含当前工作区中的方案文档。诊断所用五个源码文件在执行前后哈希一致，详见附带报告。

范围：核对 L0–L4 定义、相关计划、当前工具与新增创作运行层，并执行有限隔离诊断。本次未修改产品代码、重跑完整客户端、调用真实模型或发布安装包；不作为整个系统的完整审计结论。

## 1. 判断

分层的主要方向合理：让玩家 Agent 在世界工程中创造，通过版本、运行观测、检查、应用和恢复约束变化；进一步将成熟能力复用为模块，让创作策略通过评测改善。

目前有成体系的方案材料，但文档定义、实施状态和真实运行验收还没有完全统一。不能把已有方案与单元测试通过合并称为“L0–L4 已全部完善”。本次在新增创作层复现了三项具体缺口，同时发现能力范围、目标身份和阶段编号需要进一步整理。

建议保留架构主体，优先完成一个底座上的 L0/L1 真正运行与保存闭环，再通过 L2 复用扩大供给；L4 用对照实验改善成功率和成本，L3 按实际需求单项开发。无需为开放创作预先放开整个宿主。

## 2. L0–L4 的准确含义

这些层表示改动对象和边界，不是游戏规模、开发难度、完成阶段或依次解锁的玩家等级。它们也不是行业统一标准，而是本项目的组织方式。

| 层 | 原定义及 Godot 路线中的含义 | 玩家例子 | 实际变化与验收 |
| --- | --- | --- | --- |
| L0 数据与场景 | 修改已有结构中的内容、参数和资源绑定 | 剑伤害从 10 改 20；把树变白；布置一座城市 | 版本、目标身份、参数约束、资源与空间关系正确 |
| L1 游戏玩法 | 用运行环境已有能力编写新增规则；旧 JS 行为与普通 Godot 工程脚本属于此层 | 树可砍伐；宠物跟随；火球；骑乘；组合机关 | 真实事件触发、物理/交互、状态、重开与旧玩法回归 |
| L2 可复用扩展 | 原路线指扩展命令/事件/资源词表；Godot 计划进一步包含可复用组件与兼容包 | 将宠物跟随或钓鱼整理为能安装到其他世界的模块 | 固定依赖、声明接口、独立实例、升级、卸载和状态迁移 |
| L3 底层能力 | 扩展当前宿主或运行器尚未提供的低层实现 | 新的原生渲染/性能组件、运行后端适配 | 平台版本、明确权限、独立验证、迁移与启动恢复 |
| L4 创作策略 | 改善 Agent 使用模型、工具、指导和记忆的方式 | 先找资源再开发；改变检索与修复策略 | 同一任务集上的成功率、成本、耗时与回归，而非自报更聪明 |

建造一个很大的世界可能主要是 L0；增加一项复杂玩法可能是 L1；把它变成可靠通用组件涉及 L2。“换世界底座”按底座包与兼容迁移处理，不自动意味着 L3。

同一个愿望在不同运行器中的层级可能不同。例如项目自研 Web 运行器缺少某种表现接口时可能要扩展宿主；在 Godot 中使用已有粒子、动画或着色器接口，通常属于普通项目开发。只有改变引擎或宿主实现才进入相应底层维护范围。

## 4. 应继续保留的底层原则

1. **内容和游玩进度分开。** 改伤害、场景和资源进入内容版本；背包、一次性奖励和位置属于进度；界面偏好另行保存。应用时使用最新正式进度。
2. **界面不持有第二份权威状态。** 工作台与游戏内面板共用会话、任务、世界与操作回执，收起面板不取消任务。
3. **优先在世界工程内开发。** 常见需求走数据和组合，新增规则走普通脚本，超出真实引擎/宿主能力时才形成平台变更。
4. **能力根据真实接线与版本报告。** 清单存在、工具可调用、引擎实际支持、完整玩家故事通过、安装包已发行应分别记录。
5. **检查和正式应用由宿主协调。** 生成者提供候选与证据，不能自己填写通过回执、放宽权限或降低本次验收条件。
6. **共享生命周期，允许运行器专属能力。** Web 与 Godot 共用任务、身份、应用和恢复语义；无需把所有能力压缩成两者都认识的几种对象。

这里的 Web 指当前自研 JS/WebGL 世界。Godot 本身也能导出到 Web；“选择 Godot”与“是否使用浏览器运行”属于不同决策，不能把二者当成同一个二选一。

## 5. 本次实际验证

### 5.1 现有选定测试

执行 `creation-operations`、`creation-runtime`、`creation-entities`、`creation-sequence-rule` 四个测试文件，结果 **19 通过、0 失败、0 跳过**。设置了当前 Windows 上已有的固定 Godot 路径，顺序机关脚本实际在隔离 headless Godot 中执行。

这些测试没有调用模型，没有运行真实客户端应用事务，也没有证明新增实体可在正式世界中进行物理互动。原始输出见[选定测试记录](architecture-reviews/agent-layers-20260911/selected-tests.log)。

### 5.2 补充真实引擎诊断

在新建隔离目录中复制当前渲染脚本，运行固定创作实体和生成的顺序规则。无鼠标/键盘输入，无 Pointer Lock，无可见测试窗口，不使用玩家数据。

| 检查 | 实际结果 | 含义 |
| --- | --- | --- |
| 蓝→红→绿 | 纯逻辑投影与 Godot 规则都打开门 | 正常路径一致 |
| 蓝→蓝→红→绿 | 纯逻辑投影不开门；Godot 规则打开门 | 重复首个标记的语义不一致 |

诊断脚本正常执行退出不等于上述产品要求通过；其报告中的不一致和缺失就是发现。本次检查真实脚本与节点树，未检查可见像素、GPU 表现或真人手感。

## 6. 需要优先修正的实现问题

### A01：投影与运行逻辑不一致——已复现

对应：[纯逻辑顺序处理](../desktop/godot/shared/creation_runtime.mjs#L89)、[生成规则](../plugins/craftmine-world/creation-sequence-rule.cjs#L4)。重复首个标记、无关事件两类输入产生不同结果。

应先明确规则语义，再用同一组事件对照真实脚本与测试投影。纯逻辑可以用于快速反馈，最终放行需要实际运行链路；不能让第二份简化实现成为唯一判定依据。

### A02：新增实体渲染尚未连接完整玩法——已复现部分缺口

对应：[第一人称创作渲染器](../desktop/godot/bases/first-person/scripts/core/creation_renderer.gd#L41)。当前新增节点是可见网格，诊断子树没有碰撞体。渲染器也没有 `set_door_open` 方法。

这不表示第一人称底座整体没有碰撞或训练场不能交互；它说明新加入的创作实体尚不能继承已有底座的完整能力。后续需要实体实例化、碰撞、选择/交互、规则装载与存档接入，再验证真实门状态。把 JSON 中 kind 写成 chest/door 不能自动获得宝箱/门的玩法。

### A03：无效创作文件清空当前显示——已复现

对应：[重新载入流程](../desktop/godot/bases/first-person/scripts/core/creation_renderer.gd#L26)。代码先清除旧实体，再读取和解析文件；损坏时返回，导致已显示内容消失。

建议先读取、校验并准备新子树，成功后再替换旧内容；失败保留最后一份可用内容并报告原因。源码持久化、运行载入和正式应用仍需共用版本与回执，不能单凭文件变化视为正式采用。

### A04：目标快照的信任来源需要补强——代码审查发现，未做端到端攻击测试

对应：[creation_operation 工具入口](../plugins/craftmine-world/world-tools.cjs#L193)。`source.instanceId` 来自调用参数里的 `targetSnapshot`，随后与该请求中的实例字段比较。当前路径能检查一致性，但这种比较本身无法证明它是当前真实实例采集的新鲜目标。

应由宿主取回或验证绑定当前运行实例、采样修订及来源的快照，模型提交目标引用或受控意图。还要区分工程源码 revision 与 creation 文档 revision；[当前投影](../desktop/godot/shared/creation_runtime.mjs#L42)把文档 revision 作为 sourceRevision，而编译器另有工程修订校验。此项仍需用真实宿主链路复核。

## 7. 能力上限与证据口径问题

### A05：有限快捷操作应是快速路径，不能成为整个产品的表达上限

[creation-operations](../plugins/craftmine-world/creation-operations.cjs#L6)当前固定支持 tree、rock、chest、door、marker，并有有限动作与 64 条操作收据上限。作为早期受控能力合理；持续创作需要收据归档/去重的完整生命周期，避免世界最终因历史记录满而无法继续。

普通 Godot 源码补丁与构建工具仍存在，因此不能据此说整个产品只能造这五种对象。应明确从快捷操作转到模块检索、普通 GDScript 开发和必要扩展的路径，并验证模型能实际走通。

共享协议应覆盖目标身份、任务、内容引用、应用和恢复；对象类型与表现能力通过底座/资源版本扩展。无需强制宠物、飞机、城市都塞进树/石头这一类固定枚举。

### A06：固定源码生成器不能证明开放式 L1 开发

[generateSequenceDoorRule](../plugins/craftmine-world/creation-sequence-rule.cjs)把有限参数写入固定 GDScript 模板。本次证明这段真实脚本可以执行，并发现其与投影的差异；它仍然属于预制能力的配置与代码生成。

要宣布 Agent 已完成非预置玩法，需有真实模型读取工程、生成此前没有的逻辑、独立运行检查、玩家互动及重启证据。保留一个不在固定模板中的需求作为验收，不能把文件后缀为 `.gd` 等同于模型自主开发了新机制。

### A07：分层清单还不是一张完整的能力状态表

旧路线图仍写 L2 缺失，源码已存在扩展 ABI；早期文档与新总计划对阶段编号和能力状态有不同表述。此前回答引用旧 R2 报告把路由与初始进度缺口当成当前阻塞，不够准确，应撤回该现状判断。

当前沉浸面板和语音转写基础已经有接线记录；报告中的“当前环境没有 Godot”是当时环境描述，本机已存在固定 Godot 且本轮执行成功。以上仍不代表实际玩家语音、完整浮层合成或所有当前安装包已通过验收。

建议能力状态至少分别记录：声明/实现、可从工具调用、真实运行通过、模型完整故事通过、正式安装包交付。状态绑定准确运行目标、版本和证据，不只写“L1 完成”。

## 8. “Agent 开发整个 Harness”应如何理解

可以用开发 Agent 帮助维护和开发整个产品，但产品中的玩家 Agent 与平台维护任务承担不同职责。

| 范围 | 正常执行方式 | 不能混淆的事情 |
| --- | --- | --- |
| 世界内容与玩法 | 当前世界草稿、隔离检查、版本与进度应用 | 不因新增玩法自动取得宿主和个人文件权限 |
| L4 策略改进 | 独立策略版本、固定任务与保留样本对照、采用与回退 | 不能修改正在评估自己的标准来取得分数提升 |
| 工具网关、运行适配、数据库或恢复机制 | 平台维护任务中的独立版本开发与集成验收 | 不让游戏里的一条愿望热改正在服务所有世界的控制系统 |
| 测试框架、权限和数据协议 | 维护者授权的独立修改、迁移、反例和回归 | “冻结”指一次评测/执行期间不能由被测者放宽，不是产品永远不能修正错误标准 |

用户关于使用 Codex 子 agent 的要求适用于本项目后续并行开发与集成组织，不自动改变产品中既有 Agent 后端的实现或授权范围。

旧文件中“只有人能改”应区分产品执行权限和维护流程：维护者可以授权开发 Agent 编写修复，但该授权不能由游戏内容或被测模型自行生成。固定哈希也不能单独提供全部隔离，真正的权限边界还需要由宿主和执行环境落实；本轮未做完整隔离审计。

## 9. 验证逻辑需要调整的两点

第一，机器执行规则可以确定，但规则是否覆盖了玩家意图仍需判断。“白色博美是否像博美”“城市是否达到想要的观感”“战斗是否有趣”不能全部化成一条确定性断言。状态、碰撞、存档与预算用代码检查；语义和视觉用适当的模型辅助评估；体验通过玩家反馈校准。代码检查通过是证据的一部分。

这种按任务选择代码、模型与人工评估的方式，也与 [Anthropic 的 Agent 评测说明](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)相符。这里借鉴的是评测方法，不据此认定本项目已经实现完整评测体系。

第二，模型能力、上下文、可用工具、模块覆盖、执行可靠性和成本都会成为瓶颈。旧路线图“瓶颈不是模型”的说法过于绝对。应测量实际失败原因，而不是预先认定换引擎、加工具或延长思考必然解决问题。

同样，旧 Web 的逻辑测试与 Godot 的物理 headless 测试不是相同任务的速度对照；上一轮 57 项与 32 项存在重叠，不能累加成独立覆盖。本轮没有模型任务，不能据此比较两种路线的生成速度、成功率或 token 成本。

## 10. 建议的修正顺序

| 顺序 | 工作 | 完成的判断 |
| --- | --- | --- |
| 1 | 统一能力层定义、阶段映射和当前证据索引 | 同一个层级/阶段只有明确含义，状态可追溯到版本与运行目标 |
| 2 | 修正 A01–A04，并完成一条真实 L0/L1 故事 | 放树、碰撞、选中修改、真实机关、失败保留旧内容、重开都通过 |
| 3 | 加入一个固定模板没有的真实模型任务 | 模型新写逻辑，而非只填写现成模板；旧玩法回归仍通过 |
| 4 | 将通过的能力做成 L2 组件，在第二世界复用 | 依赖、独立身份、升级卸载、保存与回退均有证据 |
| 5 | 开展 L4 小规模对照 | 相同任务与环境，衡量成功率、费用、耗时，保留失败和未知 |
| 6 | 按需求安排 L3 平台扩展 | 有确切缺口，普通工程无法满足，独立平台版本可验收和恢复 |

这些是评估后的建议，不是本轮自动派发的开发任务。原代码与验收规则保持不变，补充诊断只在隔离副本运行。
