# 最中幻想 / Craftmine World：许可与商业授权方案

确认日期：2026-09-09。用户已在项目讨论中接受本方案。

状态：**许可设计已确认，逐模块权利核对与正式适用尚待完成。** 本文是项目决策记录，不是许可证、商业合同或对既有代码的重新授权。现有文件声明与第三方许可继续适用。

## 1. 已确认的选择

采用以下分层：自有创作核心以 **AGPL-3.0-only** 提供社区许可，并另行提供商业许可；导出游戏所需的自有运行时代码和示例脚本采用 **MIT**；上游代码保留其许可；未来具备独立授权条件的企业模块采用专有商业许可。

商业目标是让个人与工作室能够使用社区版制作、发布商业作品，同时为需要另一种核心集成或分发权利、企业功能、部署与支持的客户提供付费产品。企业身份、营业收入或作品销售行为本身不构成社区版的额外付费条件。

| 内容 | 目标许可 | 正式适用条件 |
| --- | --- | --- |
| PI-Desktop 及受其许可约束的修改 | 保留 LGPL-3.0-or-later | 保留上游来源、声明与修改记录，按实际分发方式履行相应源码、构建及替换或重新组合等义务 |
| 拥有充分授权权利的自有创作核心，包括生成流程、作品管理、验证与恢复 | AGPL-3.0-only，另提供商业许可 | 核对逐文件来源、依赖、权利归属、已有许可与交付历史；商业许可仅覆盖有权另行授权的部分 |
| 导出游戏必需的自有运行时代码、示例脚本 | MIT | 核对来源并明确导出清单；创作核心与导出运行时代码需有实际职责边界 |
| 未来独立企业模块，如组织管理、部署管理、企业系统连接器 | 专有商业许可 | 拥有充分权利，实际组合方式及全部依赖允许该分发方式 |
| Godot、字体、模型、音乐及其他第三方内容 | 各自原许可 | 逐项核对使用、修改、打包、作品导出与再分发条件 |
| 用户创作、导入的作品与素材 | 按作者选择及实际包含内容的许可 | 项目不因用户使用创作工具而主张其原创作品版权；不对 AI 输出或第三方素材作统一权属保证 |

AGPL 与商业许可是同一自有核心的两种可选授权路径。购买商业许可不免除第三方许可义务。不得在标准 AGPL 文本中附加“企业必须付费”条件后仍称其为标准 AGPL。[AGPL 正文](https://opensource.org/license/agpl-3.0)、[开源与商业使用](https://opensource.org/faq)

## 2. 面向用户的收费边界

| 使用情形 | 本方案的处理 |
| --- | --- |
| 个人或工作室使用社区版制作并出售游戏 | 不因销售作品而另收工具授权费，不收作品流水分成；随作品分发的代码和素材仍须遵守各自许可 |
| 企业使用未修改的社区版完成内部创作 | 不因企业身份要求购买另一套许可；部署或支持服务可自愿购买 |
| 修改社区版后分发，或让用户通过网络与修改版本交互 | 可选择遵守 AGPL 的适用义务；根据触发条件向相应接收者或交互用户提供对应源码，不概括成“公司所有代码必须公开” |
| 希望把自有核心闭源整合进产品，且该方式无法满足 AGPL | 可洽谈另一套商业授权，先确认实际集成范围和项目有权授予的权利 |
| 购买企业模块、部署、培训、维护及约定响应服务 | 按具体产品或服务合同收费 |
| 通过独立 API 与系统通信 | 根据实际程序关系和使用方式判断，不能仅凭 API 调用认定必须购买许可 |

AGPL 允许商业使用，不能保证企业都付费，也不能禁止他人在履行适用义务后运营收费服务。第 13 条针对修改版本的网络交互规定对应源码提供要求，不等于所有托管服务都必须购买商业许可。[AGPL 第 13 条](https://opensource.org/license/agpl-3.0)

## 3. 导出作品的边界

创作工作台负责模型调用、候选管理、验证和作品管理；导出运行时负责独立作品实际运行所需的功能。按实际代码和依赖划分两者，不以目录名称或是否独立进程代替许可判断。

导出流水线应生成文件与依赖清单，只纳入已确认允许目标发行方式的运行库、模板与素材，并携带必要版权、许可及第三方声明。若导出物包含受 AGPL、LGPL 或其他条件约束的代码，需单独处理，不能用“用户作品不抽成”代替分发合规。

MIT 允许商业使用、修改和再分发，须保留适用版权与许可声明。Godot 本身采用 MIT，允许游戏使用自己的许可；其内含依赖和游戏素材仍单独核对。[MIT 正文](https://opensource.org/license/mit)、[Godot 官方许可](https://godotengine.org/license/)

付费素材或模板若未来提供，需单独说明可用于哪些作品、能否再分发源素材及是否允许独立转售；本方案不自动改变现有素材权利。

## 5. 商业合同与外部贡献

商业许可应明确：授权主体、被许可主体、覆盖模块和版本、使用及闭源集成范围、托管与再分发权限、期限、更新与支持范围、费用和到期处理。区分软件授权费与服务费，不承诺覆盖第三方代码、素材或未知权属内容。具体价格与合同条款尚未确定。

对计划双重授权的核心，接受外部贡献前准备明确包含商业再授权权利的 CLA：贡献者保留原有版权，授权项目在约定范围内使用及再授权；公开解释商业用途，核对雇主权利和第三方来源。不能只收取 DCO 签署，就认为获得了任意商业再授权权利。[贡献者协议说明](https://www.apache.org/licenses/contributor-agreements.html)、[DCO 正文](https://developercertificate.org/)

CLA 不能追溯覆盖尚未同意的既有贡献，也不能替第三方版权人授权。MIT 的导出示例等贡献按其许可及项目贡献规则处理。项目名称与标识另行说明使用规则，避免将代码使用权误解为官方背书。

## 6. 实施顺序与完成标准

1. **逐模块权利清单**：为每个拟授权模块记录文件范围、来源提交、作者或权利人、现有许可、依赖、既有交付以及目标许可；未核对项保留为待确认。
2. **划分代码职责**：明确自有创作核心、上游修改、导出运行时和未来企业模块的实际边界；核对依赖与组合方式，不为改许可而仅移动文件。
3. **准备正式文本**：提供社区许可说明、商业授权范围、导出作品许可说明、核心贡献 CLA 与第三方清单。AGPL、MIT、LGPL/GPL 标准文本按适用范围原样附带；根目录提供清晰索引。
4. **核对法律文本和权利范围**：正式公开前由熟悉软件许可的律师核对模块边界、合同与贡献规则；填入确定的授权主体和权利人信息。
5. **应用并验证**：在已确认范围内同步文件声明、包元数据与发行流程，检查客户端和导出游戏的实际许可清单、对应源码及构建材料。

完成标准：每个对外发行模块都有可追溯的许可依据；社区使用、商业授权和作品导出的说明一致；商业授权范围不覆盖无权另行授权的上游代码；标准许可证和包元数据与实际分发内容一致。
