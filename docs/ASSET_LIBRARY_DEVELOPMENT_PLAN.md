## 1. 产品目标与首发边界

建立一个面向玩家和 AI 的本地素材与作品库：素材能被找到、预览、放入世界；做好的物件或玩法可以连同源码和依赖保存；每次复用使用固定版本；后续升级有变化说明、检查和恢复路径。

第一阶段覆盖本地导入、分类搜索、可信预览、固定版本安装、简单 Godot 物件保存与跨世界复用，以及完整备份。先将 3D 和俯视底座的必要链路跑通，横版按已交付能力逐步纳入。在线社区、交易结算、远程协作权限、大规模推荐和实时协同编辑放在后续。

首个完整场景：玩家导入一张门面贴图和一个门模型，让 AI 做成可交互的门；应用后保存为“自动门 v1”；在第二个兼容世界放入两扇门；只把其中一扇改红并保存为变体；以后升级门的规则时，看到影响与检查结果，原世界仍可使用旧版本。

## 3. 素材、物件、作品与模板

2026-09-10 在原四类规划上细化为七类；类型与包格式以[创作包计划第 3–7 节](CREATION_PACKAGE_DEVELOPMENT_PLAN.md#3-七类内容与分类边界)为准。本计划负责它们的本地正文、索引、预览和使用关系，CP 计划负责底座/模块开发接口与统一导出约定。

| 类型 | 玩家例子 | 必需内容 | 默认状态 |
| --- | --- | --- | --- |
| 底座 `base` | 第一人称、俯视、横版、卡牌桌面 | 最小工程、运行接口、能力/状态声明、兼容检查 | 通过验证后用于新建世界 |
| 世界 `world` | 小镇起点、完整横版游戏 | 初始工程、底座及版本、资源锁和入口；可用作模板 | 从作者设定的初始状态新建世界 |
| 玩法模块 `module` | 背包、交易、对话、合成 | 代码、参数、接口、依赖、适配及状态约定 | 安装进兼容工程，使用初始模块状态 |
| 原始素材 `raw` | 图片、模型、音效 | 文件正文、格式、预览、来源、版本 | 不含玩法进度 |
| 可用物件 `object` | 自动门、宝箱、武器 | 场景、脚本、碰撞、默认参数、素材依赖与适用底座 | 使用作者明确的初始状态 |
| 场景/关卡 `scene` | 商店建筑、战斗区域、地图片段 | 多实体场景、入口/锚点、固定依赖和状态接口 | 新实体身份，不继承来源玩家的钱和奖励 |
| 数据 `data` | 配方、物品属性、对白 | 数据正文、结构版本、稳定记录 ID 与目标模块接口 | 初始配置，不含个人游玩记录 |

旧 `creation` 保留为历史格式，通过适配按实际用途转为 module/object/scene/world；旧 `world-template` 对应 world 的模板用途。迁移创建新记录并保留原包与映射，不就地改写旧资源类型或哈希。

类型与范围分别建模：“当前世界”“我的本地库”“导入来源”是查询范围，不是另造三种文件格式。未来团队库和社区库通过明确来源加入同一检索界面。

资源的“已索引”“可预览”“已通过某底座检查”“已应用于来源世界”分别记录，不能用一个绿色标签代表全部。兼容性是对具体版本、底座、引擎、目标及检查记录的结论。

普通素材可有不可变版本清单，不必为每张图片创建一个 Git 仓库。含可编辑工程的作品可以关联来源 `ContentRef`，便于追溯与继续创作；不为每个物件实例创建仓库，世界工程仍按 VM 计划拥有独立仓库。

## 5. 数据模型与共同契约

共用格式以[版本管理计划第 5 节](VERSION_MANAGEMENT_DEVELOPMENT_PLAN.md#5-与素材库共用的数据契约)为准：`AssetRef={assetId,version,contentHash}`、`FileRef`、`ContentRef`、`BuildRef`、`ProgressRef` 和 `OperationContext`。不另建相似但含义不同的引用结构。

| 对象 | 内容与规则 |
| --- | --- |
| 资源身份 | 稳定 `assetId` 与类型；名称不是身份，改名不改变世界引用 |
| 资源版本 | 第一版使用递增整数；保存不可变运行内容清单、文件、固定依赖、底座/引擎/目标约束、状态格式及来源记录 |
| 内容哈希 | `contentHash` 根据规范化不可变内容清单计算；各文件另有 SHA-256。相同 ID/版本却内容不同必须冲突，不能覆盖 |
| 展示元数据 | 标签、收藏、备注等可更新；与影响运行的版本清单分开，禁止通过改展示字段变更代码/依赖 |
| 实例绑定 | `instanceId`、固定 `AssetRef`、模板实体到世界实体的映射，以及局部覆盖引用 |
| 检查记录 | 检查对象的准确版本、底座、引擎、目标、检查器版本和真实结果；不由模型填写通过状态 |
| 使用关系 | 世界当前内容、历史提交、草稿、作品依赖和本地保留归档对资源版本的引用 |

第一版在现有 Rust/SQLite 领域存储中扩展索引，不引入第二套独立“素材事实数据库”。大文件正文按内容哈希保存；界面缓存和搜索索引可重建。跨世界去重只合并相同正文，不合并不同作者来源、许可或逻辑身份。

每个工程提交携带 `craftmine.assets.lock.json`（`craftmine.assets-lock/1`），固定所需资源版本和完整依赖。AL0 与 VM0 一起冻结规范化、路径、排序、重复引用、依赖环和哈希规则，并提供相同测试向量。

## 6. 导入、索引与预览

导入路径：用户选择文件/文件夹或 AI 生成任务产物 → 宿主接收文件句柄/限定路径 → 限额与格式检查 → 分块计算哈希并写临时正文 → 校验完整性 → 原子登记资源版本 → 异步建立索引和预览。导入登记与放入世界是两项操作。

玩家导入使用流式传输或宿主文件读取，避免把大素材 Base64 经过聊天工具。现有模型小载荷入口可保留；大生成结果通过受管理产物句柄登记。单文件、总容量、解码预算、并行预览和构建预算分开管理，不仅放大一个 JSON 限制。

首发格式：PNG/JPEG 图片、静态 GLB、WAV/OGG 音频，以及经检查的 Godot 场景/脚本作品包。带骨骼/动画 GLB、外链 glTF、FBX、MP3 和其他格式按 AL4 后的实际适配结果扩展；不能因为 Godot 引擎能导入就承诺本产品完整支持。

目录扫描只处理用户选择的范围。目录监听发现外部文件变化时提示新内容，确认登记为新版本后才供新引用使用；不静默改写已有世界或删除用户原文件。路径穿越、Windows 保留名称、大小写冲突与链接目标都在登记前核对。

预览按内容哈希、预览器版本、引擎版本和设置建立缓存。静态资源使用固定预览场景；物件和含脚本作品预览依赖 GD0 的可信隔离执行器。格式探测、图片解码、模型导入失败和超时分别展示，不用占位图当作已成功预览。

正文已登记但预览失败时，资源可保留为明确失败状态；不得因此标为可安装。单个预览失败不影响其他卡片或正式世界。关闭面板后取消不需要的任务，重开根据内容身份复用缓存。

## 7. 玩家界面与 AI 使用方式

在现有世界与右侧对话布局中，将“素材与作品”作为按需展开的面板：范围/分类在左，卡片列表在中，详细预览与版本在右。窄窗口使用列表与详情切换，返回时保留检索条件和选中项。

卡片至少显示名称、类型、真实预览或当前预览状态、版本与底座兼容情况；详情显示作者/来源、许可说明、依赖、检查记录、版本变化与“哪些世界在使用”。底层哈希和文件列表放到可展开详情。

首批操作为导入、搜索、标签/收藏、预览、加入世界草稿、保存选中物件、另存变体、选择版本、查看使用关系、导出作品包和归档。操作返回真实回执后更新状态，失败保留检索和选择，不把请求发送成功写成已安装。

AI 优先读取当前世界和本地库，以紧凑元数据、固定引用和必要源码作决策：直接复用、基于已有版本改造或新建。记录实际引用与改造来源，不把复制预制内容报告为从零生成。避免把全部素材正文放入上下文。

[C / D / L 愿望、模型与社区总体方案](WISH_CDL_FRAMEWORK_AND_NORTH_STAR_PROPOSAL.md)将本地库作为模型选择前的能力来源：先查询、核对可复用条件，再评估剩余难度。资源摘要需区分外形、实际行为、可配置参数与验证范围，例如静态飞机模型和可驾驶模块不能只以“飞机”标签混为一类。教程、参考工程、可安装模块与完整模板具有不同复用成本。

能力、参数和安装配方按 CP 的内容契约组织，AL 提供准确正文、固定引用、索引和使用关系；Agent 负责提出选择，宿主处理依赖与安装检查。小模型是否适用由真实配置任务评测决定，不因资源已经入库就跳过目标世界验证。

元数据中的描述与脚本是待处理内容，不是系统指令。模型可提出名称、标签和用途；资源事实、来源记录、版本身份与检查状态由宿主验证。临时失败产物留在任务记录，正式应用后的内容始终有历史；玩家保存或明确启用的归库规则才将其提升为可浏览的收藏作品。

拟增加按资源版本读取、依赖解析、保存作品、安装提案、升级提案和使用关系查询能力，沿用已有 `library_*`、`godot_asset_*` 命名的适配思路。新接口名称在实现时注册；本文不把拟定能力写成现有工具。

## 8. 安装、实例修改与升级

1. **保存作品**：从准确的已应用版本读取选中实体和依赖，定义锚点、稳定模板实体 ID、参数与初始状态；使用新实例验证其完整性，再登记不可变作品版本。跨实体引用不能遗漏。
2. **安装版本**：解析固定依赖、检查底座/引擎/目标及权利状态，取得全部正文，在目标分支草稿生成实体、文件和素材锁修改；提交候选后执行真实构建和结果检查。
3. **应用**：通过版本管理 VM2 的正式应用事务完成，不由素材库直接改动运行中的正式世界。源世界的游玩奖励和实例进度默认不复制。
4. **局部修改**：“这扇门变红”默认生成选中实例的局部覆盖，保留其身份；需要复用时保存为变体或明确的新资源版本。结构性改造可产生独立派生作品，保留来源。
5. **升级**：列出目标实例及其当前固定版本，与新模板和本地覆盖做兼容比较。冲突要保留双方选择；升级形成新草稿、固定锁和迁移检查。世界继续使用旧版直到确认应用。
6. **卸载与归档**：卸载世界实例先检查被引用实体、背包物品和任务依赖，再形成候选；从库中归档仅影响浏览，不删除仍被历史或世界使用的正文。

同一资源 v2 发布后，引用 v1 的世界不自动更新。修改库里的显示名称不改变实例内容。批量升级跨世界时，每个世界有独立提案与事务，明确逐个结果，不假装多个世界共享一次原子提交。

状态迁移基于稳定身份和版本协议；新装物件使用模板初始状态，升级已用物件保留兼容进度。门的开关、宝箱是否领取、商店库存与一次性任务奖励分别覆盖测试。复制模板实体时为新实例分配新世界身份，不能让两个实例共享同一奖励记录。

## 9. 来源、许可与导出

资源记录来源、作者声明、版本、文件哈希、许可文本引用和用途范围。区分客户端随包分发、玩家作品导出、仅本地使用与尚未核对；“MIT 的库管理代码”不等于“库中所有素材都是 MIT”。

允许本地登记来源不完整的用户素材，并明确显示待核对；对外分享和发行时按[已确认许可方案](LICENSING_STRATEGY.md)检查相应权利和声明。AI 不能仅根据文件名、网站标签或生成过程填写“可商用/可再分发”。

作品包仅携带准确版本的必要资源、源码、依赖锁、初始状态和适用声明。个人完整备份另外覆盖版本历史、选择的进度及保留草稿。导出中排除凭据、私有对话和不需要的全库资源；缺依赖正文或声明时报告具体缺项，不输出看似完整的包。

现有 `desktop/delivery/base-assets` 清单与新库互相引用确切正文，继续进行实际字节和声明检查。显示元数据中的许可修订不悄悄改写旧内容和原始来源记录；分发判断变化需保留变更记录。

## 10. 迁移、备份与清理

迁移旧 `asset id/version/hash` 和 `library-bundle/1` 时保留原始定义、哈希与映射，不改写历史包以伪装成新格式。可转为 Godot 的内容创建新版本与转换记录，旧世界继续由旧运行器使用；不支持的脚本或能力逐项说明。

新 Godot 素材表已登记的文件先按实际正文与历史构建清单建立来源，不能假设同名文件就是同一资源的连续版本。迁移以副本试验、核对和一次登记完成，失败可继续使用原路径。

完整备份与 VM1/VM2 共用归档任务：固定数据库快照和 Git 引用，遍历资源依赖，校验正文并写归档清单。跨两个存储的快照必须有可验证的共同边界，不能边写世界边随意复制文件夹。

清理区分预览缓存、无引用临时正文、已归档逻辑资源和被历史引用的版本。正式世界、草稿、分支、命名版本、迁移保留项以及本地备份保留项均阻止误删；归档不会破坏旧版本。外部导出包必须自包含，不能依赖当前机器以后仍保留某个缓存。

支持扫描/预览取消、导入中断与重新登记；相同操作 ID 返回同一结果，相同正文可去重。磁盘满、文件被锁定或哈希冲突时清楚记录失败，未完成资源不进入可安装清单。

## 11. 开发阶段与验收出口

| 阶段 | 工作与交付物 | 依赖 | 阶段出口 |
| --- | --- | --- | --- |
| AL0 契约与开源评估 | 冻结资源类型、固定引用与锁文件；评估上游代码，固定选择的提交/许可；形成格式与容量试验表 | 当前基线、VM0/CP0 同批冻结 | 配套计划共用测试向量；候选有真实源码评估结果；预算明确区分建议值与实测值 |
| AL1 正文与不可变版本 | 流式导入、哈希存储、多版本索引、完整依赖解析、旧格式映射、初步备份 | AL0、VM0 | 大于当前 512 KiB 的真实素材能按新预算导入；同版冲突拒绝；中断不产生伪完整资源 |
| AL2 浏览与预览 | 分类、搜索、标签、缩略图、图片/模型/音频预览、失败与取消状态 | AL1；脚本预览需 GD0 | 已支持格式实际显示/播放，坏文件不影响其他资源；UI 和独立预览边界通过 |
| AL3 简单物件闭环 | 保存门等单物件、固定依赖安装、独立实例、局部覆盖、接入 VM2 应用 | AL1/AL2、VM1、GD0/GD2 | 两个兼容世界复用同一版本；修改一个实例不改变其他实例；保存重启与备份恢复通过 |
| AL4 组合作品与升级 | 多实体作品、模板、状态迁移、升级/卸载提案、冲突及更多格式适配 | AL3、VM2 | 商店/战斗区完整依赖安装；升级保留状态，奖励不重复；旧版本继续可用 |
| AL5 完整库管理与交付 | 使用关系、归档/清理、许可清单、作品包和完整备份、旧库迁移 | AL3、VM2；复杂作品部分依赖 AL4 | 清理后历史可重现；新目录恢复完整；实际发行清单与正文相符 |
| AL6 远程与团队来源 | 远程目录接口、内容上传/下载、LFS 适配、同步完整性、来源权限 | 固定包目录/传输子集可在 AL1/CP1/CC1 及所用类型恢复就绪后先交付；完整同步需 AL4/AL5、VM4 并联调 VM5 | 两台环境获得相同固定资源，传输中断可恢复，未授权资源不会随分享泄漏 |
| AL7 社区作品库 | 作者主页、分享、Fork 来源、审核；团队与交易按 CC 后续阶段 | AL6 已交付子集与 CC1/CC2；完整 Git 协作对接 VM6 | 按社区计划分类型验收开放，交易需 CC6 独立条件 |

首发必须包含 AL0–AL3，以及 AL5 中备份、使用关系保护和所用资源的声明清单；不能把恢复能力全部推迟到社区阶段。VM2 与 AL3 联合验收，不把单独“存入库”当作完成玩家创作闭环。

当前单文件、总量和引擎预算保持为已知基线，AL0/AL1 用真实样本确定升级值。拟测 1 千/1 万资源、1/16/64 MiB 文件及不同解码成本，分别记录可接受与明确拒绝范围；这些是测量档位，不是承诺全部支持。UI 首次可用时间、搜索/预览 P50/P95、内存峰值、取消时延、扫描速度、磁盘去重和构建增量均保留冷/热缓存条件。

## 12. 必须覆盖的验收场景

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| A01 | 导入支持格式的真实文件 | 正文哈希、解码/导入结果和预览一致；名称不能代替格式检查 |
| A02 | 大文件与分块中断 | 预算内可恢复完成；超限有具体错误，无伪完整资源和 UI 假成功 |
| A03 | 同版不同内容、重复操作和相同正文 | 冲突拒绝；相同操作返回同一结果；去重不合并来源与许可 |
| A04 | 坏图、模型引用缺失、预览超时 | 状态准确，正式世界和其他资源保持可用 |
| A05 | 当前世界引用 v1，库里新增 v2 | 旧世界仍显示并运行 v1；新版本可独立预览 |
| A06 | 同一模板放两个实例，只改其中一个 | 实例身份、局部覆盖和进度独立 |
| A07 | 自动门保存后跨世界复用 | 外观、碰撞、源码、声音与交互真实存在；使用初始状态 |
| A08 | 商店/战斗区的传递依赖和版本冲突 | 完整闭包可安装，缺项/冲突明确，不能运行部分拼装包 |
| A09 | 升级宝箱、商店或任务作品 | 兼容状态保留；领取、消耗与奖励不重复；失败恢复旧实例 |
| A10 | 目标世界已有本地覆盖 | 明确保留或冲突，不用新版静默覆盖玩家修改 |
| A11 | 归档、卸载和清理 | 使用关系正确；当前/历史/草稿引用均不损坏；用户源文件不被删除 |
| A12 | 导出到新目录或另一台环境 | 精确依赖、声明和内容齐全；不依赖原机器缓存，不带凭据或默认私有进度 |
| A13 | 旧 Web 包与 Godot 存储迁移 | 保留原始版本和来源；不支持项明确；失败不破坏原库 |
| A14 | AI 检索并安装旧作品 | 工具记录实际固定引用；模型不能伪造资源存在、兼容或检查通过 |
| A15 | 目录监听、路径碰撞、链接与外链文件 | 只在授权范围扫描/读取；变化生成新版本提示，不隐式更新世界 |
| A16 | 切世界时旧搜索/预览请求返回 | 结果不串到新世界，任务取消与缓存身份正确 |
| A17 | 实际打包资源与许可清单不一致 | 预检明确失败；不以清单自测通过替代实际分发检查 |

真实模型验收至少包括“检索并复用自动门”“在既有版本上改造”“保存到另一个世界复用”“升级保留状态”四种任务，保留失败、人工干预与素材引用。固定作者作品、模拟工具和真实模型结果分别报告。

浏览器、Electron 和 Godot 自动验证均使用独立 headless/offscreen 进程与独立测试数据；初始化禁用 Pointer Lock，通过 HTTP、页面脚本和引擎状态接口断言，不发送真实鼠标键盘、不置前窗口、不操作用户浏览器。音频预览用后台解码/状态与离线信号验证，不在自动测试中主动播放给用户。[项目约束](../AGENTS.md)

## 13. 联合实施顺序与交付要求

共同入口是 AL0/VM0/CP0；随后 AL1 与 VM1 建立内容基础，CP1 完成静态包往返，AL2 完成浏览预览；GD0/GD2 提供正式执行和应用条件后，AL3、VM2 与 CP2 完成“门的版本创作—应用—跨世界复用—恢复”的联合样本。再推进模块/场景/世界包、玩家底座、合并、发布与远程同步。普通社区目录按 CC1/CC2 接入，不等待完整 Git 托管。

每阶段交付代码、来源与许可清单、实际验证结果、失败与未验证范围、迁移/恢复说明。共享契约变更必须同时更新版本管理计划及测试向量。工作量在 AL0 的源码评估和格式/容量样本完成后估算，不把两个已有开源项目的功能列表直接当作本项目的交付承诺。
