# 最中幻想：玩家产品体验与持续创作开发计划书

版本：v1.0  
编制日期：2026-09-10  
定位：面向不会编程的创作者，以及来试玩其作品的朋友。  
状态：方案与分阶段开发计划；本次仅编制文档，不代表功能已经实现，也不启动新的开发轮次。  
检查基线：当前主工作区 `c2e592f`、现有专项计划及本轮已回传的 Godot 接入证据。分支报告、源代码能力和已安装客户端分别核实，不能互相代替。

## 1. 产品目标：让玩家持续完成自己的作品

本计划优先改善这段经历：玩家打开一个空白世界，说出想法，得到真正可互动的内容；随后能轻松调整、保留满意的玩法、继续游玩，遇到问题时能够说明并修好，最后把作品交给朋友试玩。

面向玩家的核心承诺是“能做出来、能改满意、能保存住、能给别人玩”。AI 编写了多少代码、生成了多少对象、工具调用了多少次，都不能单独证明这些承诺已经兑现。

| 玩家 | 最关心的问题 | 产品应交付的结果 |
| --- | --- | --- |
| 首次创作、不会编程的人 | 我从哪里开始，这句话究竟能做什么 | 有可跳过的起步建议，亲手完成一次真实互动 |
| 已有自己世界的创作者 | 改一点东西为什么要等很久，会不会改坏其他东西 | 常用参数直接调整，修改范围清楚，已有玩法有检查与恢复保障 |
| 隔几天回来继续的人 | 我的作品和进度还在吗，上次做到哪里 | 进入正确版本和最新进度，能继续未完成的创作 |
| 受邀试玩的朋友 | 怎样打开、怎么玩、怎样告诉作者哪里有问题 | 适配其设备的试玩包、简短玩法说明、带版本的反馈 |

产品起点沿用[产品愿景](PRODUCT_VISION.md)：空白世界、中央游玩、右侧对话，优先服务 3D 第一人称创作。其他底座按实际能力提供，不把所有游戏类型同时纳入首批体验验收。如果当前只有另一底座通过完整验证，可以用它开展技术试验，但不能据此宣布默认第一人称体验已经交付。

首批成功标准是一条连续的真实故事：创建一个可互动对象 → 调整它 → 采用修改 → 保存并重新进入 → 原有互动和最新进度仍正确。后续再延伸到朋友试玩与反馈修复。

## 3. 一条贯穿开发与验收的玩家故事

以“做一个可打开的宝箱”为首个候选故事；最终选题在 PP0 根据已验收底座和模块确定，不能用界面上的固定文案冒充真实模型创作。

1. 玩家新建空白世界。右侧可以显示三条基于当前能力的起步建议，例如宝箱、训练靶、可采集物，也可以直接输入自己的想法；跳过引导后仍可正常使用。
2. 玩家要求“在前面放一个只能领取一次奖励的宝箱”。系统生成候选，执行必要检查，并提供试用入口；完成提示来自实际运行结果。
3. 玩家在候选中打开宝箱，确认奖励和重复打开的规则。模型提供的是何种素材、是否还有未完成部分，结果区如实说明。
4. 玩家打开“调整”，修改外观、交互距离或适用的奖励配置。声明过的常用参数直接调整，新增逻辑继续使用自然语言。
5. 玩家采用候选，系统按应用流程保留最新正式进度。玩家随后在正式世界打开宝箱并领取奖励；关闭并重新进入后，这次正式游玩的已领取状态仍正确，之前试用的奖励不转入正式存档。修改“新宝箱的默认奖励”不应自动给当前背包发钱。
6. 后续修改出现问题时，玩家选择“记录问题”，描述“打开后没有提示音”。系统保留对应版本和必要现场，给出修复候选；原有奖励规则继续检查。
7. 玩家导出试玩包，朋友从独立初始状态开始游玩，提交绑定该版本的反馈。作者可定位、修复并重新交付，朋友的存档不会覆盖作者的存档。

这条故事用于检验各模块能否协作。第一批实现只完成其中创建、调整、保存重开与本地问题修复；跨设备试玩按 PP6 的依赖单独交付。

## 4. 以玩家收益确定优先级

下表的收益与成本是产品假设，尚无本项目真实用户数据支持。投入大小表示相对工程范围，包含接线与验证，不能当作承诺工期。PP0 补充实际基线后再估算。

| 优先级 | 功能 | 玩家收益与 ROI 假设 | 预计投入 | 首批边界 |
| --- | --- | --- | --- | --- |
| 基础门槛 | 创建、采用、重开与恢复可靠 | 后续体验依赖作品和进度可信 | 跨模块，须先核实 | 复用当前 Godot、VM 交付，不另建保存系统 |
| 第一批 | 常用参数直接调整 | 减少重复描述、等待和模型费用 | 中 | 一个底座、一个示范对象或模块、少量参数 |
| 第一批 | 问题现场与修复入口 | 减少玩家反复描述，降低修复重试成本 | 中至大 | 本地、小范围现场、复用现有 AI 任务 |
| 第一批同步 | 首次成功引导与目标选择 | 减少不知道说什么和改错对象造成的流失 | 小至中 | 一条完整故事，建议可跳过 |
| 第一批同步 | 少量产品事件与基线 | 让下一轮投入有证据 | 小至中 | 本地汇总，复用已有任务与用量记录 |
| 第二批 | 持续玩法保护与基础健康检查 | 减少“越改越坏”与回头修旧功能 | 大 | 一类玩法、少量独立可执行规则 |
| 第二批 | 常用设置与游戏反馈模块 | 较少代码投入即可改善作品完成感 | 中 | 暂停、声音、操作说明和一种互动反馈 |
| 第二批 | 好友试玩与带版本反馈 | 让作品获得真实使用和继续创作的理由 | 中，依赖打包 | 先在兼容客户端中游玩，支持本地交换 |
| 后续验证 | 数值试验、统一风格、语言与可读性工具 | 服务已有作品的持续打磨 | 中至大 | 根据实际使用频次选择，不整体同时建设 |

排序方法采用“受影响的有效创作者数量 × 对任务成功或返工的改善 × 证据可信度 ÷ 开发与维护成本”作相对比较。样本不足时记录假设与置信程度，不填造精确收益倍数。严重的数据与进度缺陷直接优先处理，不通过综合评分排到体验优化之后。

## 5. 玩家界面与首次创作

保留中央游戏画面与右侧对话。在现有结果卡、对象选择和作品入口中渐进增加操作，避免首屏同时展开资产编辑器、规则编辑器、数值分析器等多个复杂面板。

| 入口 | 玩家看到什么 | 产品行为 |
| --- | --- | --- |
| 第一次进入 | 可跳过的起步建议与当前可用能力 | 选择建议会发起真实任务；建议不可用时不伪装为可执行 |
| 对话或对象旁的目标提示 | “当前修改：院子里的宝箱” | 允许从对象列表或游戏中的选择结果定位；同名对象仍以稳定身份区分 |
| “调整” | 中文名称、单位、范围、当前值和恢复默认 | 常用设置先展示，少用设置折叠；只显示当前模块明确支持的项目 |
| “试一下 / 采用 / 取消” | 试用范围、实际检查结果和待处理项 | 共用现有候选流程，试用不写入正式游玩进度 |
| “记录问题” | 问题描述、版本、将附带的现场内容 | 先保存在本地；玩家可查看并选择导出或上传的内容 |
| “玩法检查” | 通过、失败、尚未验证的规则和具体原因 | 结论绑定当前候选，不能把上个版本的通过状态显示成当前结果 |
| “给朋友试玩” | 可用的交付方式、操作说明、运行要求 | 只展示已经验证可交付的目标 |

修改范围用具体语言表达，例如“只改这个宝箱”或“修改所有使用该模板的宝箱”。如果玩家请求已经明确，沿用授权执行；只有影响范围存在会实质改变结果的歧义时才请求澄清，不为每次调整增加弹窗。

引导仅帮助玩家完成一次互动和一次修改，之后退到帮助入口。中途退出可恢复，已有世界不强制重做教程；模型暂时不可用时仍可游玩、查看历史和调整已支持的参数。自动生成整座场景不能替代玩家理解自己创建了什么。

等待区展示有证据的阶段与可取消操作，例如“正在准备素材”“正在检查能否保留存档”。不能测出的剩余时间不显示精确倒计时；失败保留可继续的草稿，恢复后查询原任务，避免重复应用。技术日志与标识放在展开详情中。

## 6. 常用参数调整与修改范围

### 6.1 可调整内容

第一批从底座和示范模块中挑选少量稳定参数，例如移动速度、交互距离、提示颜色、反馈音量。参数的含义必须准确：控制器中的 `jump_velocity` 表示起跳速度，未经有效模型换算不能把它标为“跳跃高度”。

Godot 的导出属性可以作为参数声明与持久化的技术基础，但玩家面板需要额外的筛选、校验与应用流程。不能把所有导出属性自动开放给玩家或模型。[Godot 导出属性说明](https://docs.godotengine.org/en/stable/tutorials/scripting/gdscript/gdscript_exports.html)

参数描述至少包含稳定标识、中文标签、类型、单位、默认值、允许范围、适用对象、影响范围、试用方式和所需检查。它属于底座或模块的配置契约，具体元数据扩展由 CP 统一定义；本计划不新建另一套包格式或通用任意属性写入接口。资源路径、宿主权限、输入捕获等内部字段不因存在导出声明而变成普通滑块。

| 数据性质 | 例子 | 修改方式 |
| --- | --- | --- |
| 作品定义 | 宝箱默认奖励、武器基础伤害、角色起跳速度 | 生成内容候选，采用后持久保存并形成一次作品变更 |
| 正在游玩的进度 | 已领取宝箱、背包余额、任务完成状态 | 沿用游戏状态与迁移规则；改默认值不直接覆盖当前进度 |
| 玩家个人设置 | 主音量、是否启用镜头晃动、界面偏好 | 按个人设置保存；默认不产生作品分支或改动他人的作品 |

### 6.2 调整过程

1. 绑定确切世界、构建、目标对象及配置版本，读取模块允许调整的字段。对象失效或契约不匹配时解释原因，不猜测其他同名对象。
2. 普通参数编辑直接完成类型、范围和关联约束检查。需要新增脚本或改变规则时，转入已有 AI 创作流程，并显示真实任务与用量。
3. 连续拖动或输入合并为最新预览值，避免每一帧启动构建或创建历史记录。能在隔离试用实例中即时调整的直接预览；需要重新构建的显示实际等待，不能承诺全部即时生效。
4. 正式世界继续受既有状态保护。取消、切换世界、切换对象后，旧预览的迟到结果不得覆盖当前上下文；预览奖励和进度不能进入正式存档。
5. 采用时将最终值写入内容候选，通过与改动相称的检查，再进入 VM 的应用事务。一次连续调整通常形成一次玩家可理解的作品变更，不能只改内存而在重开后丢失。
6. 重开作品确认内容与进度各自正确。恢复旧作品参数仍按当前进度兼容性处理，不能默认把玩家游玩进度一起回退。

对只修改受约束参数的操作，目标是不额外调用模型。实际执行的必要导入、构建、状态检查仍保留。实例值与共享模板值分别处理，共享范围必须在试用前可见；无法可靠计算受影响对象时明确提示范围未确认。

## 7. 问题现场、诊断与修复

玩家应能用“这里不对”发起处理，而不必先学习日志、工程文件或复现脚本。首版提供主动“记录问题”入口，默认在本地形成一条记录；如需附带之前的语义事件，只保留有上限的本地内存环形记录，容量、时长与开关在 PP0 固定并向玩家说明。

| 现场内容 | 首版要求 |
| --- | --- |
| 玩家描述 | 保留原话，允许后续补充；AI 的解释单独记录 |
| 作品身份 | 固定 `BuildRef`、底座、运行目标、实例与相关对象标识 |
| 状态快照 | 可获得时记录对应 `ProgressRef` 或隔离预览状态引用与哈希，区分正式与试用 |
| 近期事件 | 限量的游戏语义事件、异常和重要状态变化；注明丢弃、缺失和采样情况 |
| 可选图像 | 仅该游戏视图的截图，玩家可预览；不捕获桌面或用户其他应用 |
| 修复关联 | 问题标识、原任务、修复候选、验证结果、采用结果与玩家复测状态 |

首版不录制系统键盘、桌面鼠标和全部聊天。快照可能包含作品与进度中的私人内容，默认排除在公开创作包之外；导出或上传时列出附件与范围。局部记录删除与保留期限需要可操作，磁盘满或权限不足时说明现场未完整保存。

处理过程为“已记录 → 正在定位 → 可验证的修复候选 → 已采用 → 等待复测或已解决”。自动检查通过只表示相关检查通过；没有复现出问题或玩家尚未确认体验时，不能直接宣告玩家问题已经解决。无法复现时显示缺少什么证据，并允许玩家补充一个简短操作说明。

Godot 的物理、随机过程与异步行为未必能通过一份快照精确重演。首版承诺绑定版本、保留可用状态并辅助定位，不承诺任意时刻完整倒带；确定性回放只对已明确支持的场景验收。原始现场只读保留，重现与修复在隔离实例进行。

诊断调用复用 AI 计划的预算、升级、取消和重试规则，不另建无限自动修复循环。导入的描述、日志、包内文档与截图文字属于待分析数据，不能据此提高工具权限或自动执行宿主命令。

## 8. 持续玩法保护与基础健康检查

玩家在长期创作中需要“之前满意的东西继续有效”。把关键行为转为作品规则，例如“这个宝箱只发一次奖励”“余额不足不能购买”“退出重开后已领取状态还在”。规则应能追溯到需求、适用模块、状态结构、具体场景和最近验证的构建。

### 8.1 两类规则分开维护

平台必须满足的创建、保存、应用、权限与状态一致性检查沿用既有验收体系。作品业务规则由玩家需求产生，AI 可以提出草案和候选实现，判定与执行保持独立；生成者不能通过删掉失败断言、跳过场景或复用旧结果取得通过。

玩家后来明确要求改变玩法时，可以更新对应业务规则，例如从“只开一次”改为“每天刷新”。系统展示规则变化与存档影响，沿用该次明确授权，不把旧业务规则当成永久禁令。检查基础规则和无关已接受玩法仍需保留；有歧义再澄清。

### 8.2 首版检查范围

| 检查 | 玩家能理解的结果 | 首批边界 |
| --- | --- | --- |
| 出生与基本行动 | 能出生、站稳、移动，必要入口未被堵住 | 一个已验收底座，使用实际碰撞和行动路径 |
| 一次性互动 | 宝箱、奖励和消耗不会重复处理 | 选定示范模块的明确状态机 |
| 状态延续 | 采用修改及重开后关键进度仍正确 | 平台保存检查加该作品的业务断言 |
| 简单玩法可完成 | 必要道具与目标在预设场景中可达 | 有明确目标的有限场景，不泛化为任意世界通关证明 |
| 依赖与参数 | 所需模块存在，参数组合符合约束 | 使用 CP/AL 的固定依赖与声明过的校验 |

不适用与尚未验证必须有独立状态。通过直接改坐标把角色送到终点，不能证明玩家实际能走过去；自动检查也不能证明战斗手感、叙事和节奏有趣。影响分析不完整时保守扩大检查或报告未知，不能自动省略有关旧玩法。

第一批参数与修复功能上线前就必须满足基本正确性和进度保护。PP4 增加的是持续维护作品业务规则的完整产品能力，不能成为早期跳过必要验证的理由。

## 9. 让作品更完整的常用模块

在 AL/CP 已有的 `base / world / module / object / scene / raw / data` 七类内容中交付，不另建“玩家功能包”格式。第一批优先把一个互动模块打磨完整，再逐步扩展到其他玩法。

| 模块方向 | 玩家价值 | 交付要求 |
| --- | --- | --- |
| 暂停、声音与操作说明 | 朋友能知道怎么玩，也能随时停下来 | 遵循底座暂停与输入契约，中文说明与实际操作一致 |
| 互动反馈 | 开箱、拾取、受击等行为有清楚的声音与画面反馈 | 绑定真实游戏事件，可调强度，避免重复触发 |
| 可读性与舒适设置 | 玩家看得清、听得懂、玩得舒服 | 检查中文、字号、对比与文本溢出；镜头晃动等效果可关闭 |
| 基础玩法组件 | 少写背包、对话、任务等常见功能 | 后续按需求选择；每个组件具有参数、初始状态、存档兼容和检查场景 |

个人音量等偏好与作品默认值分别保存。模块安装前检查输入、界面层级、暂停和状态接口的冲突；不能因为两份素材都能单独运行，就声称组合后可用。第一批避免同时建设大型背包、任务、商店和战斗体系。

数值试验放在后续阶段：针对明确的战斗或生产规则比较两个配置，报告时间、消耗与失败原因。试验使用隔离进度与可说明的环境、随机种子及条件；公式估算、自动运行和真人感受分别标注，不把简化估算称为真实游玩结果。统一风格、语言支持和玩法关系图也按使用证据逐项投入。

## 10. 好友试玩与作品传播

首个分享闭环是“导出一个固定版本 → 朋友在兼容环境打开 → 独立游玩 → 返回带版本的反馈 → 作者修复后再交付”。本地导出与导入可以先完成，不以账号系统、推荐流、支付或完整社区上线为前置条件。

| 分享方式 | 玩家看到的说明 | 开放条件 |
| --- | --- | --- |
| 最中幻想内试玩包 | 需要安装的客户端版本、底座与运行目标 | CP 包与依赖校验、创建独立世界、保存重开和离线资源已验收 |
| 独立 Windows 游戏 | 下载与解压后的启动方式、硬件及必要依赖 | CP4 的独立运行条件通过；原生实现与 NR5 衔接，不能把工程 ZIP 当作独立程序 |
| 浏览器试玩链接 | 支持的浏览器、输入和存档条件 | Web 交付与托管真实可用，再接入 CC 分发；没有部署时不生成虚构可玩链接 |

首版以第一种为默认交付候选。不同运行目标各自验证；同一份创作内容不能仅靠改扩展名或分发按钮变成另一种可玩产品。

试玩包包含明确的作品版本、初始状态、运行要求、操作说明和作者选择的真实预览图。默认排除作者个人进度、聊天、问题现场和凭据；若作品需要非默认试玩起点，作者明确选择并预览该初始状态。接收者获得新的世界身份与独立进度，双方游玩结果不自动合并。

“让朋友游玩”与“把可编辑创作交给朋友”分别说明，所需包格式、资源依赖、来源与分发范围沿用 CP 和许可方案。自动保存、创建候选与本地导出不会自动上传或替玩家发送给他人。未来网站发布再选择可见范围与实际发布内容。

反馈沿用第 7 节的记录与附件规则，绑定朋友实际玩的 `BuildRef`。作者已经升级作品时，旧反馈仍保留原版本；系统在隔离环境复现或说明版本差异，不悄悄把当前世界降级。首版提供本地反馈包的导出、导入和状态更新即可，后续社区只是增加传输与协作入口。

传播功能先做好“朋友真的能打开”和“作者真的能修复”。自动生成介绍文字可以基于实际功能；预览图来自真实作品，未经验证的玩法不能写成已完成卖点。点赞排行、关注系统和素材交易不进入首批范围。

## 11. 与现有工程计划的衔接

本计划负责玩家操作、反馈和交付体验。内容、资源、任务与进度仍各有既定权威来源，避免再造一套隐藏在界面中的版本和保存逻辑。

| 事项 | 复用的权威契约 | 本计划负责的部分 |
| --- | --- | --- |
| 修改与采用 | VM 的 `ContentRef`、`BuildRef`、`ProgressRef`、`OperationContext` 与应用事务 | 目标、范围、试用、采用、取消及结果解释 |
| 素材与模块 | AL 的资源查询，CP 的七类内容、固定依赖和导出用途 | 推荐少量已验证内容，展示适用参数与安装效果 |
| AI 执行 | AI 计划的任务、预算、指导资料、模型策略和真实用量 | 起步建议、需求上下文、失败恢复与问题修复入口 |
| 运行与状态 | 现有 Godot 运行协议及后续适配 | 依据当前目标展示能力；不依赖先完成原生中央嵌入 |
| 试玩分发 | CP 打包与 CC 发布任务 | 本地试玩路径、反馈入口，后续接入社区 |

参数编辑与 AI 修改绑定同一作品基线；并发变更通过既有前置版本检查拒绝过期写入，保留草稿后让玩家比较或重新生成。响应不确定时查询原 `operationId`，不能通过多点几次制造多个应用。

采用候选时仍需冻结必要事件、捕获最新正式进度、在隔离副本迁移，并完成 VM 定义的持久化与恢复流程。正式应用失败保留可恢复的旧状态，成功后才报告已采用。问题记录与预览状态不能成为覆盖正式存档的捷径。

新增的参数元数据、问题记录与产品事件属于待冻结设计：分别由内容契约、运行诊断与客户端统计的负责模块确认格式和迁移方案。本文件中的字段要求不是已经实现的 API。涉及备份的新表、资源与附件路径须登记完整；个人诊断数据是否纳入私有备份由备份选项明确决定，公开作品包保持独立。

## 12. 如何判断功能值得继续投入

主指标采用“完成有效创作并再次进入该作品的创作者数”，同时报告每位有效创作者完成的修改数。这里的“有效创作”至少包含真实候选、必要检查通过、成功采用以及对应互动或结果证据；仅收到模型文本、生成文件或看到完成按钮不算。

再次进入是持续使用的早期信号，不能替代满意度。暂未再次打开的作品标为观察未完成；主动放弃尝试与运行失败分开统计。需要补充简短的玩家访谈，理解“没再打开”的具体原因。

| 指标 | 建议定义 | 用来判断什么 |
| --- | --- | --- |
| 首次互动成功 | 从创建首个世界到采用创作并触发预期互动；同时列出成功人数、总人数与未完成原因 | 新玩家是否知道如何开始，系统是否真的做成 |
| 首次有效修改耗时 | 从提交或开始调整到成功采用；区分系统等待、试用和玩家暂停 | 参数面板及指导是否缩短完成任务的时间 |
| 保存重开成功 | 具备重开观察的作品中，内容与关键进度都正确的数量 | 创作成果是否可信 |
| 后续继续创作 | 首次成功后再次进入，并产生新的有效修改 | 玩家是否愿意持续完善自己的作品 |
| 采用与撤回 | 候选的试用、采用、取消、版本恢复及原因 | 修改是否符合意图；撤回不自动等同质量失败 |
| 修复效率 | 有现场的问题中，复现、提供候选、成功采用与玩家复测的数量和耗时 | 记录现场是否减少反复沟通与返工 |
| 有效创作成本 | 复用 AI 计划的实际用量，计入失败与重试，再按成功结果统计 | 提速是否同时降低实际成本 |
| 好友试玩完成 | 成功导入启动、发生互动、返回有效反馈的人次 | 分享链路和操作说明是否有用 |

事件按本地用户配置、会话、世界、操作与构建关联，记录阶段、结果、时间和可选原因。计数按稳定事件身份去重；一次拖动的一百个预览值、自动保存与网络重试都不能计作一百次创作成功。默认事件不包含原始聊天、截图、完整存档或系统输入。

首版先做本地统计和可由玩家主动导出的汇总。远程分析另外提供明确开关与内容说明；现场附件分享和统计授权不能相互替代。成本继续读取既有用量记录，不再建立第二套可能重复计费的统计账本；没有实际价格或用量时标为未知。

次日、七日回访等指标在 PP0 固定观察窗口、时区和分母，仅使用已经到达观察期限且数据可用的样本。离线数据未回收、删除记录和观察未满分别处理，不把未知当作流失。小样本优先展示人数与个案，再给比率，不声称已经得到稳定留存结论。

## 13. 分阶段开发与交付门槛

阶段编号 PP0–PP7 只用于本计划，不替代 GD、VM、AL、CP、CC、AI、NR 的阶段。按实际依赖与试玩结果排期，本次不承诺日期或自动分派任务。

| 阶段 | 交付内容 | 主要依赖与责任 | 完成门槛 |
| --- | --- | --- | --- |
| PP0：确定首个可用体验 | 核实安装包与源代码能力、选定一个底座和示范故事、记录基线与指标口径 | 客户端、核心、底座、验证共同确认；消费当前 Godot 创建与状态修复 | 同一实际构建跑通创建、基本互动、采用、保存重开与恢复；缺项明确列出 |
| PP1：帮助玩家开始 | 可跳过引导、目标与范围提示、真实阶段和恢复入口 | 客户端与创作编排，复用当前候选流程；PP0 | 新玩家能完成指定故事，退出可继续，提示能力与真实接口一致 |
| PP2：常用参数调整 | 小量参数契约、调整面板、隔离预览、一次采用与持久化 | 客户端、底座/模块、CP 配置契约、VM 应用路径；PP0–PP1 | 支持的参数无需额外模型调用，取消不改正式世界，采用重开不丢值和进度 |
| PP3：记录问题并修好 | 本地现场记录、诊断入口、修复候选与复测状态 | 运行诊断、AI 编排、客户端；PP0 的构建与状态身份可用 | 一个真实可复现问题从记录到修复采用闭环，原始现场可查，旧玩法仍通过 |
| PP4：持续玩法保护 | 作品业务规则、变更影响说明、有限场景的健康检查 | 独立验证、内容契约、客户端；PP2–PP3，并延伸既有基础检查 | 后续修改会发现预设旧玩法回归；规则有版本，未知不显示通过 |
| PP5：提高作品完成度 | 暂停、声音、操作说明和一种互动反馈，有限可读性设置 | AL/CP 模块安装、底座输入与状态契约；PP4 的回归案例可复用 | 在新世界与已有世界安装后均可用，无输入冲突，设置重开仍正确 |
| PP6：好友试玩闭环 | 本地试玩包、运行要求、初始状态、反馈包与修复回传 | CP 的所选打包路径、PP3 问题记录；不要求完整社区或 NR 全部完成 | 另一套干净环境成功游玩，双方进度独立，反馈准确指向所玩版本 |
| PP7：依据使用结果扩展 | 选择数值试验、风格、语言支持、更多模块或社区入口中的高收益项 | 前阶段真实使用数据及所选能力依赖 | 有明确受益人群、基线、成本与验证结果，再决定扩大或停止 |

建议先以 PP0–PP3 形成首次玩家测试版本。基础验证与指标从 PP0 开始，不能等 PP4 或 PP7 才补。PP3 的现场设计可以与 PP2 的界面工作独立推进，最终在同一构建集成验收；本计划不据此自动启动并行任务。

PP6 最先验证兼容客户端中的本地试玩，不等待完整网站。独立 Windows 导出、浏览器托管各自满足 CP 与运行目标要求后追加，不将它们捆绑成首个分享版本的共同门槛。

## 14. 玩家试验与上线判断

建议邀请 6–10 位此前未参与开发、编程经验较少的玩家进行首轮定性试用，再安排愿意回来继续创作的人完成第二次任务。这是后续招募建议，尚未执行，也不构成统计显著性的保证。

每人完成“第一次创造、一次调整、保存重开、一次问题反馈”的固定任务，并留一个自主创作任务。记录卡住的位置、需要解释的术语、等待与返工、作品是否符合预期，以及是否愿意带朋友来玩；允许跳过或退出，保留其原始反馈。

对照应控制底座、设备、模型、模块与验收条件。比较“自然语言调整”和“参数调整”时使用同一可配置功能；比较起步建议时安排不同但难度相近的任务，避免第二次熟练程度被误认作产品收益。未支持的新玩法另列，不混入常用参数提速结果。

PP0 先测出现有耗时和失败类型，再冻结目标设备与验收阈值。第一轮可关注完成率、等待中位数与慢案例、重试次数、模型费用和需要人工解释的次数；小样本同时报告原始人数和范围，不预先宣称“人人五分钟完成游戏”或某个 ROI 倍数。

进入更大范围测试的门槛：规定案例没有已知进度损坏、错误完成提示、错对象覆盖或重复应用；主要流程能由新玩家独立完成；关键失败可恢复；实际交付与宣传相符。自动化通过之后还需要独立真人试玩，验证手感、可读性与引导是否清楚。

如果某功能没有明显收益，先收窄类型、调整入口或保留实验状态。数据与恢复问题优先修复；没有证据说明值得做的大功能，不因“已经列入计划”而继续扩大投入。

## 15. 验收案例

下列 26 项是后续开发验收清单，尚未执行。每项结果须记录版本、运行目标、数据来源、通过/失败/未覆盖及证据位置。夹具、真实核心、真实运行实例和真人试玩分别标注，不能相互替代。

| 编号 | 场景 | 必须满足的结果 |
| --- | --- | --- |
| PP-A01 | 首次进入与跳过引导 | 空白世界保留，建议与实际能力一致，跳过后所有正常入口可用 |
| PP-A02 | 创建首个互动对象 | 实际生成、检查、采用并发生预期互动；只有文本或占位显示不算完成 |
| PP-A03 | 同名对象及中途切换目标 | 修改绑定稳定对象身份，旧目标的迟到响应不影响新目标 |
| PP-A04 | 实例与共享模板修改 | 影响范围可见，实例修改不意外扩散到其他对象 |
| PP-A05 | 参数类型、单位、边界与旧契约 | 非法组合被说明并拒绝；含义准确；不支持的字段不猜测写入 |
| PP-A06 | 连续调整与构建合并 | 采用最新预览值，不逐帧创建历史或重复构建，不修改正式进度 |
| PP-A07 | 取消、切换世界及迟到完成 | 取消的候选不自动应用，不把其他世界的值显示为当前值 |
| PP-A08 | 采用参数并关闭重开 | 最终值持久化，一次采用对应一次操作；内容与实际运行一致 |
| PP-A09 | AI 与手动参数同时修改 | 过期基线被发现，草稿可保留，没有静默覆盖或重复应用 |
| PP-A10 | 进度变化与参数采用 | 使用最新正式进度；作品默认奖励、背包余额与个人设置互不混写 |
| PP-A11 | 普通参数的成本 | 无额外模型调用，实际构建与等待如实记录，不用假计时证明提速 |
| PP-A12 | 本地记录现场与附件选择 | 作品、构建、实例匹配；记录有上限，截图限游戏视图，默认不外发 |
| PP-A13 | 缺失快照或无法精确复现 | 标明缺失与重现范围，不把推测标为复现成功或已解决 |
| PP-A14 | 导入不可信反馈 | 描述与日志只作为数据，不引发额外权限、自动上传或宿主命令执行 |
| PP-A15 | 从真实问题到修复 | 修复绑定原问题，独立检查通过并成功采用，保留玩家复测状态 |
| PP-A16 | 玩家明确改变业务规则 | 规则与内容一起更新并说明状态影响，平台基础检查不被删除 |
| PP-A17 | 新修改破坏旧玩法 | 对应回归被发现；不删断言、跳场景或复用旧构建的通过记录 |
| PP-A18 | 基础可玩性检查 | 依据真实碰撞、行动与规则；传送不作为可达性证明，未知明确显示 |
| PP-A19 | 暂停、操作说明与模块组合 | 说明和真实行为一致，无输入、暂停与状态接口冲突 |
| PP-A20 | 音量、反馈强度与可读性 | 设置可调整并保存；需要时可关闭镜头晃动；中文和文本溢出有证据 |
| PP-A21 | 干净环境导入试玩包 | 依赖齐全或清楚列出缺项，创建独立世界与进度，无作者私人数据 |
| PP-A22 | 朋友反馈来自旧版本 | 保留实际版本，隔离复现或说明不匹配，不改写作者当前世界 |
| PP-A23 | 不同交付目标 | 客户端包、独立程序、浏览器链接按实际可用情况展示并各自验证 |
| PP-A24 | 指标去重与观察窗口 | 重试、预览和自动保存不放大成功数；未知成本、未满观察期单列 |
| PP-A25 | 记录、采用期间故障与重启 | 保存不完整有提示；应用按原操作恢复查询，旧内容和进度可恢复 |
| PP-A26 | 无输入自动验证与真人试玩 | 自动验证遵循项目不抢鼠标规则；真人体验结论有独立、实际证据 |

开发测试遵循 [AGENTS.md](../AGENTS.md)：浏览器验证使用独立 headless 进程与测试目录，在页面代码前禁用 `requestPointerLock`，通过 HTTP、页面脚本与纯逻辑验证；不发送真实鼠标/键盘，不激活或置前测试窗口，不操控用户正在使用的浏览器，也不使用 Playwright 的输入模拟验收。未经另行明确要求，不运行历史 `tests/browser.mjs`、`tests/modules-browser.mjs`。

自动化能验证状态、接线、语义动作和大量规则；不能把这些结果当作真人已经验证过第一人称操作与手感。视觉、操作舒适度与作品是否有趣的证据来自安排好的真实试玩。

## 16. 收益机会与暂不投入的方向

最先验证的经济收益来自每次有效创作成本降低、返工减少和玩家愿意继续创作。只有这些基础成立，才值得测试付费服务。潜在方向包括明确计量的 AI 用量、更丰富且经过验证的玩法模块、可选云备份与托管试玩；具体价格、需求和持续运营成本在有使用证据后另做方案。

参数基础调整、明确的任务状态、正常保存恢复和必要的玩法正确性属于产品可靠性要求，不以付费作为补救条件。导出与资源分发遵循已确认的许可和 CP 方案，本计划不改变许可证、作品权利或商业授权条款。

企业 CI、批量项目检查、任意外部 Godot 工程导入、多人实时共同编辑、交易市场、推荐算法、全引擎支持和完整客户端原生重写，不进入本计划首批范围。未来只有出现明确玩家需求与收益证据，才转交对应专项计划评估。

## 17. 下一次启动开发时的最小任务包

先执行 PP0：核实实际客户端可用能力，选定一个底座、一个互动对象和一条可保存重开的故事；把当前阻塞按核心、底座、界面、验证职责记录下来。随后围绕同一故事交付起步入口、少量参数调整和本地问题记录，避免一次覆盖所有底座与模块。

任务包应包含：可审阅的界面流程与中文文案、最小配置契约、状态与并发处理、必要的案例证据、实际包版本、仍未覆盖的范围，以及后续真人试玩脚本。有关实施的拆分与排期在启动时决定，本次交付物是计划书。
