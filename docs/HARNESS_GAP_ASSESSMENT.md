**从可用原型走向好用的游戏开发 Harness：缺口与优先级**

评估日期：2026-09-09；代码基线：`ebc55c9`。本文件是对当前实现的差距评估与后续顺序建议，不代表下述能力已经完成。已有 M1–M5 的证据继续有效，M5 的剩余验收仍需完成。

这里的 Harness 指 AI 开发游戏时使用的工作环境、工具、任务流程、记忆、验证和恢复机制。用户描述想要的效果后，它应能理解已有世界、分步开发、实际验证、根据失败修复，并保留作品和进度。

当前已经有真实模型生成、可执行源码、隔离运行、候选预览与应用事务、有限自动修复、模块版本、项目约定、本地素材、共享背包和持久任务。主要缺口是把外部开发者完成的工作，转为产品内 Agent 能独立完成的工具闭环。

**1. 已有能力和差距**

| 环节 | 当前实际实现 | 好用的 Harness 还需要什么 |
| --- | --- | --- |
| 自主开发 | 服务先组装场景、记忆与提示，模型返回完整场景；校验失败时最多追加两次修复 | 模型能按需查询现场、读取具体模块、拆分任务、修改局部、调用构建和试玩工具，再决定下一步 |
| 需求验收 | 产品自动运行固定事件序列；测试每份源码的接口和恢复。完整采木、制作、碰撞验收由外部测试脚本组织 | 把真实游戏操作与断言接入产品。验证掉落、扣料、可通行、重复奖励、重启恢复和多模块组合，提供截图及状态证据 |
| 修改效率 | 每次输出完整场景，包含未修改对象和源码；目前真实小场景请求已达到约两万输入 token | 项目索引与按需读取，基于固定版本提交局部修改，避免每次重写整个世界 |
| 任务恢复 | 保留任务、尝试、错误和产物；服务中断后任务标为 interrupted | 持久的任务步骤与完成条件；恢复已通过的步骤，只继续未完成部分；取消和旧结果处理保持正确 |
| 记忆与组合 | 已应用内容自动进入版本库；主要按文字匹配检索；新能力有依赖声明 | 用途、接口、依赖、适用版本和验收证据共同检索；记录有版本范围的失败原因；处理物品身份、全局系统配置与模块组合冲突 |
| 新能力扩展 | 源码通过受限命令改变对象、玩家、背包和 HUD；可用系统与接口由宿主实现 | 明确的扩展接口、能力清单与依赖协商。能说明现有接口是否足以完成需求；新增宿主能力走隔离开发、验证及版本发布流程 |
| 进度兼容 | 同状态版本保留进度，不兼容的新状态版本会拒绝应用 | 在副本上执行可验证的状态迁移，失败保留旧存档；版本升级、回退和卸载恢复要有组合验收 |
| 用户交付 | 本机工作台、任务日志、预览及导入导出已有；新开发内容尚未交付到个人 Alpha 0.8 | 清晰的阶段与失败原因、当前实际模型信息和用量、项目管理、可靠启动更新，以及完整初始示例 |

源码依据：`app/agent.mjs`、`app/agent-model.mjs`、`app/agent-prompt.mjs`、`app/behavior-verify.mjs`、`app/memory.mjs`、`app/behavior-state.mjs`、`app/store.mjs`。当前传给模型的提示要求它不调用工具；模型侧 shell、插件和应用也被关闭。增加开发能力应先提供受约束的产品工具，不直接开放个人电脑操作权限。

**2. 最优先的三个切片**

H1：模型能使用产品内的开发工具。

提供查询场景与对象、检索及读取模块、读取能力说明、提交局部修改、构建候选、查看错误等工具。每个任务固定基准版本，修改写入独立工作区；通过检查后沿用现有候选应用事务。任务步骤、调用参数和结果有持久记录。第一批把工具保持在项目资源和已有游戏接口范围内。

验收：模型收到“修改这扇门的规则”，能够自行读取该门及依赖、只改相关源码，再构建候选；其他对象保持原样。中断后恢复已完成步骤，不重新生成全部世界。具体工具名称属于实现细节，接口尚未开发。

H2：把实际试玩和需求检查装进产品。

从现有 `tests/world-probe.mjs` 提炼生产可用的独立试玩执行器，支持有上限的移动位置、瞄准、攻击、互动、时间推进、保存与恢复。工具调用在独立 headless 进程和数据目录执行，只调用游戏逻辑，不发送真实键鼠输入、不请求 Pointer Lock，也不操控用户浏览器。校验器读取宿主实际库存、生命值、碰撞与持久状态，生成可追溯的断言及截图证据。

在修改前固定需求对应的验收条件。模型可以提议测试步骤，实际结果由宿主产生；修复时不能通过删除测试、降低条件或自报“通过”交付。图像检查辅助验证视觉效果，不能替代碰撞、扣料和状态测试。保留人工判断无法可靠自动验证的体验问题。

验收：模型自己发现“看起来开门但通道仍有碰撞”或“重新进入会重复发奖”，读到具体失败证据并修复。整个过程由产品完成，不需要外部开发者为这一次需求临时编写验收脚本。

H3：长任务与长期作品保持可靠。

把任务拆分与断点、按需上下文、版本化局部修改、可复用验收条件，以及模块进度迁移连接起来。世界版本、源码版本、测试结果和实际运行进度明确对应。记录各阶段耗时与模型用量，区分生成、验证、恢复和失败；保留次数与总资源上限，并在合理的步骤边界中断。

验收：在同一作品里连续修改多个互相关联的规则；一次失败、一次服务中断和一次模块升级都不会丢进度，也不会让其他规则悄悄失效。新能力扩展与完整 Windows 交付在此基础上继续推进。

**3. 与现有开发计划的关系**

建议把下一阶段的重心调整为 H1、H2，并继续使用已经由真实模型做出的采木与制作营地作验收场景。M5 剩余的战斗、奖励、跨项目迁移和 Alpha 0.9 交付继续保留，用它们验证产品内的闭环能力。

M1–M5 完成可以证明个人创作 Alpha 的示例和基础流程成立；“好用的 Harness”还要证明这套流程面对未预设需求能够独立重复完成。多人和社区继续放在单机开发流程稳定以后。

**4. 建议新增的好用性验收门槛**

- 用户在界面连续提出至少 10 轮预先记录的不同需求，覆盖新增、修改、复用、删除和报错修复；每轮结果有对应证据，不挑掉失败请求。
- 正常流程无需外部开发者为某一轮手工修改源码、测试脚本或存档。
- 至少跨两个独立项目，验证已有模块复用、依赖冲突处理和兼容进度恢复。
- 故意加入一份错误候选，并在一次长任务中断后恢复；旧世界完整，重复恢复不会重复执行已完成的扣料或奖励。
- 模型无法完成的需求有明确说明和保留的工作成果，不会以通过接口检查冒充需求完成。
- 用户看得懂当前阶段、实际完成内容、测试证据和需要自己决定的事项；启动和更新有可执行的验证流程。

这些是建议的目标，尚无证据支持把产品成熟度写成某个百分比。成功率、完成时长、修复次数和用量应通过实际需求集测量后报告。
