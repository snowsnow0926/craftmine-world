# craftmine world / 最中幻想：目标与持续开发路线

更新：2026-09-09。用户授权按产品目标循环开发，不需要每轮重新确认普通开发工作。

**最新工程顺序采用 [Harness 项目开发计划书](HARNESS_DEVELOPMENT_PLAN.md) 的 P0–P7。** 本文件保留 M1–M5 产品目标、既有证据和持续执行边界；M5 剩余战斗、奖励、作品迁移及个人交付继续保留。新计划目前仅完成研究与设计，从 P0/P1 的领域工具和门修改闭环开始，不把计划中的能力记为已实现。

## 产品目标

创作者进入可游玩的空白世界，用自然语言增加事物和规则。Agent 理解现场，查找已有成果；能复用时复用，需要新能力时编写真正的新玩法代码，实际检查和试玩验证后交付候选。创作者应用、体验、提出反馈，Agent 继续修改。成熟的对象、素材和玩法成为有来源、有版本、能在其他兼容世界使用的模块。长期支持多人进入世界和共同创造。

体验判据：**“我想要有树 → 树出现 → 让它能被砍并掉木头 → 背包出现木材 → 再把木材做成门 → 门能开关 → 换一个空白世界仍能复用这些成果。”** 不能把未开发的能力映射成外观假象，也不能把几个固定玩法选项当成最终平台。

## 第一阶段实施设计（M1）

- 新玩法是可审查的源码模块，模型只能提交源码和相关资源描述，不能直接改写工作台或执行任意系统命令。
- 定义运行接口：模块接收有限的世界/玩家快照、输入事件、参数和自己拥有的 JSON 状态；返回受校验的游戏命令。逻辑由源码决定，不给每种新需求再写一个关键词分支。
- 代码运行在独立 Worker 中；主线程保留渲染、碰撞、状态与命令校验。Worker 超时或异常时终止该模块，保住世界；不把 Node vm 当成安全沙箱，也不在工作台页面 eval 模型输出。
- 代码产物先进入独立后台检查，至少做语法/接口/命令范围/超时/状态序列化检查；构建成功与实际玩法验收分别记录。
- 完整候选仍按当前事务流程应用。为代码参数、模块状态与兼容版本扩展存档，不静默清空已有状态。
- 首个切片：实现通用 Worker 代码模块接口、命令校验和失控恢复，再接真实 LLM 输出、游戏输入与模块记忆。

## 每一轮开发循环

1. 读取本文件、`HARNESS_DEVELOPMENT_PLAN.md`、`DEVELOPMENT_STATUS.json` 和 Git 状态，核对实现与证据；不要重做已经完成的检查。
2. 选择当前里程碑里最靠前且未阻塞的一项，限定成一个可以实际验证的切片。
3. 实现并执行匹配的核心/后台测试；需要模型才能证明的能力做一次实际调用，失败必须记录，不假造成功。自动修复有次数与时间上限。
4. 通过后检查差异，记录代码提交、测试产物和下一个接点。用户反馈优先进入当前轮。
5. 立即继续下一项；任务结束后由同一任务的定期跟进从记录的断点继续。只有可试玩交付、重要失败或确实需要用户决定时通知，不反复发送无变化报告。

## 持续执行边界

仅在 `D:\Craftmine World` 中开发。使用已有本机工具与已登录模型，不购买服务或额度，不读取密钥正文，不上传作品到外部托管，不推送远程或发布公网。普通实现、局部重构、独立测试和本地提交已授权；遇到上述外部决策时先完成其余可做工作，再说明具体选项。实际执行仍受本机在线、Codex 可运行和账号额度影响。

不擅自覆盖用户改动、删除存档、丢弃用户候选，也不因持续开发而持续重启用户正在使用的服务。每个可试玩版本准备好后再安排本地更新，保留旧版和迁移备份。
