## 覆盖流程

1. 官方物化器生成空白 `creation-sandbox`，真实执行隔离导入、Web 导出和画面／状态检查，生成可采用候选。
2. 实际候选运行实例返回保存回执，首次建立正式世界。
3. 主进程从正式实例捕获目标，绑定项目、会话和轮次，保存此世界的自动采用授权。
4. 加入一棵树、门、两个标记及新生成的顺序开门 GDScript。生产执行器再次编译、导出、检查，终态回调触发主进程重新核验任务、候选、源码和授权后自动采用。
5. 采用保留已有背包 `kept-token=7`，增加新门和新机关的默认状态；正式运行实例的观察中可见新树。
6. 读取真实 Rust 已完成任务上下文，验证正常创作请求能降为只读收尾请求，以摘要预算预留、清空工具列表，保持写租约已释放。该检查不调用模型；预留随后按未发送取消结算。
7. 把规则声明的源码哈希改成错误值，真实引擎明确报告 `Authored rule source hash mismatch`，检查失败且候选被拒绝。不会触发自动采用，不改变已采用的正式世界。
8. 关闭并重启 Rust 后，确认正式构建和完整进度仍一致。

## 过程中修复的接线问题

实际主进程路由的 `godotCandidate.read` 只接受世界和候选 ID；移除多余的 `context` 参数后，自动采用才可通过该路由。服务测试已接入真实私有路由及字段校验，任务身份仍由携带上下文的检查任务与源码索引验证。

自动采用会结束原任务并释放租约。原有上下文刷新仍尝试登记请求，且下一次模型请求仍按写入用途验证，导致已成功采用后报错。现已改为读取已完成任务的真实事实、使用只读最终回复策略、移除全部工具并拒绝异常工具调用，同时处理采用与上下文刷新并发的情况。21 项运行时测试和 3 项主进程上下文测试覆盖此行为，完整 TypeScript 检查与 Electron 生产构建通过。
