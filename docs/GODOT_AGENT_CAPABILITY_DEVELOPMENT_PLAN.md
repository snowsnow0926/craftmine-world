## 1 目标与完成定义

### 1 1 如何定义充分利用

“完美利用”在本计划中指一个可以持续验证的目标：对产品声明支持的创作类别，Agent 能选择合适的引擎能力，以真实工程和运行证据完成需求，保留已有玩法与进度，并把成功实现沉淀为可复用能力。它不等于开放全部引擎 API，也不意味着任意自然语言愿望都能一次完成。

保留项目现有北极星：每周完成至少一个有效愿望并继续游玩的创作者数。有效愿望、实际游玩和重开正确性沿用 C／D／L 总体方案，不用自动探针冒充真人体验。[E01]

工程侧同时考察三类收益：可支持的任务范围扩大；同等要求下自主完成更可靠；达到同等质量的时间与成本下降。扩大范围与提升原有范围的效率分开统计。

### 1 2 七个必要环节

| 环节 | 要达到的行为 | 完成证据 |
| --- | --- | --- |
| 发现 | 正确知道当前工具、底座、执行器和目标平台能做什么 | 能力描述与真实调用一致，状态变化可更新 |
| 理解 | 读懂相关场景、脚本、资源、状态与依赖 | 查询结果绑定准确源码版本，未知部分显式返回 |
| 创作 | 选择配置、复用或普通工程开发路径 | 原子源码事务和受检查的实际变更 |
| 观察 | 获取当前实例或候选的状态与必要画面 | 世界、构建、实例、采样时刻和来源可追溯 |
| 验证 | 将需求转成可执行且不被生成者篡改的检查 | 行为轨迹、断言、保存重开与必要视觉证据 |
| 修复 | 根据实际失败定位并在预算内纠正 | 新旧失败证据、修复范围与回归结果对应 |
| 积累 | 成功内容能够被下次需求准确复用 | 固定版本模块、依赖、指导和独立实例验收 |

其中任何一环缺失，都要说明该能力的适用边界。例如，能导出工程而没有玩法检查，只能证明构建能力；具有截图而没有视觉判断，不能声称已完成美术验收。

### 1 3 与没有内置 Godot 的比较口径

与旧自定义运行系统相比，Godot 提供更多现成的场景、物理、动画和资源机制，减少平台逐项实现底层功能的负担。与已正确安装并接好工具的外部 Godot 相比，引擎上限可能相同；内置方案的优势需要体现在环境一致、工程身份、连续创作、运行反馈、存档保护和恢复成本上。[E02、E20]

后续评测首先比较当前内置方案与增强后的内置方案。外部 Godot 对照属于可选实验，必须给予相同版本、资源、模型、预算和可执行条件，不把“缺少环境配置”人为设成对照组的必然失败。

### 2 1 已有能力及其证据范围

| 资源与复用 | 资产、组件包和内容历史已有工具绑定与后端入口 | 各模式实际权限、结果和客户端接线需继续核实 [E11] |

前序分析执行了 53 项能力、查询、观察、文档与服务契约单元测试，全部通过。这些测试含纯逻辑与替身环境，不是此次新功能的完成证明，也不是当前安装包或真实模型的全面验收。

### 2 2 优先修复的具体问题

`godot-routing.cjs` 仍将 `godot_history`、`asset_library`、`package_library` 固定描述为不可达；实际工具分支及 Rust 分发器已存在对应入口。能力报告与调用实现存在不一致，而 Agent 提示又要求优先相信能力报告。GU1 必须逐模式验证并修复描述生成机制，不能只把三个布尔值改为 true。[E03、E11、E12]

当前 `godot_project_query` 主要解析源码文本，不能完整解释继承场景、动态节点、运行时资源和复杂脚本语义。需要区分静态声明、真实导入结果与实际运行状态，避免把推测包装成工程事实。[E13]

通用检查缺少可组合的玩法场景、广泛状态断言和模型可消费的失败现场。底座专用检查应逐步接入共同框架，同时保留原有判定强度。[E08、E09]

当前 Godot 工具清单未呈现通用候选截图检查、语义试玩和性能诊断接口。宿主已有的截图和探针能力不能直接计作 Agent 已可自主使用的工具；GU0 要逐项建立完整调用链证据。

### 2 3 不能提前下结论的部分

暂时不能给出总体“潜力利用率”，也没有可泛化的真实模型首次成功率或任务提速倍率。历史报告明确保留真实模型与真人体验限制。[E06]

文档中的旧阻塞说明、源码当前状态和安装包状态可能不同。后续一律区分“源码已实现”“当前进程可用”“独立实例已验收”“真实模型已验收”“玩家体验已观察”五个层次。

## 3 范围与能力覆盖路线

首批以 Windows、固定 Godot 工具链、creation-sandbox 主世界为产品入口，沿用 GDScript、Compatibility 和 Web 主创作链。第一人称、俯视、横版、采矿底座保持原功能并按矩阵回归。已有 Windows 导出单独核验；不因导出可用就认为任意原生运行能力已经接入。[E04、E14]

| 能力领域 | Agent 应获得的可操作能力 | 优先级与首个验收 |
| --- | --- | --- |
| 场景与对象 | 理解实例、继承、变换、资源引用和稳定身份 | P0 树变大后外观与碰撞一致 |
| 物理与交互 | 通过真实控制器移动、碰撞、触发和射线交互 | P0 门关闭阻挡，打开可通行 |
| 玩法与状态 | 组合物品、任务、奖励和持久状态 | P0 奖励一次性且重启不重复 |
| 游戏 UI | 检查控件状态、布局、遮挡和世界 UI 联动 | P1 商店库存与背包结果一致 |
| 动画 | 查询与配置动画、状态转换及事件连接 | P1 开门动画与碰撞释放同步 |
| 导航与角色 | 理解导航资源并验证可达性和追随行为 | P1 同伴绕障碍且不穿墙 |
| 模型材质纹理 | 导入、绑定、单位检查、碰撞与视觉预览 | P1 固定资源完整加载且比例正确 |
| 声音 | 绑定音效、播放状态、音量与目标平台能力 | P2 交互音只触发一次，静音策略有效 |
| 光照粒子 Shader | 查询目标兼容性，构建并查看候选效果 | P2 无缺失材质和遮挡主要目标的问题 |
| 性能与规模 | 取得真实采样并提出保持语义的优化 | P1 同场景对象规模实验与回归 |
| 包与版本 | 检索、配置、安装建议、迁移和复用反馈 | P1 第二世界独立身份与初始进度 |
| 原生扩展与其他平台 | 明确缺口、收益和接入成本 | 后续专项，以需求和实测决策 |

P0 为第一批必须项；P1 为完整增强版目标；P2 为在基础完成后逐项扩展的能力。分类代表实施优先级，不代表已经完成。第一版不承诺所有底座拥有完全相同的新增探针，也不承诺任意外部工程导入、C#、GDExtension、编辑器插件、联网多人或完整原生编辑器控制。

Godot Web 的渲染路径和运行限制由目标平台决定。官方 stable 文档只用于机制参考，生产知识库必须对应本项目固定版本；不能凭未来文档或原生 API 存在就升级产品能力声明。[E21]

## 4 目标架构与端到端流程

### 4 1 沿用现有分层

Agent 负责理解需求、检索、选择实现路径、提出源码修改和处理反馈。插件工具层提供受限操作、结构化查询和清晰错误。Rust 核心继续拥有世界身份、源码、版本、进度、作业、预算和事务。宿主执行器负责引擎启动、隔离检查、证据采集和采用协调。Godot 运行时提供实际游戏行为与受限观察。[E03、E04、E05]

在这些已有层中增加能力注册描述、工程语义索引、候选诊断与试玩接口，复用现有作业和证据存储。避免另建一套与当前任务、版本或预算不一致的“Godot Agent 服务”。

正式世界采样以只读为主；可能改变游戏状态的试玩在候选或复制实例中执行。检查实例不拥有正式应用和正式存档写入权限。玩家预览或已有明确自动采用策略仍通过宿主流程处理，新增工具不能自行扩大同意范围。

### 4 2 一次创作的目标流程

1. 固定原始需求、目标对象、当前世界与预算；沿用 C／D／L 记录结果类别、预计难度与修改层次。
2. 查询实时能力，检索准确版本的工程、文档和可复用组件，确定剩余工作。
3. 形成需求验收草案，标明可自动验证、需要视觉判断、需要玩家体验和暂不可验证的条目。
4. 宿主保存验收版本。对明确需求自动形成检查，对关键语义歧义才询问玩家，普通步骤不重复确认。
5. Agent 原子修改源码或使用配置、复用操作，取得准确回执。
6. 先进行便宜的语法与导入检查；完整候选仍经过真实构建、运行与必要迁移检查。
7. 在独立实例执行需求场景，采集状态、轨迹、必要画面与错误。
8. 若失败，按类别在预算内修复；若通过，按既有策略进入预览或采用。
9. 验证采用后的实际版本和兼容进度；记录完成、未覆盖项及后续复用候选。

### 4 3 贯穿开发的代表故事

玩家要求“在这里放一扇门，先取得钥匙才能打开，门后宝箱只能领取一次；以后可以换门的外观而不丢掉已领取记录”。目标来自当前宿主捕获。Agent 读取对象与存档契约，选择已有组件或编写普通脚本，再生成候选。

独立试玩依次验证无钥匙打不开、取得钥匙后能开、碰撞实际消失、领取一次、再次领取无收益、保存重开结果一致。随后换外观并采用，原门和宝箱的稳定身份以及奖励账本保持正确。失败时提供实际事件、背包变化和世界版本；不能通过修改测试预期或直接设置“已通过”变量完成。

第二条故事为同伴绕障碍跟随，覆盖导航与动画；第三条为商店，覆盖 UI、交易和持久状态。这两条在相关能力接入后进入 P1，不提前列作已支持。

## 5 GU1 能力发现与调用一致性

### 5 1 单一事实来源

从实际工具注册、RPC 分发与宿主提供者构造能力描述，按工具和 mode 分别记录。一个工具可能支持读取而不支持某种提案执行，不能用一个总开关覆盖全部行为。

能力状态建议拆成：工具已注册、后端方法存在、权限允许、执行器可用、平台支持、输入契约匹配和最近健康检查。未知保持 unknown；临时离线与永久不支持分别返回。宿主专用 prepare、commit、作业租约等接口标为 host-only，不能误记成 Agent 功能缺失，也不因此直接向模型开放。

每份能力描述绑定插件版本、核心协议、底座与引擎版本、平台、工具契约哈希、注册代次和观测时刻。启动、执行器重启、插件重载、世界切换和模式变化触发失效；模型切换与上下文压缩后恢复最新简要事实。

### 5 2 开发任务与出口

- GU1.1 审计所有当前 Godot 工具及其模式，列出注册、路由、权限和真实结果；重点修正历史、资产和组件包描述。
- GU1.2 用实际注册生成静态描述，运行状态叠加为独立健康层；增加契约漂移检查。
- GU1.3 改善错误提示，返回失败环节、可重试条件和下一步；玩家侧使用可理解文案。
- GU1.4 使提示、ToolSearch 与能力报告读取同一描述版本，避免旧提示压过当前事实。

验收必须同时覆盖可用、未注册、无权限、执行器离线、平台不支持和模式局部可用。对三项已发现的不一致，分别运行真实只读方法；写入相关流程在独立世界验收。修复测试应检出真实漂移，不能只是断言新常量为 true。

## 6 GU2 引擎知识与工程语义

### 6 1 固定版本的知识支持

保留现有 16 条摘要作为入门入口，增加固定引擎版本的类、方法、属性、枚举、信号和典型用法索引。资料分为官方 API、底座接口、可执行示例与任务指导四类。每条保留版本、来源、哈希、目标兼容性及覆盖范围。[E10]

优先在打包阶段从对应官方资料或固定引擎可提供的元数据生成索引。ClassDB 等运行时信息作为补充，其能覆盖什么须由原型验证。文档生成与导入若可能执行项目代码，必须置于现有隔离边界，不能在宿主内加载不受信任工程。

新增语义查询可先采用关键词、类名、中文别名与依赖过滤，只有实测需要时再引入向量检索。避免将整个手册塞入每次模型上下文。返回结果支持分页、精确引用、缺口提示和缓存失效。

### 6 2 三类工程信息

| 信息层 | 内容 | 可信范围 |
| --- | --- | --- |
| 静态源码 | 文件、类、导出属性、信号声明、场景节点和引用 | 只证明对应源码声明，未解析结构要报告未知 |
| 引擎导入 | 真实解析、资源导入、依赖解析和结构诊断 | 证明固定构建的引擎处理结果，不能代替运行状态 |
| 运行实例 | 实际节点、实例属性、碰撞、交互和业务状态 | 只描述绑定实例的采样窗口，并标明来自项目数据 |

查询同时返回来源层、源码版本、覆盖文件、截断位置和无法解释的内容。稳定实体 ID 用于持久身份；节点路径只作定位线索，不能成为唯一存档键。动态创建、继承场景覆盖与共享资源要有独立用例。[E13]

### 6 3 开发任务与出口

- GU2.1 生成固定版本知识索引与兼容性元数据，并验证打包产物可离线检索。
- GU2.2 扩展工程查询，提供节点与资源依赖、导出属性、信号连接、输入动作和持久化字段的关联。
- GU2.3 在隔离导入后返回引擎诊断；建立增量缓存，以源码和资源锁为键。
- GU2.4 原型评估语言服务对符号定位与诊断的收益。仅在固定工具链、隔离和恢复均通过后接入；不得把 LSP 作为未验证的强制依赖。

出口包含继承场景、重复名称、断开的资源、动态节点、属性覆盖、旧版本资料拒绝以及分页读取。查询结果必须定位到真实来源；同一实体在源码和运行中不一致时明确呈现差异。

## 7 GU3 创作操作与增量执行

### 7 1 配置与源码路径共同保留

常见操作提供类型明确的参数，如变换、材质绑定、组件配置和连接已声明的行为。复杂玩法继续允许普通 GDScript 与场景开发，不能把平台重新限制为有限按钮集合。高层操作必须产生可查看的真实源码变更，并复用现有原子补丁事务。

`@export` 可提供类型和提示，但不是权限声明。可配置属性还需声明作用对象、允许范围、是否共享资源、状态迁移影响和适用底座；带 setter 的属性可能执行项目代码，也不能在宿主中直接调用。[E22]

每次操作绑定准确源码与对象身份，包含预期哈希、操作 ID 和必要状态版本。对名称相同的两个门、多人式并发任务、共享材质和过时目标不能猜测应用。当前公开 authoring 主要编辑 main 的事实需要保留；若引入任务分支，必须先由版本管理契约和宿主身份支持，不能直接让模型自由选择分支。[E15]

### 7 2 按影响选择检查

新增轻量语法、导入、依赖和参数检查，可在完整导出前提前发现错误；最终候选仍走现有正式验证。检查缓存同时包含源码、资源、宿主桥、引擎、检查器、冻结需求与必要进度版本，缺一项时不能复用通过结果。

同一任务内合并相关修改以减少反复导出；跨任务不得把不相干变更捆入同一候选。冷热缓存耗时分别记录。源码改动、构建完成、检查通过与正式采用继续保持独立状态。

### 7 3 开发任务与出口

- GU3.1 建立参数与对象操作描述，首批覆盖外观、变换和已验收组件配置。
- GU3.2 生成可检查的变更摘要、依赖影响与保存影响，保持底层源码接口可用。
- GU3.3 引入分级检查和准确缓存键，支持取消、丢回复查询和跨重启继续。

验收包括重复请求不重复建物、哈希冲突不写入、共享材质影响范围正确、源码失败不影响正式世界、缓存对每种身份变化正确失效。性能优化不能跳过必须的应用与迁移判定。

## 8 GU4 独立运行观察与自动试玩

### 8 1 从读取状态扩展到可组合场景

继续使用现有实时观察信封，增加可分页实体、按需属性、碰撞和交互描述。新增字段带 schema 版本与底座支持声明；不能把不存在的字段填为空值假装已支持。[E07]

试玩采用受限动作词汇，例如沿方向行走、转向、交互、使用物品、等待物理步和读取结果。这些是拟新增或统一的产品协议，不是现有工具保证。各底座可声明支持的动作子集。

动作通过游戏控制器和实际交互系统执行。例如 walk 必须调用正式移动逻辑并经历碰撞，interact 必须通过同一目标判定和交互逻辑，不能直接给玩家传送、发钥匙或把门设为打开。用于准备初始条件的夹具操作单列 setup，不能冒充玩家已完成行为。

Godot 纯逻辑与物理场景可使用 `--headless`。需要真实像素的 Web 检查在独立无界面浏览器或已有 offscreen 宿主中运行，使用单独 profile 与数据目录。所有验证禁止真实鼠标键盘、Playwright mouse／keyboard／click／fill、请求 Pointer Lock、激活或置前窗口；页面脚本在初始化时禁用 `requestPointerLock`。[E16]

### 8 2 需求与断言协议

冻结需求记录原文哈希、准确版本、场景步骤、断言、阈值、必要保存重开和最大运行预算。Agent 可以提出验收草案，宿主校验支持范围并持久化；候选生成者不能在修复时改弱必需断言。

首批断言覆盖存在性、数量、位置容差、可见与碰撞、交互前置条件、库存变化、一次性奖励、有限时间内到达状态、保存重开和不相关进度保留。采用有界数据协议，不提供任意 shell、JavaScript eval、任意 GDScript 方法执行或自由表达式求值。

未知需求返回 unsupported 或 inconclusive，包含缺少的动作或观察能力。不同状态至少区分 passed、failed、blocked、cancelled、inconclusive 和 not-run。没有执行、证据过期或缺少观察时不得合并成通过。

### 8 3 证据来源与独立性

每份结果绑定 task、job、world、source、build、instance、需求哈希、检查器版本和采样窗口。宿主记录动作顺序、真实运行错误、截图摘要和操作回执；游戏返回的业务状态仍是项目数据，不能因为附有宿主时间戳就当作完全可信。

检查者应尽量通过实际动作后果、宿主保存回执、碰撞与画面等不同证据交叉验证。持久化奖励尤其要比较运行变化与核心账本。这个机制提升可检测性，但不承诺证明任意恶意或自报状态的脚本永远正确。

物理、导航、异步和随机过程不默认具备跨平台逐帧确定性。固定引擎、种子和物理步，断言使用明确容差与有界最终条件；必要时重复独立实例。不得靠失败后无上限重跑挑选成功轨迹。

### 8 4 画面与现场

在具备图像输入能力的模型上，提供任务相关候选截图、视口信息和前后对比。图像来自该候选实例，保留哈希、相机和采样时刻；截图不得控制玩家当前相机。

像素检查判断空白或异常画面；视觉模型辅助发现比例、遮挡、布局与风格问题；主观美感和手感仍由玩家评价。纯文本模型可以读取结构化结果，但不能宣称做过视觉判断。音频触发可自动检查，声音质量与物理扬声器表现保留独立验收。

开发子项 GU4.1 为观察契约，GU4.2 为动作适配，GU4.3 为需求编译与独立执行，GU4.4 为截图和失败现场，GU4.5 为跨重启与故障回归。首个出口是第 4.3 节钥匙门故事，随后扩展跟随与商店场景。

## 9 GU5 基于证据的修复与任务策略

### 9 1 诊断和恢复

统一诊断包含阶段、错误码、文件与行号、相关实体、源码版本、实际观察、预期结果、可重试条件及最小复现步骤。解析错误、缺资源、玩法错误、状态迁移、平台不支持、预算不足和环境故障分别处理。

Agent 先阅读失败及受影响依赖，提出可验证的原因，再进行最小连贯修改。每轮保留原因、变更、实际检查和剩余项。没有新证据的相同错误禁止原样循环；已成功的写入通过回执恢复，不能重放成另一笔操作。

建议初始策略为同一失败原因最多两轮有证据的修复，仍未解决则重新诊断或进入当前允许范围内的更强推理路径。最终次数、时间与费用由 GU0 基线和现有预算机制冻结；不能通过换模型或恢复任务重置总消耗。

### 9 2 路径与模型选择

沿用现有 AI 效率计划：先检查可复用条件，再估计剩余难度，选择配置、组件复用、局部脚本或子系统开发。用户固定的模型、禁止云端和费用约束持续有效。[E17]

首轮实验证明工具和验证增益时固定模型及思考参数。跨模型路由、本地 4B 和社区复用收益分别做对照，不能同时更改模型、工具、资料和检查器后把所有提升归给内置 Godot。

上下文压缩后恢复需求、准确源码头、已读记录、操作回执、候选状态、失败原因和剩余预算。恢复事实来自现有持久记录，不仅依赖模型写的摘要。[E12]

### 9 3 修复完成标准

每个已修复缺陷必须保留原始失败复现和同一标准下的通过结果。必要时增加防回归场景，且覆盖真实行为。禁止删除功能、取消持久化、放宽阈值或跳过检查以获得通过；范围调整必须显式记录并重新建立需求版本。

GU5.1 交付诊断模型与反馈工具；GU5.2 交付有限修复状态机；GU5.3 交付上下文恢复与路径选择；GU5.4 交付错误注入和真实模型修复评测。

## 10 GU6 资源复用与性能优化

### 10 1 把成功实现变成可复用资产

资产查询返回精确版本、来源、授权记录、依赖、预览与适用底座。模型、纹理、音效和组件应通过既有资产与创作包流程传输、导入和验证，避免要求模型直接生成大块 Base64 来搬运正常资源。

新增场景或机制完成后，可以形成模块候选，声明稳定身份、参数、依赖、状态格式、初始状态、升级与移除行为以及验证场景。整理成可复用包不自动授权公开发布或批量升级世界。

Agent 优先查找、读取并评估兼容包，必要时适配；检索结果存在不等于安装成功。第二世界复用必须产生独立实例和规定初始状态，不能继承原作者背包、奖励或任务进度。沿用 VM、AL、CP 的历史和事务，不新建重复注册表。[E11、E18]

### 10 2 性能数据进入修复循环

通过固定探针收集目标平台实际可取得的帧时间、物理处理时间、对象数量、内存和渲染统计；Godot Performance 提供一部分监测能力，但不同运行目标和发布构建的可用字段要逐项验证，不能把不可取得的 GPU 数据填成零。[E23、E24]

性能实验固定设备、分辨率、场景版本、对象规模、存档、引擎和后台负载。建议先预热 10 秒，再采样 60 秒，每场景独立运行三次，最后根据 GU0 实测调整并冻结。软件渲染用于回归，不据此承诺真实 GPU 帧率。

Agent 可以提出节点复用、减少每帧脚本、MultiMesh、资源共享、碰撞简化和可见范围管理等优化候选；每种方案先确认目标支持并保留交互、存档和画面标准。不得通过删除对象、降低已约定质量或停止模拟来制造提速。

GU6.1 交付资源与模块消费链验收；GU6.2 交付性能采样与报告；GU6.3 交付一项真实规模优化和功能回归；GU6.4 交付固定版本的可复用示例与指导。

## 11 兼容性与信任边界

继续以核心持久记录决定正式内容和进度。引擎日志、生成脚本、文档、截图和自报状态均不能授权应用、改变任务身份或扩大宿主权限。新增诊断和试玩不绕过现有执行器、资源校验与工作区边界。

公开协议版本、工具 schema、底座能力和检查器均需协商。旧世界未声明新增观察字段时返回缺口；旧候选沿用其原有检查证据范围，不追溯性标记为拥有新检查。需要重新检查时创建新作业并保留旧记录。

进度迁移从最新确认状态出发，保留旧快照并验证新字段默认值。源内容回退、组件回退和恢复玩家存档是不同操作；不能为了回滚某项内容而自动重置玩家进度。

测试数据、截图和轨迹复用当前配额与回收机制。建议首版每次试玩最多 12 张截图、10 MB 结构化轨迹、120 秒执行时间；长任务使用明确扩展预算。GUI、后台任务和引擎并发共享资源上限，采用按任务和世界限流及取消传播。上述数值为 GU0 待校准的候选上限，不是当前实现事实。

公开内容、账号与服务设置、云端模型使用、批量升级和发布继续遵循既有用户授权；普通已授权创作、检查和修复不额外增加重复确认。新协议必须有路径越界、身份错配、失效租约、过期证据、取消后迟到结果和不受信任文本测试。

## 12 玩家体验与开发者可观察性

玩家主要看到正在处理的目标、可理解的阶段、候选结果、变化范围和必要的失败原因。工程哈希、内部 RPC、令牌和检查器实现保留在诊断详情，不进入常用创作流程。

默认阶段可表示为理解需求、准备内容、构建、检查玩法、完成采用。进度来自真实任务状态，不用固定百分比模拟。取消应快速停止后续执行并保留可恢复草稿；恢复说明已有成果与未完成步骤，不重复制造同一对象。

检查报告分开显示功能通过、未覆盖条目、视觉辅助判断和待玩家体验。若某项需求尚不能自动验证，候选可以在既有允许流程中预览，但不得显示“所有要求已确认”。失败现场支持绑定世界、构建、目标和存档；不影响玩家当前窗口和镜头。

开发者诊断统一记录 capabilityVersion、strategyVersion、model、sourceRef、assetLock、requirementsHash、job、instance、阶段时间、预算与结果。原始用量未知时保留未知。正常产品流程复用任务事实与用量账本，外部导出仅用于分析，不形成第二套状态真相。

### 13 2 分批交付

第一批交付 GU0、GU1、GU2 最小索引及 GU4 最小观察原型，解决“知道有哪些能力、找对相关文件和状态”。出口是能力误报修复与可复现查询，不提前宣传自动试玩已完整支持。

第二批交付 GU3、GU4 钥匙门故事和 GU5 基础诊断，形成主世界中一次完整的创作、检查、修复与保存闭环。这是首个玩家可感知的能力增强版本。

第三批扩展同伴与商店、动画和 UI 检查，完成 GU6 资源复用与性能原型。每次只扩大已经有动作与断言覆盖的范围。

第四批执行 GU7 的冻结模型任务、兼容回归和交付，形成可说明适用范围的增强版本。P2 的声音、复杂 Shader、光照与更多底座继续按独立能力项接入，不通过改变本版范围来隐藏尚未完成的 P0／P1。

## 14 开发分工与实施纪律

### 14 1 Codex 子 Agent 协作

后续并行开发使用 Codex 子 Agent，不通过 PI 派发开发子 Agent。总控负责合同、依赖顺序、集成和验收。产品内部仍使用现有 Agent 运行器，这与开发团队的派发方式是不同事项。[E16]

建议最多同时使用总控与三个子 Agent。接口设计和所有权先冻结，再分派可独立交付的任务。共享源码目录、同一 HEAD 或相同核心协议文件不得同时修改。每个开发子 Agent 使用独立 `codex/` 分支与 worktree，总控按依赖顺序合并。

| 角色 | 主责 | 交付边界 |
| --- | --- | --- |
| 总控 | 基线、契约、任务拆分、核心集成、最终验收 | 统一变更顺序和机器状态，不用子报告替代集成 |
| 核心与宿主 | 注册、任务与权限、作业、证据、恢复 | Rust 和 Electron 主进程接口 |
| Godot 与底座 | 观察、控制器动作、持久化和性能探针 | 真实工程与底座协议，保持旧行为 |
| Agent 与工具 | 查询、知识、schema、诊断与策略 | 插件工具和运行器上下文 |
| 质量与产品 | 场景、对照、UI 验证、玩家观察 | 可轮换角色；冻结判定与原始证据独立维护 |

角色是职责划分，不代表需要五个同时在线的人员或 Agent。实际并发按当前资源和任务独立性调整。

### 14 2 单任务交接模板

每项任务必须带有目标行为、当前基线、所属工作包、允许修改的文件范围、依赖版本、接口草案、非目标、验收命令、必须保留的行为和回执格式。交付报告说明完成项、未完成项、提交、检查结果及证据路径。

接口变更进入相应 spec，架构与信任边界变化增加 ADR；涉及玩家或协议行为的变更更新相关 E2E 方案。测试启动遵守适用 AGENTS.md 和明确授权，不把本计划视作已执行 E2E 或付费模型试验的证明。

后续仓库编辑遵守文件所在目录的指令。合并仅包含本任务变更，不覆盖已有未提交用户文档，不修改其他工作树，不因完成计划书就自动发布远端或替换正在使用的安装。

## 16 评测设计与验收矩阵

### 16 1 四层证据分别记录

第一层为纯函数和协议测试，证明解析、参数和状态转换。第二层为真实 Godot、核心 RPC 与宿主集成，证明代码实际进入执行链。第三层为真实模型任务，证明模型能选择工具并交付。第四层为玩家体验，证明结果可理解、可玩和愿意继续创作。

替身、夹具、预制候选和预写工具轨迹只能证明相应基础，不能混入真实模型自主完成率。自动动作也不能计作真人游玩。每条记录同时保留通过、失败、跳过和未覆盖；skip 不等于 passed。

### 16 3 真实模型对照

首先用四项任务各运行一次当前路径与增强路径，共八次任务运行，验证评测管线；不据此得出普遍成功率。正式探索建议使用 12 个预先冻结任务、两组、每项三次，共 72 次任务运行。每个任务可能发出多次模型请求，预算按真实请求累计。

其中八个任务覆盖本次开发领域，四个使用未参与调参的新措辞、布局或组合方式。最终保留题在策略冻结后才运行。题目、断言和资源由宿主评测清单固定，不能让被评模型自己重写通过标准。

两组固定模型版本、思考参数、目标设备、工程、资源、存档和预算，随机交错运行；使用干净世界并隔离记忆与缓存，冷热分别报告。先比较整条增强路径，再用消融实验区分知识、查询、试玩和诊断的各自收益。任务不支持、环境失败、超时和人工补代码都保留在完整产品任务分母中。

真实模型调用及费用按实际授权与额度执行，本文不启动这些调用。所需模型或设备不可用时，报告阻塞的具体评测层，不用夹具补成真实模型结果。

### 16 4 指标与候选门槛

| 指标 | 计算口径 | 首轮候选目标 |
| --- | --- | --- |
| 能力真实性 | 每个声明模式与对应实测结果的一致性 | 冻结必测矩阵无误报，无未知被当作可用 |
| 需求覆盖 | 自动判定、人工待评、未支持条目分别计数 | 所有需求有去向，必需条目无静默遗漏 |
| 预算内自主完成 | 无人工改代码且在预算内完成冻结需求 | ≥85%，分任务类别与原始计数报告 |
| 首候选成功 | 第一个实际候选即通过冻结标准 | 相对基线提升，具体幅度在 GU0 冻结 |
| 到正式可玩时间 | 接收需求至应用与实例就绪的完整时间 | 成功配对样本中位数改善 ≥20% |
| 每成功任务成本 | 组内全部费用含失败成本除以成功数 | 在质量不下降时争取改善 ≥15% |
| 状态与身份底线 | 错世界写入、丢进度、重复奖励、虚构通过 | 冻结故障矩阵零事件 |
| 性能 | 同设备场景的帧时间、负载和内存分布 | 不越过 GU0 冻结预算，优化项证明实际收益 |

这些数字是待 GU0 校准与冻结的发布候选，不是当前已达到结果，也不是必须降低质量才能追求的承诺。冻结后不能根据最终结果追调门槛；若样本不足或结果波动，只能标为探索性结论并扩充验证。

发布至少要求所有必须功能、状态和恢复检查通过，预算内自主完成达到冻结质量门槛，并在耗时或成本中至少一项达到冻结改善目标，其他项没有超出预先约定的退化范围。新任务范围与原有可配对范围分开报告。只在两组均成功的配对样本比较耗时，同时必须展示全体失败率和超时；不得删除慢案例。

对重复题的三次运行按任务聚类分析，报告每题结果、样本数和不确定范围；小样本不发布精确 P95 或“所有愿望成功率”。失败环境可另做诊断分层，但不得在看结果后从主分母中排除。成功数为零时每成功任务成本记为不可定义。

## 17 交付物与发布检查

每个工作包交付实现、相关 spec／ADR、必要验证、原始日志、结果清单与限制。建议计划状态使用一个现有机器状态体系中的 GU 命名空间，记录 planned、in-progress、blocked、verified、delivered；不要因写了文档就把工程项标为 verified。

最终材料至少包含以下内容：

- 模式级能力清单，以及源码、协议、工具链和安装包版本清单。
- 固定引擎知识索引、底座契约、场景动作描述与可运行示例。
- 新增工具的结构化 schema、错误码、分页、限额和恢复约定。
- 28 项验收的原始证据、范围、未覆盖项与同版本集成报告。
- 真实模型逐任务结果、费用与时间、人工介入及失败分类。
- 新旧世界迁移与回退方案、运行资源预算和分发资源校验。
- 玩家可理解的能力说明，准确区分已支持、预览可用与后续能力。

建议使用按能力启用的版本化配置逐批接入。关闭新策略时回到旧策略；关闭新增检查时必须降低相应能力声明，不能仍显示原范围已验收。已经产生的新状态格式如不可向旧版读取，应使用已保留的迁移方案与快照，不直接回退程序覆盖当前存档。

安装包验收必须针对实际打包产物，不能只在工作区通过后宣布玩家版本完成。远端发布、替换安装和社区公开依照后续明确执行范围操作，本计划本身只是开发与验收依据。

## 18 风险与后续决策

| 风险 | 具体影响 | 处理与判断点 |
| --- | --- | --- |
| 能力描述与实现再次分离 | Agent 放弃已有能力或调用不可用接口 | 从注册生成，GU1 加模式级契约和真实探测 |
| 动作适配绕过真实玩法 | 测试通过但玩家无法触发 | 同控制器与交互逻辑，setup 单独记录 |
| 项目自报状态失真 | 错误需求被判通过 | 交叉观察、宿主回执、独立断言，标明证明边界 |
| 非确定性引擎行为 | 同场景偶发失败或误判 | 固定环境、有界容差、独立重复，保留失败 |
| 模型工具与上下文膨胀 | 更慢、更贵且选择错误 | 按需检索、紧凑 schema、记录读取量与增量收益 |
| 缓存与恢复身份错误 | 旧结果通过新内容或重复写入 | 完整缓存键、原回执恢复、取消迟到拒绝 |
| 资源与截图挤占运行预算 | 玩家世界卡顿、磁盘增长 | 任务配额、队列、TTL 与现有回收机制 |
| 平台限制被当成推理问题 | 无限重试仍无法完成 | 能力矩阵说明目标限制，转入独立研发项 |
| 评测污染与选样偏差 | 分数上升但真实玩家无收益 | 冻结题、保留题、随机交错、全分母报告 |
| 同时扩展过多底座 | 主世界迟迟无法交付 | 主世界先形成完整故事，其他底座逐项声明 |

GUI 编辑器自动控制、完整语言服务、原生性能分析、GDExtension 与跨平台导出，只有在前述数据证明其能解决主要失败或性能瓶颈时进入后续专项。选择依据为真实受阻愿望、预计收益、实现与维护成本、验证能力和既有产品授权。

本阶段的首要开发决策是完成 GU0／GU1，并冻结 GU4 的最小动作和断言协议。具备这两项后，团队才能可靠判断后续投入应优先放在知识、工程理解、试玩覆盖、模型策略还是引擎目标扩展。

```json
    {"action": "interact", "entityId": "gate-01"},
    {"assert": "door-state", "entityId": "gate-01",
     "expected": "closed"},
    {"action": "walk", "direction": [0, 0, -1],
     "physicsSteps": 60},
    {"assert": "inventory-count", "itemId": "key",
     "expected": 1}
  ]
}
```

fixtureRef 指向已定义的钥匙位置和玩家初始状态；walk 是真实控制器动作，结果必须由实际拾取路径产生。动作无效、没有走到钥匙或观察能力缺失时，返回相应失败或未覆盖，不能补发钥匙。预算由宿主与现有总预算共同限制，模型不能提高宿主上限。

### A3 运行证据最小字段

证据至少记录 format、taskId、jobId、worldId、sourceRevision、manifestHash、assetLockHash、buildId、instanceId、requirementsHash、verifierVersion、startedAt、finishedAt、status、assertions、artifacts、diagnostics 和 usage。所有关键引用由宿主验证，工件包含哈希与保留策略；迟到结果不得复活已结束作业。
