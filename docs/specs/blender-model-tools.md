# Bundled Blender model tools and job lifecycle

The trusted Craftmine plugin owns four model tools: `blender_status`, `blender_generate`, `blender_job_read`, and `blender_cancel`. They use ordinary host-provided project/session/turn/task/world bindings. Model arguments cannot select an executable, local path, runtime, world, credentials, OS policy or receipt. Godot worlds advertise `blender_status` in the initial tool set; the other operations remain discoverable through ToolSearch. Discussion turns refuse generation and cancellation before acquiring a workspace lease.

World-bound `blender_status` accepts optional `name` (exact asset name), `offset` and `limit` (1–20, default 10). Its `jobs.items` contain same-project/world/current-storage records, sorted newest first, including sourceJobId for retained editable assets; `jobs.nextOffset` supports pagination. A new conversation can therefore discover source reuse without an old dialogue. Global `runtime_info` calls the service's unbound status and receives no jobs. Linked, corrupt, foreign and invalid-path records are excluded. While generation has finished but asynchronous import is still pending, both read and history report importing, never terminal generated.

`blender_generate` requires `{name,script,revision,manifestHash,expectedHash}` and accepts optional `previousJobId`. Name selects only `assets/blender/<name>.glb`, using lowercase letters/digits/hyphens. The source revision/hash is explicit and the destination expectation is either an existing SHA256 or null for absence. An invocation replay returns its original durable job; changing arguments under that same invocation is rejected. Concurrent invocations can generate independently, but each import must still match the source head.

The service receives host-selected `{dataPath,toolchain}`. Toolchain paths are `{broker,brokerIdentity,runtimeRoot,toolchainLock}`. Discovery hashes the pinned native executable, validates the runtime inventory lock against its compiled broker identity, and runs the native `recover <tasksRoot>` protocol. Incomplete recovery is an explicit capability failure. Every modeling operation independently validates the actual broker identity, measured source snapshot, source binding, runtime identity, OS process/network enforcement and verified cleanup. The native process is spawned hidden, with no shell; the Python script never executes in the plugin process.

Jobs have durable UUIDs and separate short native task IDs. `blender-jobs/<UUID>/record.json` is replaced atomically. The input directory contains only `script.py` and optionally a rehashed prior `source.blend` from this same project/world/active core storage. Verified outputs are copied into a managed job asset directory. The artifact list must be exactly model.glb, source.blend, script.py and report.json; ordinary filesystem components and all hashes are checked before use. Model statistics and bounded script diagnostics are marked untrusted. Absolute host roots are omitted from model tool results.

States are queued, running, generated, importing, imported, failed, cancelled and interrupted. Imported means only that a source transaction succeeded; `applied` and `playableVerified` remain false. The import uses `godotProject.patch` putBytes with the original revision/manifestHash, destination expectedHash and the actual Git content operation context. An uncertain patch transport attempts exact receipt recovery. A conflict or import failure preserves verified outputs with status generated and the concrete reason. The current core source file ceiling is 4 MiB; this is an existing storage policy, not an added model or turn budget.

To retry preserved output after a conflict, generate against current source pins using previousJobId and script `pass`. To modify an earlier asset, use that source job with a new bpy script. This reopens verified source.blend; it never accepts a caller filesystem path. Source generation alone does not implement scene placement, collision, driving, combat or other behavior. The AI must continue the ordinary Godot editing/build/check/application flow and inspect actual application state.

The model must poll a job to terminal before its final answer. Every host turn end, including completed turns, cancels remaining jobs because the source lease expires. Cancellation is scoped to the owning session/turn. Plugin shutdown, storage restore and restart also prevent late imports. On restart, abandoned records become interrupted; native recovery proves identity before removing a dead process/profile/task tree. Jobs are bound to the active core storage directory so restoring a same-named world cannot silently reuse an old job. No additional token, model-call or whole-turn cap is introduced.

Automated checks: `node --test tests/blender-jobs.test.mjs tests/blender-tools.test.mjs`. The job tests use real private temporary directories and a fake broker only at the trusted transport boundary. They cover receipt tampering, source races, destination conflicts, source reuse, world isolation, turn cancellation, interrupted recovery, storage changes and invocation replay. The tool test bundles the actual world-tool implementation and verifies discovery, host binding and write refusal. Native integration acceptance is separate and must use the real pinned Blender/broker, Rust source transaction and isolated headless Godot; fake transport tests are not player acceptance.
