# 可玩预制组件下一批计划

## 顺序与目标

用户要求预制资源让游戏内 agent 更容易呈现好效果。首批 18 个包已支持环境搭建和真实模型成组拼城门；继续以普通玩家愿望、实际画面和保存后的行为作为验收依据。当前先闭合城门的视觉纠正及连续创造基线交接，再建设宠物伙伴，不用新增资源数量代替现有流程质量。

| 顺序 | 工作 | 完成标准 |
| --- | --- | --- |
| 1 | 修复素材候选采用后的会话草稿基线交接 | 原会话继续输入能正常工作；有未采用编辑、过期世界、未完成采用和错误身份时仍拒绝；保留真实失败输入，不手改玩家数据库 |
| 2 | 完成城门视觉纠正 | 原模型原配置收到真实游戏图片，或明确记录供应商拒绝；模型按自然愿望调整遮挡的树，保留门洞、花草及原对象，正常检查、预览、采用和保存重开 |
| 3 | 可玩宠物组件与外观资源 | 正常安装的伙伴能够跟随和互动，名字、外观、模式、位置及身份能保存恢复；两实例分别修改不串对象 |
| 4 | 后续战斗、雨场及驾驶组件 | 根据宠物的通用身份、动画和状态能力逐项扩展，分别验收真实攻击击杀、具有深度的雨效果、登离机及驾驶，不以静态外观代表行为 |

## 宠物首版范围

先做一套伙伴行为以及普通犬、白色博美两种可辨识外观。外观必须有真实形体差异，不能仅涂白。资源和动画需保留原始文件、版本、哈希、作者和允许随成品分发的许可；尚未找到和确认的资源明确保持待定。与现有环境采用协调的低多边形风格，实际 Compatibility/Web 加载通过后才入库。

伙伴在平地跟随玩家，接近后停止；碰到障碍不穿越，也不以瞬移冒充跟随。首版不扩展复杂全场寻路。近处 E 抚摸产生可见反馈，远处无效；至少有待机、行走和互动反馈。换名字或外观保留同一伙伴身份，两个实例分别保存名字、外观、跟随模式及位置。

动态角色不能破坏原有树木、城墙的对象选中。现有拾取逻辑遇到 AnimationMixer 或 Skeleton3D 的 fallback 行为需按实际生产代码验证并建立明确目标合同；不能为了新增角色而放松全局来源与身份保护。组件状态必须通过既有有版本的保存/恢复协议接入，不能假设场景脚本变量会自动入档。

验收顺序为：独立档案中正常安装、检查、预览、采用，真实有限跟随和互动，障碍阻挡，两实例独立修改，保存冷重开。之后用原玩家配置提交自然愿望，单列模型发现与复用结果。开发者预制场景与模型作品分别留证。

## 执行约束

仅用 Codex 子 agent 并行，主控负责集成与成品。记录使用中文。自动验证在独立后台，不使用真实键鼠、Pointer Lock 或用户浏览器；真实玩家模型流程不新增评测 token、调用次数或整轮时长上限。冻结成品和失败记录保持不变，不手改模型作品作为成功证据。

当前宠物部分仅完成范围审查和官方资源筛选，尚无新宠物包、动画、状态接入或成功率结论。城门连续创造的 `DRAFT_BASE_CONFLICT` 是本批先行阻断项，修复及真实继续通过前不把该链路标为完成。
