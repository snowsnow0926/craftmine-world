## 1. 北极星

> **玩家说一句中文，系统尽力把它实现——包括需要新增宿主能力的请求。玩家不需要知道 L0–L4 的存在。**

判定成功的唯一标准：**玩家不用找开发者改代码，就能把想做的玩法做出来。**

由此得到三条推论：

1. **瓶颈不是模型，是「可被验证的表达能力」。** 玩家能想到的东西，必须先在宿主里有一条可被机器验收的通道。
2. **「尽力实现一切」需要一个明确的降级阶梯**（见 §3），而不是一句口号。系统在做不到时必须说清做不到什么、差哪一层、替代方案是什么。
3. **迭代成本与速度是核心指标**（CREATION_LOOP §6-4：玩家是 fun oracle）。所以路线图把「度量」放在第一位，而不是把「能力」放在第一位。

## 2. 信任分层：L0–L4

| 层 | 内容 | 谁能改 | 谁来验收 | 现状 |
| --- | --- | --- | --- | --- |
| **L0 数据** | 场景 JSON、物体、位置、参数 | 模型 | 宿主校验器 | ✅ 已有 |
| **L1 玩法** | 沙箱 JS 模块 + 8 条命令 | 模型 | 契约 + headless 验证 | ✅ 已有 |
| **L2 词表** | 新的命令 / 事件 / 资源类型 | 模型（受审） | 扩展 ABI + 扩展自带测试 | ❌ 缺 |
| **L3 内核** | 渲染、物理、输入、存档格式 | 模型（远期、限低风险区） | 冻结内核 + 回归测试 | ❌ 不建议近期做 |
| **L4 策略** | 提示词、工具集、计划、记忆组织 | 模型（受审） | **外置冻结判定** | ❌ 缺 |
| **— 判定面** | 验证器、权限模型、回滚逻辑、测试集、指标定义 | **只有人** | — | 部分存在 |

**一句话规则：可变的是「怎么做」，不可变的是「什么算对」。**

判定面永远不交给模型。这是整条路线图的安全边界，也是 L2/L3/L4 能被信任的前提。

### 2.1 当前供给侧的真实底账

| 维度 | 现状 | 出处 |
| --- | --- | --- |
| 玩法命令 | **8 条**：object.patch / player.impulse / hud.message / audio.play / target.revive / inventory.add / inventory.define / hud.panel | `app/behavior-contracts.mjs` |
| 玩法事件 | **7 种**：start / tick / interact / contact / attack / land / key | 同上 |
| 内置玩法系统 | **3 种**：health / ranged / melee，字段固定 | `app/gameplay.mjs` |
| 几何形状 | **2 种**：box / blade，**基元不能旋转** | `app/scene.mjs` |
| 材质 | **10 种**：grass/dirt/stone/wood/leaves/planks/sand/brick/light/glass + solid | 同上 |
| 外部模型 | GLB，**必须静态**（带骨骼或动画直接拒绝）；外观仅支持绕 Y 轴旋转 | `app/asset-decode.mjs:56` |
| 音效 | **5 个内置** | `app/world-runtime.mjs` |
| UI | 纯文本飘字（≤160 字）+ 纯文本面板（≤6 行） | `app/behavior-contracts.mjs` |
| 规模上限 | 128 物体 / 每步 32 命令 / 代码 32KB / 状态 16KB / 10 万面 | 各处 |

这 8 条命令就是当前全部的「言出法随」词表。

## 3. 能力缺口处理阶梯（「尽力实现一切」的可操作定义）

玩家提出任何需求，系统按以下顺序尝试，**每一步都明确告知玩家发生了什么**：

| 级别 | 情况 | 系统行为 |
| --- | --- | --- |
| **G0** | 现有词表能实现 | 直接生成候选，headless 验收，玩家应用 |
| **G1** | 现有词表能部分实现 | 先实现能做的部分，明确列出做不到的部分 |
| **G2** | 需要新词表（L2） | 生成**宿主扩展提案**：新命令/事件的 schema + 实现 + 自带测试 + 版本，走 §5 R2 流程 |
| **G3** | 需要内核改动（L3） | 生成**内核变更提案**，只允许低风险区，走 §5 R4 流程，必须人审 |
| **G4** | 当前架构做不到 | 明确说明原因 + 给出可行的替代方案，**绝不伪装成实现** |

原则（沿用 PRODUCT_VISION L39 / CREATION_LOOP §6-3）：**不允许用提前写好的关键词分支或视觉假象冒充通用开发能力。**

现有文档有三套编号，路线图统一用 **R0–R5**，映射如下：

| 路线图 | 目标 | 对应已有工作 |
| --- | --- | --- |
| **R0** | 度量与结果级验证 | H2、计划 §7.2/§7.3/§17、P1–P2 |
| **R1** | L1 词表扩容 | CREATION_LOOP §7 优先级 2、H3 |

## 5. 阶段

### R0 — 度量与结果级验证（最高优先级，先做）

**为什么第一**：L1 扩容、L2、L4 都依赖「能不能判断好坏」。没有数字，任何改动都是随机漫步。计划 §17.4 已要求记录指标但尚无数字，HARNESS_GAP_ASSESSMENT L63 明确「成功率、完成时长、修复次数、用量须由实际需求集测量后报告」。

**交付物**

1. `capabilities.catalog`：从运行契约生成（计划 §14.1、§5.3 L145「不能由模型虚构」），模型可查询自己有哪些能力。
2. **产品内 headless 试玩执行器**（H2）：移动 / 瞄准 / 攻击 / 交互 / 推进时间 / 存档恢复；独立进程 + 独立数据目录 + 禁 Pointer Lock + 不发真实键鼠。
3. **验收 DSL + acceptanceSpec**：例如「按 G 后所有目标 health === maxHealth 且位置回到出生点」。
4. **证据链**（计划 §7.3）：buildHash + sourceHashes + acceptanceHash + 初始快照 + 动作日志 + 断言结果 + 最终状态。
5. **指标落盘**：首次成功率 / 修复成功率 / 人工干预率 / 端到端耗时中位数与 P90 / token 中位数与 P90 / 失败分类。
6. **10 轮需求回归集**（计划 §17.2）：冻结、不挑掉失败、失败留在分母。

**机器可验收**

- 同一批 10 条需求跑两遍，指标可复现。
- 注入一个「语法对但没效果」的候选（复刻「刷新怪物」bug），验收器必须判失败。
- 验收器不能通过删测试 / 降条件 / 自报通过来通过（HARNESS_GAP_ASSESSMENT H2）。
- 模拟后端只证明流程正确，不能计为真实模型自主完成（计划 §17.4）。

**退出条件**：10 条需求集能自动判对错且误判可接受；指标面板可见。

**风险**：试玩执行器本身可能脆弱 → 采用「确定性模拟后端 + 独立 headless 真实引擎」两档对照。

---

### R1 — L1 词表扩容（补齐高频动词）

按「玩家最常说的话」排序。每条新能力都必须齐备：契约 + 权限 + schema + 提示词文档 + 测试 + headless 验收。

**P0（做完立刻有用）**

1. **通用资源系统**：任意命名资源（血量 / 魔法 / 体力 / 饥饿 / 护甲），含上限、恢复速率、显示名。取代写死的 `health`。→ 以后「加个蓝条」不用改宿主。
2. **object.spawn / object.despawn**：凭空造物体、销毁物体（现在只能 `target.revive` 复活已有目标，不能造新怪）。
3. **object.rotate**：绕任意轴旋转（现在基元完全不能转，只有 GLB 外观能绕 Y 转）。
4. **平滑移动**：带时长的 `object.move`（现在每 tick 瞬移，怪物只能「滑行」）。
5. **inventory.use / consume**：物品真正能被使用（现在只能加减计数）。

**P1**

6. **事件扩容**：定时器（每 N 秒）、区域进入/离开、物品使用、对话选择。
7. **音效增强**：更多内置音效 + 音量 + 位置音效。
8. **hud 增强**：颜色 / 时长 / 图标。
9. **标签与阵营**：谁是敌人、谁是友军。

**机器可验收**：每条能力都有对应的 acceptanceSpec；用 ≥20 条真实玩家请求测「不需要改宿主就能实现」的比例。

**退出条件**：先测出基线，再定目标值（不预设百分比，沿用 HARNESS_GAP_ASSESSMENT L63 的要求）。

---

### R2 — L2 扩展 ABI（模型自己造动词）

**这是「言出法随」的质变点。**

**交付物**

1. **扩展包格式** `craftmine.extension/1`：声明（新命令/事件/资源类型的 schema）+ 实现 + 依赖 + **自带测试** + 版本 + 生命周期（注册/注销，计划 §13 L646）。
2. **扩展沙箱**：独立 Worker，无文件系统、无网络，只能通过声明的宿主 API 访问。
3. **装载流程**：模型提议 → 影子副本构建 → 扩展自带测试 + 冻结回归集全绿 → 生成候选扩展版本 → **人一键接受/回退**。
4. `capabilities.catalog` 自动包含已装载扩展。
5. **版本与依赖协商**：扩展之间、扩展与内核之间的版本约束。
6. **卸载与回退**：卸载后引用它的模块必须**显式失败**，不能静默失效。

**机器可验收**

- 用第一个扩展（建议：通用资源系统或 `effect.spawn`）走完整流程。
- 故意提交一个自带测试造假的扩展 → 必须被拒。
- 卸载扩展 → 相关模块报明确错误，存档不丢。

**红线**：扩展不能改内核、不能改判定面、不能碰存档格式。

**退出条件**：至少 3 个由模型自己写的扩展成功上线并稳定运行。

---

### R3 — L4-a 策略层自演化

**模型可以改**：提示词、工具集、计划策略、记忆组织、检索策略。
**不可改**：验证器、权限模型、回滚逻辑、存档格式、测试集、指标定义。

**机制**

```
模型提出 harness 策略改动
  → 影子 harness 副本上应用（不碰正在跑的那套）
  → 冻结的回归测试集 + 历史任务回放
  → 指标不退化 → 生成候选策略版本
  → 人一键接受 / 回退
```

**为什么安全**：判定面外置且冻结。类似编译器自举——GCC 能用旧版编译新版，但永远有一个固定的 stage0 作为不动点。

**退出条件**：至少一次「模型自己改提示词/工具集 → 指标提升 → 人接受」的完整循环。

---

### R4 — L3 内核自改（远期实验，不承诺时间）

**前置条件（全部满足才可开始）**

1. 内核切分为「**冻结最小核** + 可替换部件」。
2. 可替换部件只限低风险区：后处理着色、新 HUD 元素、新渲染 pass。
3. 每个改动自带测试，全绿才允许装载。
4. 装载即快照，失败自动回退到上一个能启动的内核。
5. 第一个改动必须人审。

**明确不做**：存档格式、物理内核、输入内核、权限模型、回滚逻辑。

**退出条件**：能安全地让模型加一个后处理效果且不破坏任何回归测试。

---

### R5 — 多人共创

单机闭环稳定后再做（M6）。未决问题：谁应用、如何同步、权限归属。

## 6. 度量表（贯穿所有阶段）

| 指标 | 定义 | 现状 |
| --- | --- | --- |
| 首次成功率 | 第一次候选即通过验收的比例 | 无（仅探针个案） |
| 修复成功率 | 需 1–2 次修复后通过的比例 | 无 |
| 人工干预率 | 需要你手动改代码/重说的比例 | 无 |
| 端到端耗时 | 中位数 / P90 | 部分（单点实测） |
| token 用量 | 中位数 / P90（输入、输出分开） | 部分 |
| 「应用了但没效果」率 | 应用后玩家发现没用 | 无 |

已测到的单点数据（CREATION_LOOP §3.1–3.5）：128 物体单物体修改，输出 12,976 → **157** tokens，24 秒 → **1.0 秒**；输入按需读取后 22,722 → **14,129**（−38%）；「造小镇」18,208 → **6,253**（−66%）。

**所有指标都必须由 R0 的冻结需求集产出，且展示原始数值，不宣称统计显著**（计划 §17.4）。

## 7. 不做什么

- **不换底座**：保留 3D 第一人称。CREATION_LOOP §4 结论是「若从零开始推荐 2D 俯视 RPG，但当前不建议换」；换底座等于重写运行时与行为契约。
- **不把未实现能力做成假象**：PRODUCT_VISION L39、CREATION_LOOP §6-3。
- **不让模型改判定面**：验证器、权限、回滚、存档格式、测试集、指标定义。
- **不做**（沿用计划 §21 L910）：公开插件市场、多人协作、云记忆、自动下载任意代码、多 Agent 同时写世界、付费图像/3D 服务、新渲染器。
- **不为 L3/L4 牺牲 L0/L1 的稳定性**：低层不稳定时，高层放开只会放大故障。

## 8. 现在最该做的第一批

按顺序：

1. **R0 最小版**：`capabilities.catalog` + 一个 acceptanceSpec 执行器 + 指标落盘。
2. **用 R0 复刻「刷新怪物」bug**，确认验收器能抓住它。
3. **R1-P0 第一条**：通用资源系统（替代写死血量），顺带验证 R0 的验收能力。
4. 然后按 R1 顺序推进，R2 在 R1 稳定后启动。

**为什么不是先做 R2**：R2 让模型能造动词，但如果没有 R0 的判定，造出来的动词是否正确、是否真的有效果，仍然只能靠人肉点。**先有裁判，再有新动作。**
