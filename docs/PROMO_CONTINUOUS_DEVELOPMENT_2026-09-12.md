# 宣传愿望驱动的持续开发记录

用户已授权持续循环开发，直到主动要求停止。主线以宣传分镜及 v2 愿望测试
方案为准，每轮按“定位缺口→通用实现→独立验证→提交→下一轮”推进。
不将预置目标场景作为模型生成成果，不将离线断言当成实机宣传依据。

## 本轮基线和已确认事实

起点为 `82380309`，已验证 Windows 包的产品源码为 `04a2ef6d`。
主工作区其他产品文档的未提交修改保留；开发在独立工作树完成。

| 环节 | 现有基础 | 当前限制和推进方式 |
| --- | --- | --- |
| 沉浸入口 | 双入口、覆盖浮层、预览采用、文件评审已交付 | 真人输入手感与旧 profile 升级仍按实际反馈检验 |
| 环境及同一物体修改 | 结构化树、岩石等五类操作与持续状态 | 不将五类操作宣传为宠物、飞机等全部能力 |
| 普通脚本新玩法 | Godot 工程修改、启动检查、手动候选采用通路存在 | 未知愿望进入待人工核验，不绕过需求检查来开自动采用 |

| 宣传愿望驱动 | 已有六组／主线离线清单与指标修正 | 原驱动只接收 CA 固定案例，不能冒充任意愿望测试 |

## 第一轮

1. 复用 `39e634d5` 的离线清单和自主率分母修正，保留原始 Linux 证据。
2. 修正依赖图：狗失败只阻塞依赖狗的修改；怪物等独立步骤继续，完整主线
   仍保留失败，不能将部分成功汇总成全通过。
3. 为现有隔离模型评测增加单条普通愿望提交入口，只接收当前玩家文本与
   愿望 ID，通过原 agentPrompt、目标捕获和原请求预算执行。未来题目和
   裁判答案不进入模型上下文；提交前持久登记，回执丢失或重启后不重发。
4. 修复 Godot 历史、资产、创作包的能力报告与实际路由不一致。

## 随后的循环

- 冻结新构建，先进行零模型驱动和账本验证；再选择小范围真实愿望尝试。
- 第一条重点为宠物：外观、同一身份、约定行为、保存和后续修改分别判定。
- 根据实际失败补观察和交互能力，保持平台权限、采用与迁移检查。
- 宠物闭环稳定后推进固定版本复用、战斗和天气；飞机与城市各自保留独立
  探索，避免前置失败挡住其他组，也不拼接成同一世界的连续成功。

## 证据口径

新增愿望入口沿用既有每个隔离评测 profile 最多 40 次产品请求的持久预算，
不自动使用文档建议的 120 次上限。是否扩大真实调用范围另按实测成本决定。
本记录创建时没有发起本轮真实模型调用，没有六组功能通过结论。
所有测试禁止真实鼠标键盘、Pointer Lock、窗口激活和用户浏览器操作。
