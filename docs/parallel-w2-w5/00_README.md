## “并行”具体怎么做

1. A–F 从统一的派工基线建立各自分支与工作树，立即开始独立部分。不得同目录多人改代码。
2. 各组完成接口定义、可运行模块和本组测试；依赖未到时使用明确标注的契约夹具验证接入。不能把夹具结果写成最终产品验收。
3. 各组回传 `REPORT_<ID>.md`、`DELIVERY_<ID>.json`、提交列表和证据。共同入口的接线建议单独交付，统一由 G 合入。
4. 协调者先审查 A/B 的事实来源和恢复协议，再审查 C/D/E，随后利用 F 的脚本集成复验。不要求组与组互相等待到完全停工。
5. W2–W5 只有在集成后的同一源码版本通过相应验收才完成。最后的真实模型、三次压缩、整包安装和升级恢复需要顺序执行，不能靠六份局部报告替代。

推荐接线顺序：A 的持久接口 → B/D/E 的请求、玩法与系统服务 → C 的真实界面接线 → F 的集成场景 → 用 E 的构建链生成最终包并复验。A–F 的准备与模块开发仍可并行。G 按实际依赖调整顺序。
