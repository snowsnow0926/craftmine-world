## 第一步：接收审查

- 检查每组基线、分支、提交、补丁/bundle 能否实际读取和应用，核对 hash 和未提交改动。异机报告只有不可访问提交号时，记交付不完整，不能猜测代码。
- 区分正式提交、临时接线 overlay、夹具和真实实现；测试成绩必须对应明确源码与二进制。
- 审查跨组文件改动、锁文件/新依赖、权限和数据迁移。确认没有密钥、个人 profile、大缓存或无关改动。
- 逐项填写 ACCEPTANCE_MATRIX：通过/失败/未验证/依赖缺失及证据。模块已完成和 W 阶段已完成分开。

## 第二步：按依赖接线

1. 先集成 A 的 Rust 单一事实来源、作品引用/安装、恢复和预算接口，验证迁移与回滚。不得并存两个正式世界写入者。
2. 接入 B 的最终请求/压缩/取消边界与同一任务预算；补宿主侧工具权限，不能只依赖提示词。
3. 接入 D 的实际运行器、组合示例和扩展验收；确认 A 捕获/安装的依赖与 D 编译/加载的依赖一致。
4. 接入 C 的桌面 UI 与可信世界选择、任务/作品/恢复通道；保留 PI 功能和已有应用/关闭语义。
5. 接入 E 的系统凭据、备份目录授权、诊断、独立身份及构建链。
6. 接入 F 的测试辅助入口。限定在既有严格 headless 模式，不能开放通用 eval/RPC 或降低输入隔离。

公共入口由你逐处审查后修改；多个 integration.patch 涉及同一位置时重建最终实现，不能强制套补丁。冻结路由/内核变更要核对理由和实际差异，任何调整都不能削弱验证门槛。

可复现的小缺陷直接在集成树修复并补适当回归；需要原负责人重做的内容生成 `REWORK_<ID>.md`，写清失败证据、文件、期望行为和再验收命令。用户回传新提交后只复验受影响范围及必要集成链。

## 第三步：阶段验收

| 阶段 | 必须拿到的集成后证据 |

| W2 | 实际原生 PI Agent + 真实配置模型，空世界生成树、修改、检查评审、实际面板应用、关闭重启、新会话检索并安装精确作品版本；失败保留草稿 |
| W3 | 真实同一任务至少三次强制压缩仍绿色完成；最新纠正保留、完成/取消任务不复活、预算累计、两世界不串、丢回执不重复写、消息/任务/世界三层恢复 |

| W5 | 集成提交构建的程序/安装包、源码和许可证清单一致；凭据保护、备份恢复、首装/升级失败保护、离线世界、诊断脱敏与中文指南；干净 Windows 和可见体验有实际证据或明确未完成 |

先跑风险相关逻辑与组件测试，再在同一集成版本上跑关键原生真实场景，最后打包并对包内程序复验。已有通过检查不因汇总报告而重跑多次；代码、依赖、故障或验证范围发生变化才扩展复验。

所有测试仍禁止真实鼠标/键盘、Pointer Lock、显示/置前窗口或用户浏览器操作。没有授权隔离环境的人工/干净系统项明确保留未验证；不能把离屏截图当成可见合成或物理双击验收。
