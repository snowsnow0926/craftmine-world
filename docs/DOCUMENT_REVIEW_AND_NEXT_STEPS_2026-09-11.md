# Craftmine World / 最中幻想：文档交叉审阅与推进建议

日期：2026-09-11  
审阅基线：`snowsnow0926/craftmine-world`，`master`，`7f815914634fe862a48857f228e1116b7cf9d7bf`。  
性质：基于已推送文档相关章节与交付记录的建议；不是代码修改、执行授权、测试结果或新的全项目完成声明。本次没有运行 Windows 成品，没有调用产品模型，没有改动仓库。不覆盖本机未提交或未推送材料。

## 一、结论

保留现有工作台、Godot、Rust 状态与应用协调架构。下一阶段应同时推进两件事：用少量开放愿望检验真实创造范围；让已经能够创造的内容可以继续修改、修复、保存和复用。不能只在树、箱子和固定句式上继续增加通过数，也不应直接转向全客户端原生化、完整社区或大规模模型策略实验。

推荐下一轮主题：**开放愿望诊断与宠物创作闭环**。六组宣传愿望继续作为覆盖清单，第一条重点开发故事先选择宠物。选择理由是它同时覆盖外观、行为、对象身份、连续修改、问题反馈与复用，并与已有用户“小狗可见但无法采用”的历史反馈相连；这不代表历史问题今天仍存在。[R1][R2][R3]

| AI 效率方案 | 先分类失败，再按版本提供资料、复用模块、做小型对照 | 更长推理一定更好，或文档中的实验规模已经得到费用授权 |

沉浸式造物开发记录已经报告了真实碰撞、可信目标、源码分页、自动采用、保存与复用等修正；反馈结案也记录版本入口、应用原因、全屏和任务统计进入 preview.10。下一轮应复测相关行为，而不是重新从零实现。[R2][R4]

当前状态文件记录 preview.11 已交付、本轮新增真实模型试验延期。方案、实现、集成、成品、自动验收、真实模型、真人复测是不同证据维度。[R3]

## 三、先建立“愿望在哪一步被挡住”的表

保留六组宣传摸底：环境、宠物、战斗、倒流雨、飞机、城市。先核对已有正常产品入口和证据，随后在有效预算内做真实最小尝试；执行前标明各例的功能、范围、质量与保存要求。

每个愿望按同一条流程记录：

**理解要求 → 找到素材/模块 → 修改工程 → 构建运行 → 验证实际效果 → 正式采用 → 保存重开 → 继续修改。**

失败至少区分：资料/工具接线、资源缺失、玩法实现、检查表达不足、采用协调、状态迁移、性能或运行目标、环境和模型服务问题。证据不足可以记未知；不能一律写“模型不行”。

| 愿望 | 结果要求必须分开看 | 首轮有用的问题 |
|---|---|---|
| 树与花草 | 形态、空间、既有对象保留 | 会不会用新场景覆盖旧世界？ |
| 狗变白色博美 | 外形与辨识度、同一身份；跟随等行为以明确要求为准 | 是缺合适素材、行为失败，还是做成后无法采用？ |
| 巨怪与游戏内枪械 | 操纵、命中、伤害、死亡、原敌人身份 | 实际战斗成立，还是只有动画和血条？ |
| 雨停并倒流技能 | 可触发、雨的局部/全局范围、时序、重复使用 | 能否正常游玩时使用，而不是暂停整个世界？ |
| 驾驶飞机 | 外观、操纵、飞行空间、镜头；起降按本次约定 | 是只有模型，还是可真实改变轨迹？ |
| 城市探索 | 美术相似度、覆盖范围、路线可达性、局部修改 | 是可走的空间，还是一张远景？ |

C/D/L 仅作为这份任务记录的辅助信息。C 是玩家要什么；D 是在当前资源与环境下有多难；L 是实际改哪里。它们不是通行证或能力分数，也不应变成玩家必须学习的菜单。[R1]

## 四、通用创作通路应优先于不断增加专用名词

建议保留四类处理路径：明确属性走确定性工具；已有成品能力走固定版本复用；新玩法走普通世界工程脚本；确有宿主/引擎缺口才提出独立平台变更。

固定的五类物件和有限中文表达可以作为快速路径，但不能充当整个产品创造范围的上限。C/D/L 提案与分层评估均强调，普通脚本工具可以表达许多新玩法，不必每个名词增加一个宿主工具。[R1][R5]

需要重点核查“创作表达”和“验收表达”之间的差距。愿望检查记录及 CN3 记录明确使用有限、完整匹配的表达；未知或复合要求保留待核验。此设计保护了真实性，但未证明任意新玩法都有顺畅的核验与采用路径。[R6]

建议分开处理：

- 平台底线：身份、权限、构建、正式采用和进度保护，不能由生成模型修改或跳过。
- 可运行的业务要求：针对跟随、命中、技能切换等建立独立可执行检查；一类机制覆盖多个表达，不是每个句子写一套产品分支。
- 审美与模糊要求：使用真实画面和玩家反馈；需要时采用独立辅助评审，但明确它的局限，不代替硬性状态检查。

开放要求尚未完全验证时，应按现有安全策略提供可解释的候选、待核验项及可用的试用路径；不能伪造自动通过，也不应仅因为不在快捷语法中就断言无法开发。实际能开放到什么程度需检查现有应用策略，不能借本建议放松权限。

## 五、把“东西做出来”与“东西能工作”分开改善

宠物、怪物、飞机与城市至少包含外观、行为、身份与持久状态，以及与当前世界的集成。素材库和创作包方案已经提供对应的分类与固定依赖方向，不需要再发明一套内容体系。[R7]

建议先建立少量有来源、能预览、能替换、可编辑的资源与组件，并在新版本记录实际支持范围。优先核查的适配点包括模型导入、需要的动画、碰撞、尺寸与朝向、相机/挂点、输入与状态接口。这里是建议核查的能力，不是对当前实现缺失的断言。

对外观和功能分别验收：涂白不自动等于博美；精细飞机模型不自动等于能驾驶；可驾驶的简陋飞机也不自动满足高辨识度要求。需要降低质量或缩小范围时形成明确选择，保留原始未满足目标。

复用不是作弊，伪装复用来源才会误导。建议同时记录从零开发、模块安装、素材适配和混合创作的结果。首次摸底不能预先为题目补好答案；后续把失败驱动的通用能力加入产品是正常开发，但必须换版本、重新测，并披露变化。[R1][R8]

## 六、最值得补齐的玩家闭环：这里不对 → 修好它

玩家体验计划已经给出问题现场设计：玩家原话、真实构建、相关对象、可用进度快照、有限语义事件、可选游戏视图截图，以及修复和复测关联。应在已有入口上核查缺口，而非再造一套诊断平台。[R9]

示例：玩家说“团子不跟我了”。系统保留相关现场，在隔离实例定位；修复后既检查跟随恢复，也检查名字、外观、其他对象与当前进度没有被破坏。

现场默认本地保存。只捕获游戏视图，不录制系统输入或其他应用。物理、随机和异步过程不保证凭快照完全重演；报告应说明缺失，不把辅助定位包装成任意倒带能力。[R9]

同时将玩家已接受的关键规则关联到作品，例如宠物名字与跟随、宝箱只领奖一次、子弹命中才伤害。后续修改检查受影响规则；依赖分析不足时扩大检查，不假装无关。玩家明确改变玩法时更新对应规则，保留变更历史，不能把旧愿望永久锁死。[R9]

## 七、让创作成功后留下可复用成果

第一批只打磨一类完整作品的闭环：

**同一宠物生成与修改 → 保存为固定版本作品 → 新世界放两只 → 只改一只 → 保存重开 → 原世界及另一只不变。**

完整复用必须包括实际需要的场景、脚本、素材、依赖、参数、初始状态和检查，而不只是外观复制。世界复制、模板安装、实例升级和个人存档复制需要各自明确状态语义。[R7][R10]

成熟能力可以降低同等愿望的成本，但需实测。优先让模块来自已经成功的故事，再用不同措辞和不同场景复验，不为全部可能的玩法预建庞大体系。

## 八、建议的推进批次与出口

以下是建议顺序，不是已授权执行或日历工期；实际剩余工作须先与当前代码和成品核对。

| 批次 | 本批重点 | 必须留下的成果 | 暂不扩展 |
|---|---|---|---|
| 0：事实与摸底 | 固定成品，核对关键旧反馈，六组愿望最小尝试 | 每例准确阻断点、成本与原始证据；当前能力表 | 不临时修补受测包，不扩大模型预算 |
| 1：开放宠物闭环 | 宠物生成、同一对象修改、必要行为、采用、问题修复、保存 | 普通台词实际完成；合理澄清可记录；外观/行为/状态分项结果 | 不同时重写所有底座，不增加每类物件专用宿主 |
| 2：复用与持续保护 | 将成功宠物做成可复用作品，验证两实例和跨世界；旧规则回归 | 固定依赖、独立实例、重开一致、真实复用收益 | 不先建完整市场或复杂推荐 |
| 3：扩展主线与挑战 | 按摸底结果补战斗/天气公共能力，重跑完整宣传主线；飞机/城市保留独立探索 | 连续主线与独立故事分开出结果，不拼接成全通过 | 不把全部宣传愿望都作为一次发行的门槛 |
| 4：他人可用 | 独立环境交付、好友试玩、版本化反馈与作者修复 | 接收者能打开、能玩、可保存、能反馈；成品身份清楚 | 网站先展示分发，原生迁移另按实际瓶颈启动 |

原生计划明确以真实能力缺口或运行瓶颈作为工程启动理由，不要求重写全部工作台。社区计划也允许本地包与下载分发先成立，不以完整 Git 托管、支付、实时协作作为前提。[R11][R12]

## 九、节省 Agent 工程成本的方法

只维护一个简短的当前入口：当前版本、产品输入、已交付范围、已知阻断、下一批目标、相关方案与证据链接。历史计划和失败保留，不为统一口径批量改写原始报告。现有 DEVELOPMENT_STATUS 可继续保存历史，给日常接手 Agent 提供精简摘要即可。[R3]

给子 Agent 分派有边界的工作：一方补实际能力，一方负责真实观察/回归，一方负责玩家反馈入口；总控协调共享协议并串行集成。并行规模是建议，不要求增加空闲分支；同一世界的写入和正式采用不能并行竞争。沿用项目 Codex 子 agent 约定，不替换产品内部正常的 Agent runtime。

不必立刻执行 AI 计划中的全部对照规模。先根据真实失败选择一种改动：指导资料、复用模块、工具流程或模型设置，保持其他条件尽量不变。公开开发题与保留题分开；失败和重试消耗计入成本；新任务与重启不重置整轮预算。[R8]

新增一套愿望分类、记忆或测试系统之前，先核对既有任务、需求、问题和用量记录是否可以承载。分类应帮助执行，不应让每个小改动额外多经过数轮付费规划。

## 十、现在真正值得观察的指标

在真实用户规模很小时，优先看个案和原始数量：愿望是否达到约定结果；从提交到正式可玩的总耗时；下一次修改是否保留旧成果；保存重开是否正确；用户问题是否得到可复测的修复。

C/D/L 提案中的周活跃有效创作者指标适合未来观测。当前不需要先建设庞大分析平台，也不能把模拟玩家当真人留存。后续用户回访需有清楚观察窗口；未观察到重开不是自动失败。[R1][R9]

建议交给下一轮 Codex 的目标摘要：

> 先核对当前成品和已交付能力，对宣传片六组愿望做有预算、可追溯的最小诊断；不修改受测成品，不把未知核验当完成。依据阻断结果，优先让同一宠物从生成、改外观、保留行为到反馈修复、保存重开和跨世界复用真实成立。复用现有世界工程、应用、版本、素材和诊断服务，只补缺口。修复产生新产品版本后重新验收，保留首次失败。开发测试继续使用独立 headless/offscreen 与隔离数据，不抢占输入，不动个人安装；真实模型调用服从实际有效授权和统一预算。每批交付明确的玩家故事、失败与未覆盖项，不以工具数、代码量或分阶段标签宣布完成。
