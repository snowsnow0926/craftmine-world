## token 上限为什么会出现

截图的“剩余 938k”表示模型单次可容纳的上下文还有空间。
`TOKEN_BUDGET_EXHAUSTED` 来自本地任务的累计预算：旧默认值是 100 万，
同一任务内每步输入、输出、压缩和评审调用都会计入，用过的缓存输入也有真实用量。
界面的“本轮合计”与持久任务账本也不是同一个范围。

本批让新任务默认不限制累计 token；旧任务保留原额度和账目，玩家可以在
世界工作台解除上限或设置新额度，再恢复已保存的任务。实际用量、未知请求的预留量、
草稿和恢复关系都保留。模型自身的上下文与单次输出容量仍然存在，请求次数、
压缩次数和运行时限也单独显示，不能把这些说成模型无限上下文。

本地额度错误有独立说明并停止自动重试，不再误报成 DeepSeek 服务故障。

## 缓存做了什么

旧代码把每步变化的任务编号、草稿版本、回执和用量放在系统提示词中，
导致后面很长的重复历史也失去相同前缀。本批保留稳定的系统提示词和历史，
把最新任务事实放到本次请求的末端。事实仍逐次从宿主重建，不会作为玩家新指令保存。
工具调用与结果的相邻关系、思考内容和图片都保留。

使用现有 `deepseek-v4.1-flash-expires-on-0910`、high 思考配置进行了 6 次真实 API 对照：

| 请求结构 | 第一次 | 第二次 | 第三次 |
| --- | ---: | ---: | ---: |
| 每步改变系统内容 | 0% | 1.35% | 1.35% |
| 稳定系统内容、最新事实放末端 | 0.67% | 98.24% | 98.24% |

这是固定约 1.9 万输入 token 的小规模实验，总用量 114,096 token，
未知用量 0。它证明这处修改改善了前缀复用，不代表所有长期创作都会达到这个比例。
新增内容、发现新工具、压缩与服务端缓存预热仍会影响结果。
原始非敏感证据在 [deepseek-prefix-experiment.json](dispatch-reports/batch07/evidence/deepseek-prefix-experiment.json)。
DeepSeek 缓存默认开启、按相同前缀复用且不保证 100%。
见 [官方缓存说明](https://api-docs.deepseek.com/guides/kv_cache/)。

## 与本次问题一起完成的范围

- 重要操作保留持久回执；刷新、重启或丢失回复后确认原结果，避免重复安装和保存。
- 作品已装进草稿但检查提交失败时，可以重新检查原草稿，保留任务与预算。
- 游戏可占满工作区，一键回到创作，原会话和其他页面保持。
- 扩展的多个命令先整体校验，再一次发布状态，后一个失败不会留下半次奖励或伤害。
- 正式应用会保存本次验证过的扩展；重启后继续使用相同扩展状态。
- 评审保留全部失败断言；玩家可明确选择“带评审提示应用”，独立机器检查和加载仍须通过。
- 接入实际启动、界面帧间隔和任务耗时数据；缺少样本时不填造假的 0 毫秒。
- 复核并补强预算设置丢回复后的恢复，以及损坏备份的预算字段检查。
