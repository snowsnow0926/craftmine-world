# Agent Godot 首条普通创作验收

日期：2026-09-12。这是 GU0/GU7 的一条实际样本，不代表全部开发计划完成，也不是总体成功率或收益对照。

## 输入与真实产品配置

原样输入：

> 在我前方做一扇可以交互开关的蓝色门，关上时必须挡住人，打开后能走过去。门旁边放一个宝箱，打开给我一枚代币，每个宝箱只能领一次，退出重进也不能重复领取。保留已有内容。

从普通新建空白世界及 `sessionCreate` 开始，未使用旧评测初始化。模型为用户已确认的 `deepseek-v4.1-flash-expires-on-0910`，思考强度 `max`；完整实际绑定是 1,000,000 上下文、384,000 输出配置、agent 模式、inherit 权限。没有额外 token、模型调用次数或整轮时长上限，没有调整产品原有限制。

固定成品源码 `d4b15812227723d37538870bb11b9fe5ebc90c31`，版本标签 `0.14.4-preview.12`，实际包清单摘要 `b5da7e0fc3ea1823fa11226fc66f3aaa713d6e964a65c77dfc94e957b702431b`。该包包含初期能力真实性、分页/引擎元数据、诊断、变更摘要和普通会话初始化；后续静态关系查询、核心门通行和 Kenney 模块改动未混入这次成品结果。

## 模型实际完成情况

模型自主检查源码与底座，使用已有高层操作创建 `blue-door` 和 `token-chest`，没有测试脚本替模型编辑源码。初始视线落在世界边界墙，模型自己判断那里无法通行，选择正前方 4 米的可玩位置 `[0,0,2]`；宝箱在其右侧 `[1.8,0,2]`。

模型共 13 次请求，产品记录的整轮 wall time 为 341,000 ms。用量：input 212,955、cache-read 614,144、output 19,005（其中 reasoning 14,009）、total 846,104。总时长包含测试 agent 审查普通权限请求的等待，不能当成纯模型生成速度；缓存读取也不能算成同等未缓存费用。

普通权限流程逐项批准了放门、放宝箱、启动检查三项操作，没有切成 auto 权限。模型得到编译/运行协议检查 passed，但世界默认未授权自动采用，因此正确报告尚未应用。组合愿望在本版冻结要求解析器中是 `unsupported`，不能用绿色基础检查声称完整玩法已被产品验证。

随后测试 agent 沿正常预览、采用、保存、关闭和重新打开流程继续，原检查候选被采用，冷启动仍保持相同 world/build。没有直接改库或替换正式源码。

## 独立实际玩法证据

| 项目 | 实际观察 | 判定范围 |
| --- | --- | --- |
| 蓝门外观 | 截图可见蓝色门及旁边宝箱；运行实体颜色为 `#0000ff` | 简单原型外观，不是精细美术验收 |
| 关闭阻挡 | 60 帧实际 walk 从 Z=6 停在 Z=2.553335，门前沿 Z=2.25 | 该门与当前控制器实际产生阻挡 |
| 打开通行 | 实际射线交互命中门，随后 60 帧 walk 到 Z=-1.256665 | 从门前走过门后，未用传送冒充移动 |
| 再次关门 | 从门后瞄准打开的门板，实际交互关闭；等待 4 帧后碰撞恢复，再走 60 帧仍停 Z=1.449123 | 验证开门之后仍可关上并再次阻挡 |
| 一次奖励 | 射线命中宝箱，首次交互 token 从 0 变 1，opened=true | 实际账本与交互对应 |
| 重复交互 | 返回 already-opened，token 保持 1 | 同实例不重复领取 |
| 关闭重进 | 全进程正常关闭后再启动，初始 token=1；再次交互仍 already-opened | 冷启动恢复后不重复领取 |

第一次固定探索脚本在走回门边后，用预计位置瞄准宝箱，实际射线落在地面，两次交互均是 `no-entity`。原记录完整保留，这不算宝箱失败或通过。探索驱动新增 `--aim-creation-entity`：先等待减速，再依据实时碰撞边界和位置提出视角，必须由实际射线确认目标 ID 才执行交互。这里采用原 creation 场景 0.65 米眼高作为测试瞄准假设，射线不命中就停止，不修改对象或玩家位置。

追加的关门测试也保留了一次未命中的瞄准记录：测试最初按原门洞中心瞄准，实际开门交互区域随铰链一起旋转，因此射线没有命中。修正为实际 meshBounds 中心并独立确认射线后，关门和反向阻挡验证通过。交互后的同帧 open=false 而 solid 尚为 false；等待真实物理帧后 solid=true，再进行移动验证，没有把延迟更新前的状态当作碰撞完成。

所有新建、模型、采用及五次探索进程都使用独立 profile、隐藏不可聚焦 offscreen 窗口，退出审计无输入/焦点违规、页面错误或清理失败。物理动作通过既有有限 adapter 接口，没有真实鼠标/键盘或 Pointer Lock。上述探索是开发者独立行为验证，不冒称真人游玩。

## 同会话改色与已有进度保留

后续原始愿望为“把这扇门改成红色，其他东西保持原样。”。在 `2ae18b25` 包上，模型发起仅改颜色的高层操作，却因玩家已站在门旁被保守放置边距判为 `CREATION_PLAYER_OVERLAP`。玩家位置和门没有被测试驱动移动。模型随后给出的澄清选项都不能如实保留原目标，因此跳过，未虚称玩家已经退后。后续重试权限在审查期间过期，该轮记录为 `RUN_FAILED`，原始报告完整保留。

产品现已修复：只有几何发生变化才重新检查放置边距；颜色修改仍保留实体、源码和事务校验。撤销也采用同一原则，涉及空间改动时对完整恢复结果检查冲突，避免先后顺序漏掉同批实体。这条实现有源级回归证据，不能由下述不同模型路径代替覆盖。

在精确包 `6f1708f11f79`（清单 SHA-256 `2965b4a1459c8ba55bac60d4033fda11654bd60367c955d0603d01960cc14f91`）中，通过普通 `continue-creation` 恢复同会话原目标。实际发送的是“继续完成被中断的创作，保留已保存的改动。”，不是再次提交全新改色任务。沿用用户确认的 Flash/max 和原产品预算，未新增限制。模型自行选择通用 `godot_project_patch`，只修改 `creation.json` 中门的颜色及源码 revision；没有命中颜色高层操作，因此这轮仅证明普通创作完成，不能称为颜色 helper 的真实端到端覆盖。

模型实际 7 次请求，用量 input 53,470、cache-read 742,144、output 7,822（reasoning 5,598），总计 803,436；产品 wall time 243,587 ms，含审批等待。逐项批准通用补丁和正式检查，共两次权限，无新澄清。随后正常预览、应用、保存、退出和冷开，没有额外模型请求或驱动源码修改。

应用后及冷开后的两实体与应用前逐字段比较：除门变为 `#ff0000` 外完全相同，包括 ID、位置、尺寸、碰撞、门的关闭状态、宝箱 `opened=true` 和奖励参数；玩家整个观察对象、token×1、时间 12 均保持。源码 revision 为 4，冷开创建了新运行实例并保持同一采用 build。三次客户端启动均正常退出，输入、页面错误和清理审计均为空。

这次正式应用的 `requirementStatus` 仍为 `unsupported`。进度保留结论来自应用前后和冷开后的明确观察比较，不能冒称冻结要求已经自动验证通过，也不代表任意任务进度迁移已覆盖。
