## 1. 产品目标与范围

采用真实 Git 管理玩家世界的创作工程，提供类似 GitHub Desktop 和 GitHub 的历史、分支、改动提案、合并与作品版本体验。玩家可以持续尝试玩法、保留不同方案、恢复过去的内容，并在未来分享工程供他人继续创作。

每个世界拥有独立的工程仓库，与最中幻想产品源码仓库分开。基础创作、历史查看与恢复均可离线使用，不要求 GitHub 账号。模型生成是否联网仍由模型供应商决定。

第一阶段交付本地历史、分支、差异、受检查的应用与恢复、旧历史迁移和完整备份。之后补复杂合并、作品发布版本与远程同步。实时多人共同编辑、在线社区运营、完整 Git 托管平台和商业计费属于后续范围；此处的远程同步不自动公开玩家工程。

核心体验：玩家说“把步枪改成散弹枪”后，系统在创作分支修改；旧世界继续运行。玩家查看变化并试玩，满意后应用，应用时保留正式世界最新的兼容进度。以后可以恢复步枪版本，也可以从散弹枪版本继续另一种创作。

## 3. 玩家界面与操作语义

| 底层概念 | 玩家界面 | 明确含义 |
| --- | --- | --- |
| Repository | 世界工程 | 一个世界的内容与创作历史 |
| Commit | 创作版本 | 一次可定位的工程内容；可处于未检查、失败、通过或已应用状态 |
| Branch | 创作分支 / 新方案 | 从选定版本继续修改的独立方向 |
| Diff | 查看变化 | 物件、参数、场景、文件和素材版本的变化 |
| Change proposal | 改动提案 | 本地候选及其检查、试玩、说明；无需先创建 GitHub PR |
| Merge / Apply | 合并并应用 | 合并后的准确内容重新验证，并完成正式世界应用事务 |
| Tag / Release | 作品版本 | 固定的可交付内容及其导出产物 |
| Fork | 复制并继续创作 | 新世界身份与独立存档，保留来源关系 |

历史默认按玩家的一次需求分组。卡片显示标题、时间、来源分支、内容摘要、检查状态和操作；AI 中间补丁、修复与文件差异在详情中查看。检查状态来自对应检查记录，AI 只能提出摘要，不能自行标记“通过”。

操作区分别提供“恢复此创作版本”“回到这个存档”“从这里创建新方案”。第一项恢复内容并迁移当前兼容进度，第二项恢复内容和所选进度快照，第三项创建独立分支或世界副本。恢复旧内容生成新记录，保留之后的历史。

新分支试玩默认使用独立进度副本，带来源存档标识；与正式世界隔离。合并分支仅合并创作内容，不自动合并金币、奖励或任务完成次数。新建世界副本默认使用作品初始状态，复制某个游玩存档是明确的另一项操作。

## 4. 技术选型与职责

### 4.1 Git 适配层

首选随客户端提供固定版本的 Git CLI，由 Rust 宿主通过参数数组和结构化标准输入调用。VM0 固定版本、二进制来源、哈希和分发声明；不依赖玩家预装 Git，不修改其全局 Git 配置，不要求填写邮箱才能本地提交。作者身份使用本地显示名和稳定标识，远程发布前允许设置公开署名。

使用受管理的 bare 仓库存储历史，通过独立工作副本处理草稿、合并和检查输入。可复用 Git worktree 的工作目录机制，但工作树不是执行隔离；交给 Godot 的构建副本不包含 Git 元数据，并继续使用 GD0 的隔离执行器。[Git worktree](https://git-scm.com/docs/git-worktree)

GitHub Desktop 的历史、差异和分支交互作为参考；其 MIT 代码可在核对具体依赖后复用。GitHub Desktop 的 MIT 不代替随包 Git 及其他组件的许可。避免整体移入另一个桌面壳；现有 PI/Electron/React 继续承载产品。[GitHub Desktop](https://github.com/desktop/desktop)

### 4.2 单一内容来源

| 数据 | 权威来源 | 其他层的角色 |
| --- | --- | --- |
| 工程文件、提交父子关系、分支与版本标签 | Git | SQLite 可缓存查询索引，不能独立生成另一套内容历史 |
| 当前正式应用版本、任务、操作日志、检查和存档 | 现有 Rust / SQLite | 通过 commit OID 引用内容；应用记录不是第二份源码 |
| 大素材、固定文件正文 | 素材库内容存储 | Git 保存素材锁和引用，不保存运行时索引数据库 |
| 引擎导入缓存、可重建构建与缩略图 | 派生缓存 | 必须可由固定输入重建，不能成为历史唯一依据 |

Git 对象 ID 按所选仓库对象格式处理，不在产品协议里假定永远是 40 字符。素材正文和规范化锁文件使用 SHA-256，与 Git OID 分开命名。

工程纳入场景、脚本、项目配置、必要稳定 UID 文件、底座说明和素材锁；排除存档、凭据、个人对话、Git 操作凭据、`.godot` 生成缓存和可重建引擎产物。源码大小和引擎构建限制独立校验，接入 Git 不意味着无限放大现有预算。

## 5. 与素材库共用的数据契约

以下是拟定协议，不是已注册 API。**本节为版本管理、素材库、创作包和社区四份计划共享引用格式的定义处**。包结构与七类内容由[创作包计划](CREATION_PACKAGE_DEVELOPMENT_PLAN.md)细化，社区原样使用固定引用，不另建一套版本身份。

| 类型 | 必需内容 | 规则 |
| --- | --- | --- |
| `AssetRef` | `assetId, version, contentHash` | 逻辑资源 ID、不可变版本、规范化内容清单的 SHA-256；不得引用 latest |
| `FileRef` | `path, sha256, bytes, mediaType` | 一个版本可包含多个文件；路径为受校验的相对路径 |
| `ContentRef` | `repoId, commitOid, assetLockHash` | 源码与素材锁共同确定一份创作内容 |
| `BuildRef` | `ContentRef, baseId, baseVersion, engineVersion, target, buildId` | 引擎、底座和目标变化必须重新检查；构建正文另行验哈希 |
| `ProgressRef` | `worldId, progressId, revision, BuildRef, stateSchemaVersion, contentHash` | 指向确认过的游戏进度，不随分支合并改变 |
| `OperationContext` | `operationId, worldId, repoId, branchId, expectedHeadOid, expectedAppliedOid, expectedProgressRevision` | 宿主绑定身份与旧值；模型不能切换目标世界或伪造回执 |

Git 根目录拟使用 `craftmine.assets.lock.json`，格式 `craftmine.assets-lock/1`。包含规范排序的 `AssetRef`、安装位置、完整固定依赖以及运行需要的覆盖配置引用；不写绝对路径、下载凭据和个人聊天。`assetLockHash` 按规范化 UTF-8 内容计算，规范化规则与测试向量在 VM0/AL0 同时冻结。

VM0/AL0 与 CP0 同批冻结哈希和排序向量；CP 第 6 节给出包清单与 JCS 的拟定规则，不能在实现中产生两种规范化结果。`AssetRef.version` 使用递增整数；底座 `baseVersion` 沿用底座 manifest 的版本类型，构建记录通过固定底座资源核对两者，不强制互相转换。

版本管理负责提交和比较锁文件；素材库负责解析、取得、校验与固定资源正文。安装、替换或升级素材只产生草稿文件与锁文件变更，由同一次创作提交应用。备份和清理都按 Git 受保护引用可达的锁文件遍历资源依赖。

## 6. 提交、分支与合并

正式分支为 `main`；用户方案使用稳定内部 ID 对应分支，名称作为可编辑显示信息。每个 AI 任务绑定准确分支与基线，不能因玩家切换界面而改写另一分支。第一版每个分支只允许一个写入任务，跨分支仍通过宿主租约协调。

草稿补丁自动保存；中间检查点使用受保护的内部引用保留，历史界面按任务折叠。用户可随时手动“保存创作版本”。只有已检查并完成应用事务的内容才显示为正式已应用；失败内容仍能查看、继续修复或另开分支。

VM1/VM2 先支持从正式版本创建分支、独立修改、比较、快进应用，以及将旧内容生成为新的恢复提交。正式基线已变化时，候选明确过期，保留其草稿；不自动覆盖新内容。

VM3 增加三方合并。纯文本无冲突可以生成合并候选；场景实体删除/引用、资源依赖、同一素材两个版本以及二进制内容冲突都必须报告。二进制不按文本拼接，不用“取最新”消除冲突。AI 可提出解决方案，但合并结果必须重新构建和执行结果检查，不能复用父提交的通过记录。

差异分三层展示：玩家可读摘要、场景/资源结构差异、准确文件 diff。没有可靠解析器的格式只显示真实文件变化和预览，不让摘要冒充语义证明。局部撤销与挑选提交在 VM3 后实现，保留依赖冲突提示。

## 7. 应用事务与故障恢复

Git 引用更新、SQLite 提交、素材文件写入和 Godot 实例切换不共享一个原子事务，必须沿用操作日志和耐久回执建立可恢复流程：

1. 固定目标 `ContentRef`，核对完整素材、实际构建、检查证据、当前正式基线和候选有效期。
2. 准备候选实例；应用时冻结正式实例的必要事件，捕获并耐久保存最新进度。候选试玩消耗和奖励不进入正式进度。
3. 在独立副本执行状态迁移，校验实体、背包、装备、任务与一次性奖励；不能兼容时保留原实例并说明可选方案。
4. 写入持久操作意图，保护旧、新 Git 对象与资源引用；新实例载入迁移状态并报告真实运行身份。
5. 使用旧 OID 条件更新正式引用，再提交 SQLite 中的应用版本、进度和回执。引用的条件更新用于拒绝并发覆盖。[Git update-ref](https://git-scm.com/docs/git-update-ref)
6. 宿主确认所有部分一致后显示应用成功，再释放旧实例。期间正式世界查询与发布不得暴露未完成操作为成功。

在每个持久边界注入进程退出。重启根据操作意图、Git 引用、数据库记录和状态哈希决定补齐提交或恢复旧世界；恢复完成前冻结新的写入和发布。已提交但响应丢失只查询原 `operationId`，不重复应用或发奖励。

应用后的 UI 和运行实例以 SQLite 已确认的部署记录读取 Git 内容；Git 临时提前推进而数据库尚未提交时，由待恢复操作解释，不能当作新的正式部署。VM2 必须证明恢复状态机覆盖这个窗口。

## 8. 旧历史迁移、备份与空间管理

迁移以世界为单位：预检并备份 → 暂停该世界写入 → 将现有不可变修订导入独立新仓库 → 核对每个文件字节、父链和来源 → 建立旧修订到 commit OID 的映射 → 验证当前正式版本和存档 → 一次切换后端标记。旧目录和数据库记录保留用于审计与恢复。

素材历史只能根据实际保存的构建/清单重建。没有可靠历史素材对应关系时，标为“仅源码历史，尚不可重现”，不能把当前素材清单套到所有旧版本。旧检查状态只关联原输入与原证据，不自动升级成新版本通过。

切换失败继续使用旧后端；切换后已有新创作时，不提供会丢弃新提交的简单降级。需要经验证的转换或从备份创建副本。现有工具名通过宿主适配器过渡，不允许旧修订接口绕过 Git 继续写历史。

完整备份包括 Git 受保护引用及对象、未提交草稿、旧修订映射、素材锁引用的全部正文、应用/检查元数据和玩家选择的存档。`git bundle` 可作为 Git 部分的载体，但完整备份还必须另外打包素材正文、草稿和数据库数据。[Git bundle](https://git-scm.com/docs/git-bundle)

备份先检查所有引用完整性并生成哈希清单；恢复到新隔离目录完成校验后才登记为可用世界。缺少正文、磁盘满或哈希错误时不替换原世界。区分“分享作品包”与“个人完整备份”，前者默认不含个人进度和对话。

空间管理先清理可重建缓存，再处理明确无引用的临时内容。正式版本、命名分支、未结束任务、回收站保留项、迁移映射所需历史和本地备份保留项都纳入引用保护；不得仅因 Git 对象较旧而清除。清理策略必须与素材库共同验证。

## 9. 宿主与模型工具接入

拟新增 Rust `version_store` / `version_operations` 适配层；现有 `godot_projects`、`godot_builds`、`godot_applications`、`godot_runtime`、`backups` 分别接入内容读取、构建身份、应用事务、状态绑定和归档。模块名称在实施时按仓库惯例确定。

玩家界面新增历史列表、分支选择、变化详情和恢复流程，接入现有作品/检查辅助面板，不替换 PI 会话界面。工具能力至少包含：历史分页、读取指定版本、创建方案、比较版本、创建内容检查点、准备合并候选、查询操作结果。

模型只可在绑定任务范围内读写草稿和提出候选；正式应用、删除保留历史和远程发布通过对应玩家操作完成。普通参数修改沿用既有创作授权，不增加重复确认。检查器和回执仍由宿主产生。

Git 调用使用固定程序、受控配置和参数数组；处理中文、长路径、大小写碰撞与路径穿越。不运行导入工程的 hooks、外部 diff/merge/filter 命令，不递归拉取子模块。构建只读取已核对的文件集合，不能从项目自带配置取得宿主执行权限。

| VM3 合并与冲突 | 三方合并、资源冲突、语义摘要、局部撤销；合并结果重新验证 | VM2、AL3/AL4 固定依赖安装 | 无冲突和冲突样本均有准确结果；合并不重复奖励、不静默改素材版本 |
| VM4 作品版本与 Fork | 命名版本、离线作品包、来源记录、创建新世界、引用保护与清理 | VM2、AL4/AL5 | 从固定版本创建独立世界；包无个人凭据/默认进度；清理后历史仍可复现 |
| VM5 远程同步 | Git 远端适配、凭据存储、拉取预览、推送范围、素材正文同步和 LFS 兼容 | VM4、AL6 | 两台独立环境取回相同内容与素材；中断可续传；失败不移动正式版本 |
| VM6 社区协作 | 托管作品页、远程改动提案、来源关系与团队权限 | VM5、独立社区产品计划 | 以专门的多人权限与发布验收通过后上线 |

首个可交付范围是 VM0–VM2，加上完整备份和 AL0–AL3 的必要能力。VM3/VM4 构成后续本地创作增强版；VM5/VM6 单独立项部署，不能为等社区功能而延后基本恢复能力。

VM4 的作品包和 Fork 与 CP3/CP4、AL4/AL5 共同实施，包格式遵循 CP 计划。VM6 在本计划中特指完整 Git 协作；普通社区目录、固定包上传与下载按 CC1/CC2 推进，无需等待 VM5/VM6。

远程同步中，Git 仓库和素材正文分别核对完整性。当前哈希内容库不是 Git LFS 服务；VM5 必须实现并验证适配，不能只提交指针就宣称工程可跨机器使用。[Git LFS](https://git-lfs.com/)

## 11. 必须覆盖的验收场景

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| V01 | 连续三次创作与重启 | 历史内容准确，任务内细节可追溯，正式版本一致 |
| V02 | 创建两个方案并切换界面 | 两分支独立，原任务继续写原绑定分支 |
| V03 | 草稿未检查或检查失败 | 草稿可恢复；不改变正式世界或伪造通过状态 |
| V04 | 生成期间继续获得金币，再应用武器修改 | 应用使用最新正式进度，预览奖励不回流 |
| V05 | 恢复旧武器内容 | 新建恢复记录，兼容进度保留，后续历史仍可找回 |
| V06 | 旧内容不支持新增状态字段 | 明确拒绝或生成迁移副本，无静默清空与重复奖励 |
| V07 | 准备后正式基线或素材锁变化 | 候选过期，不能覆盖更新；原分支内容保留 |
| V08 | Git 引用更新与 DB 提交之间退出 | 按日志恢复，Git、部署记录、存档和实例最终一致 |
| V09 | 提交完成后丢失回包 | 原 operationId 查回同一回执，无重复应用 |
| V10 | 文本无冲突但玩法冲突 | 重新检查能判失败，不以 Git 合并成功当作玩法成功 |
| V11 | 同素材两个版本、场景删除引用、二进制冲突 | 列出冲突，人工或 AI 方案形成新候选后再检查 |
| V12 | 历史缺素材、坏 blob、未知旧检查状态 | 如实显示可恢复范围，不拼造历史事实 |
| V13 | 完整备份与全新目录恢复 | Git 历史、素材、应用及选定进度一致；恢复失败不覆盖原世界 |
| V14 | 清理缓存和取消任务 | 保留可达版本、活跃任务与受保护资源，未删除用户源素材 |
| V15 | 中文/长路径、大小写、链接及恶意 Git 配置 | 有明确结果；不越界，不执行项目提供的宿主命令 |
| V16 | 远程只收到 Git、缺少大文件正文 | 标为同步未完成，不允许生成伪完整作品或替换正式世界 |

性能使用拟定的 1 千/1 万源码文件、1 千/1 万提交、多个素材体积档测量；这些是测试规模，不是已支持容量。记录硬件、冷/热缓存、历史页和 diff 的 P50/P95、操作取消时延、迁移与备份耗时。在 VM0/VM1 测得基线后冻结产品门槛，不预写未经验证的速度承诺。

纯 Git/数据库测试与真实 Godot 产品验收分别报告。真实模型验收至少包含生成武器、再修改、恢复旧版、分支应用四种任务，保留失败分母、人工介入和耗时。自动浏览器/客户端验证均在独立 headless 或 offscreen 进程、独立数据目录运行，初始化禁用 Pointer Lock，不发送真实鼠标键盘输入或抢占焦点；不运行历史禁止入口。[项目约束](../AGENTS.md)

## 12. 推进与交付要求

每阶段提交实现、实际命令、通过/失败/未验证范围、证据路径和迁移说明。计划状态与实现状态分开，未实现工具不得写成已可调用。任何影响共享引用、锁格式、状态迁移或备份范围的改动，同时更新素材库计划与契约测试。

下一步从 VM0 与素材库 AL0 的共同契约开始，完成 Git 最小适配和一份现有世界历史迁移样本，再进入产品接线。工作量和排期在该样本、素材解析和执行器依赖明确后估算。
