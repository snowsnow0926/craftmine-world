## 1. 产品目标与本轮决策

玩家既能创造完整世界，也能把底座、玩法、物件、场景、素材和数据分别保存、导出，让别人安装到自己的世界继续创作。基础导入、导出、历史与复用离线可用；社区是可选的发现与分发渠道。

本计划采用七类创作包、同一套固定版本引用、同一套包校验与安装流程。第一版采用 ZIP 容器和 JSON 清单，保留 Godot 与常见素材原格式，不发明另一套游戏引擎文件。界面按用途分类，2D/3D、视角、平台、题材、标签分别记录。

官方底座和玩家底座遵守同一套生命周期与兼容接口。玩家可以制作新的基础运动方式、镜头、场景组织与交互方式；底座通过检查后进入“创建世界”的选择列表。固定官方底座通过测试，不代表开放玩家底座已经完成。

首个整体样本：甲制作横版底座与宝箱模块，导出给乙；乙创建关卡、放置两个宝箱、修改其中一个，再导出世界；丙在全新数据目录导入并游玩。甲发布新版本时，乙的世界继续使用旧版本，只有明确升级并检查后才改变。

[C / D / L 愿望、模型与社区总体方案](WISH_CDL_FRAMEWORK_AND_NORTH_STAR_PROPOSAL.md)统一描述创造结果、交付难度、技术范围及后续模型分工。本计划负责使已有成果具备可安装、可配置、可验证的形态，帮助降低重复开发成本；不把“有参考项目”直接视为“当前世界可复用”。

## 3. 七类内容与分类边界

| 类型标识 | 玩家名称与例子 | 包应提供什么 | 安装方式 |
| --- | --- | --- | --- |
| `base` | 底座：第一人称、俯视、横版、卡牌桌面 | 最小工程、基础控制与场景组织、宿主适配、能力/状态约定、可验证的空白入口 | 注册后用于新建世界；更换现有世界底座走转换副本 |
| `world` | 世界：村庄冒险、完整横版游戏；也可用作模板 | 确切底座、源码、场景、初始内容、完整依赖锁和入口 | 新建独立世界，游玩或继续编辑 |
| `module` | 玩法/代码模块：背包、对话、合成、种植 | 接口、脚本、参数、UI/场景适配、依赖、状态及必要迁移 | 安装进兼容工程，配置并验证功能 |
| `object` | 物件/角色：门、宝箱、敌人、机器 | 可实例化场景、素材、行为绑定、碰撞、默认参数和稳定模板实体 ID | 放置实例；各实例拥有独立身份和进度 |
| `scene` | 场景/关卡：房屋、森林、地下城片段 | 场景及内部对象、入口/出口、锚点、坐标约定、外部接口和依赖 | 作为子场景或关卡加入世界 |
| `raw` | 原始素材：模型、图片、音效、动画 | 实际文件、格式信息、来源、许可和预览信息 | 供场景、物件或界面引用 |
| `data` | 数据：物品表、配方、技能数值、对白 | 数据文件、结构版本、校验规则、稳定记录 ID、目标模块接口 | 校验后供指定模块读取 |

一个包只有一个主要类型，可依赖其他类型。一个商店如果重点是交易规则，保存为 module；一个摆好货架、NPC 和交易入口的商店建筑，保存为 scene，并依赖交易模块。需要分别复用的内容发布为不同资源，避免同一包同时拥有多个互相矛盾的安装语义。

“世界模板”是 world 包的一种使用方式，不复制另一份格式；“游戏作品”是 world 的产品呈现；“原型/演示/正式版”是成熟度标签。“我的本地库/社区/团队库”是来源范围。个人存档、工程历史和可执行游戏是导出用途，不增加为第八、第九种可安装资源类型。

代码不是按后缀自动形成一种玩法。独立通用代码可包装为 module，必须说明调用接口、依赖、限制和实例状态。数据表的 JSON/CSV 是数据；绑定了脚本的 Godot 资源要进入含代码检查流程，不能仅按 `.tres` 后缀当作无代码素材。

首批静态格式继承 AL 计划：PNG/JPEG、静态 GLB、WAV/OGG；含代码包优先 GDScript、`.tscn`、必要 `.tres` 和稳定 UID 文件。动画/骨骼 GLB、外链 glTF、FBX、更多音频格式按实际适配结果扩展。Godot 本身有统一资源机制，但本产品仍须验证每种格式和依赖。[Godot 资源说明](https://docs.godotengine.org/en/stable/tutorials/scripting/resources.html)

## 4. 玩家底座开发约定

### 4.1 职责与最小交付

底座包提供：空白世界入口、场景组织、基础交互、必要移动/镜头或其他输入方式、资源接入、暂停与恢复、初始状态、存档校验、可观测状态和一个最小演示。底座可以没有人物移动，例如卡牌桌面；统一的是宿主接口，不是所有游戏都强制相同玩法。

底座开发包应包括模板工程、接口说明、最小参考实现、无输入模拟的检查工具、错误码和一份能通过完整生命周期检查的样例。官方三个底座先通过同一工具，再开放第三方开发，避免工具只认识官方目录名称。

[沉浸游玩模式与造物主世界方案](IMMERSIVE_PLAYER_AND_MAIN_WORLD_DEVELOPMENT_PLAN.md)规划一个专门面向玩家的官方造物底座。底座、空白主世界模板和可组合能力分别沿用本计划的 base、world 与 module/object 等分类；技术身份、配置与能力声明在实施前共同冻结。它与其他官方或玩家底座使用同一注册、版本、状态与包校验流程，不增加特殊包格式。

| 接口职责 | 必须证明的行为 |
| --- | --- |
| 声明与初始化 | 报告确切底座、协议、引擎、入口、能力、参数与原生状态格式；绑定宿主给定的世界/构建/实例身份 |
| 加载与暂停 | 初始化保持暂停；加载成功后才恢复游玩；隐藏、切世界和退出遵循宿主协调 |
| 捕获与恢复 | 返回完整且有界的原生进度；还原不触发额外奖励；拒绝其他世界、未来不支持版本及坏状态 |
| 检查与观测 | 暴露入口、实体、状态及玩法结果的只读观测；检查成功由可信执行器签发 |
| 资源与玩法接入 | 提供已声明的场景锚点、交互/物品等接口；缺少能力时明确拒绝相应模块 |
| 销毁与错误 | 释放实例资源；保存失败、载入超时和取消不能把正式世界标成已成功切换 |

这些是接口职责，方法名在 CP0 对照现有运行协议确定，不凭本文另建第二套保存协议。沿用共享适配层中“运行快照回执”和“Rust 耐久保存回执”的区别；收到引擎快照不等于已经保存到磁盘。

### 4.2 身份、适配与权限

保留已有 `craftmine.godot-base/1` 声明中的 `baseId/baseVersion`；例如现有底座版本使用字符串。库中的 `AssetRef.version` 则沿用递增整数，两者分别表示底座协议实现版本与资源发布序号，不能互相强制转换。锁文件固定底座的 AssetRef，构建中的 baseId/baseVersion 必须与该资源内容一致。

玩家复制改造底座得到新的 assetId/baseId 和来源关系；不能用官方 ID 发布替代内容。普通资源版本升级保持同一资源身份；底座协议或存档结构变化必须有明确兼容/迁移声明。

首发玩家底座使用已支持的 GDScript 与受管理资源。原生动态库、GDExtension、编辑器插件、外部命令和更换 Godot 引擎不自动随底座获得执行资格，分别进入以后宿主扩展的独立开发范围。声明某项能力仅表示请求和用途，不能自行授予文件、网络或进程权限。

导入后先登记为“未验证底座”；可信执行器完成准确版本的生命周期和目标平台检查后，才显示“可用于创建”。已下载、静态解析通过、能够显示缩略图和实际可运行分别记录。

## 5. 模块、物件、场景与数据开发接口

模块声明提供/需要的接口及版本、参数结构、可接收事件、状态结构和安装作用域。背包逻辑可以跨底座，3D 拾取射线与 2D 碰撞检测通过各自适配接入；兼容性要对每个实际组合检查，不用“通用”标签替代证据。

为支持 Agent 检索和小模型配置，说明中应区分实际功能、必需/可选依赖、可调参数、安装步骤、初始状态和检查范围。安装配方是既有受控工具的步骤与参数约定，若含辅助脚本仍按原代码执行边界处理。作者说明、已有证据与当前组合结果分别记录；这些信息属于现有七类包的元数据和说明，不新增特权包类型。

同一世界中，自动加载单例名、全局类名、输入动作、资源 UID、文件路径、接口提供者和稳定实体 ID 都可能冲突。安装前构建冲突清单；模块不能静默改写 `project.godot`、底座入口或其他模块设置。宿主根据声明生成受控配置，重映射使用结构解析与引擎核验，不能对脚本做粗糙的全局字符串替换。

物件提供可放置锚点、参数范围和默认初始状态。场景还声明单位、坐标空间、入口/出口、外部引用及关卡切换接口。保存选中内容时，应列出需要一并导出的依赖和需要接入的外部能力，不能只复制可见模型而漏掉脚本、声音、全局规则或任务数据。

数据包固定 schema 标识、版本和目标模块接口。物品/配方 ID 不以显示名称代替；删除或修改被存档引用的记录时，升级检查必须给出映射、兼容保留或失败。首版数据校验使用宿主支持的有限声明规则，包内脚本不能作为可信宿主校验器执行。

静态共享资源与可变实例状态分开。相同贴图可以共享正文，两个宝箱的“是否开启”必须保存在各自实例状态里。Godot 会复用加载的资源对象，因此实现时还要验证可变资源的实例化/复制策略，防止改一个对象影响另一个。[Godot 资源共享行为](https://docs.godotengine.org/en/stable/tutorials/scripting/resources.html)

## 6. 统一包结构与不可变版本

### 6.1 结构草案

拟定 ZIP 包格式名为 `craftmine.package/1`，单资源清单为 `craftmine.resource/1`；这些名字尚未注册为产品 API。界面显示“创作包”，首版文件名使用 `名称-版本.zip`，以后更换文件关联扩展名不改变容器协议。

```text
package.json                         包格式、根 AssetRef、资源清单和所有条目的 FileRef
resources/<contentHash>/manifest.json 单个资源的不可变内容与 contentHash
resources/<contentHash>/payload/...   场景、源码、数据、素材、说明及许可文件
catalog.json                         导出时的名称、描述和预览索引；不决定运行内容
previews/...                         可选预览文件，由包条目清单校验
```

`package.json` 的条目清单覆盖其余所有文件；拒绝未列出的文件、重复路径和多个根声明。它自身不列入自己的 FileRef，避免哈希自引用；传输时另计算整个 ZIP 的 `archiveSha256` 和 `bytes`。资源 manifest 不把自身列入 payload 的文件列表。

单资源 manifest 由 `format`、`content`、`contentHash` 构成。`content` 至少含 assetId、整数 version、kind、FileRef 列表、确切 dependencies、入口/接口声明、兼容约束、状态约定以及许可/来源文件引用；按类型补充第 4–5 节的必需字段。contentHash 对规范化 content 计算，不包含 contentHash 本身、包路径、远程地址或可变展示元数据。

需要追溯工程来源的资源可以记录 ContentRef，但它只是来源声明；是否由该提交产出还须检查记录证明。导出清单在冻结的源码输入之外生成，不能把包含自身哈希的清单再提交回同一输入而造成循环。

### 6.2 规范化、身份与版本规则

CP0 建议采用 JCS 规范化 JSON，先按协议对文件/依赖等集合排序，再进行对象规范化与 SHA-256。JCS 不替项目规定数组语义排序。固定 UTF-8、整数范围、缺省字段、重复键拒绝及路径规则；Rust/TypeScript 必须通过同一组含中文、非 BMP 字符和排序边界的向量。[RFC 8785](https://www.rfc-editor.org/rfc/rfc8785)

资源 version 采用正整数；展示用版本名可以是“1.2 正式版”，但安装始终固定 AssetRef 三元组。协议整数不超过 JavaScript 可准确表示的范围；较大的标识使用字符串。更新源码、文件、依赖、入口、兼容声明或版本内许可清单都生成新版本，不覆盖旧版本；搜索标签和介绍单独更新。

发布前的草稿可以修改，定版后内容不可变。同一 assetId/version 的不同哈希拒绝登记为同版；同一哈希正文可物理去重，但不同作者、许可和资源身份不能合并。包内容哈希表示内容一致性，不证明作者、许可有效性或执行安全；社区来源另由账号权限与发布回执确认。

路径采用相对正斜杠路径；拒绝绝对路径、盘符、父级穿越、设备名、备用数据流、大小写/规范化碰撞以及符号/硬链接。禁止包自行声明一个可写的宿主绝对目录。冻结路径规则后再构建内容清单，导入不能悄悄改名以掩盖冲突。

### 6.3 依赖锁与离线完整性

沿用 `craftmine.assets.lock.json` / `craftmine.assets-lock/1`，记录完整固定依赖和安装绑定。包 manifest 声明直接依赖，锁文件给出解析后的完整闭包；两者必须一致。依赖图首版要求无环，同一世界每个 assetId 只解析一个版本；冲突时生成可审阅解决方案，不能偷偷选择最高版本。

普通“导出创作包”固定为自包含：根资源与完整依赖 manifest、正文、必要许可文件全部在包内。缺失正文或不允许该种源文件分享时，不生成伪完整包。以后有明确授权下载机制时再提供单独标识的在线依赖分发方式，不将其冒充离线包。

远程服务内部可以按哈希下载缺少的正文以节省带宽，但用户下载的便携包仍满足自包含要求。引擎缓存不打包，稳定 UID 和必须随工程分发的源资源保留；动态加载路径必须声明可用资源集合并检查，不能仅用一次静态扫描推断完整依赖。

## 7. 导入、复用、改造与升级

导入状态：接收 → 隔离临时区 → 限额/清单/哈希检查 → 登记资源 → 排队预览/检查 → 可用或明确失败。收到包、入库、可预览、可安装、已应用分别显示。格式升级遇到未知主版本或未知必需能力时拒绝安装，保留原包并说明原因。

| 操作 | 身份与内容处理 | 进度处理 |
| --- | --- | --- |
| 安装固定版本 | 写目标草稿与依赖锁，为新对象生成实例 ID 和实体映射 | 使用作者的初始状态 |
| 修改当前实例 | 保留实例身份，在版本历史中保存局部参数/内容覆盖 | 保留兼容进度；改变结构须检查 |
| 保存变体 / Fork | 创建新 assetId，记录准确来源版本；世界 Fork 另建世界/仓库身份 | 默认新的初始状态；不会继承作者奖励 |
| 升级已有实例 | 比较旧模板、新模板和局部覆盖，生成候选；仍固定新版本 | 在隔离副本迁移最新正式进度，失败保留旧实例 |
| 卸载 | 检查依赖、实体引用、任务与背包数据，再生成候选 | 按明确规则保留或迁移状态；不能静默丢弃 |
| 恢复旧内容 | 通过 VM 创建恢复记录，保留之后的历史 | 尝试兼容迁移当前进度；完整回档为另一操作 |

应用只能进入 VM2/GD2 的正式事务。包管理器不能直接修改正在运行的世界；构建检查通过后仍要核对 expectedHead、已应用版本和最新进度。中途退出、响应丢失或重复操作由 operationId 查询原回执，不重复安装、扣物品或发奖励。

底座替换默认创建转换副本，不在原世界里切一个标签就改变 2D/3D。只有显式实现并验证的转换器才迁移场景、物品和进度；不支持的内容逐项报告，原世界保持可打开。

底座/模块迁移脚本与普通游戏脚本同样不受信任，只能在受限的状态副本上运行，输出经宿主校验。无转换器时允许从模板重新开始，但必须是用户选择的新世界，不以“升级成功”掩盖进度重置。

## 8. 三种导出产品与运行目标

| 导出入口 | 内容 | 验收标准 |
| --- | --- | --- |
| 分享创作 | 第 6 节的可编辑创作包；默认当前固定版本，可选另附经过检查的工程历史 | 全新目录离线导入，源码、依赖和初始内容齐全 |
| 发布游戏 | 基于确定 BuildRef 的可运行程序、项目数据、必要运行库与声明；在客户端游玩的 world 包也可单独发布 | 对明确目标实际启动、游玩、保存与重启；源包通过不替代发行测试 |
| 个人备份 | VM/AL 的共同归档：Git 对象与保留引用、素材、草稿、应用记录及选定进度 | 新目录恢复一致；与公开上传入口分开 |

三个入口给出导出范围、目标、预计体积和缺项。分享包及默认备份排除账号密钥、模型凭据、临时签名 URL、设备路径与无关私人对话；备份需要选择创作记录时明确展示范围。普通包不携带 `.git` 目录或 hooks；可选 Git 历史使用经核对的 bundle 和引用清单，检查所含历史文件与作者信息。

独立游戏导出先支持实际验收的 Windows x64。客户端内部 Web 运行目标、Windows 独立程序以及将来的浏览器发布是不同构建目标；任何一个通过不自动证明另一个可用。Linux/macOS 导出与测试按后续需求排期，不作为本地创作包首发条件。

独立运行要求清点所有宿主依赖：保存、输入、资源读取和必要游戏接口必须有可随游戏分发的实现；模型调用、创作历史、账号和社区功能按作品实际需要另行处理。尚依赖工作台服务的作品明确显示“在最中幻想中游玩”。导出不会凭空解决宿主依赖。

[Godot 原生运行与多目标交付长期计划](NATIVE_RUNTIME_LONG_TERM_DEVELOPMENT_PLAN.md)进一步规划客户端内原生运行、中央嵌入和独立 Windows 交付。其 NR5 为本计划 CP4 提供或复用原生运行适配与验收，包格式和导出用途仍由本计划定义。两份计划不重复建立导出系统；中央嵌入与独立导出分别验收，长期计划不推迟当前已安排的工作。

Godot 的 Export Project 生成程序与项目数据，Export PCK/ZIP 只生成资源包；具体平台还需要匹配模板和工具。因此 PCK 文件不能独自充当已经完成的 Windows 游戏交付。[Godot 导出说明](https://docs.godotengine.org/en/stable/tutorials/export/exporting_projects.html)

## 9. 权利信息与社区发布关系

沿用[已确认许可方案](LICENSING_STRATEGY.md)，代码、原始素材、完整作品分别记录适用许可。作者选择并确认自己有权分享的范围；作品能商用、能随游戏分发、能把原始素材再分享和能发布派生包是不同用途，不能合并成一个“可商用”开关。

发布包携带作者/来源、适用文件范围、许可文本或标识和必要声明；自创内容、第三方内容与待核对内容分别显示。许可状态未知的文件可本地保存，对外发布流程列出待处理项。模型不能替作者确认权利，社区通过技术检查也不等于版权已经确证。

本轮不修改现有代码许可证，不生成商业合同。导出运行时代码采用 MIT 是已确认的目标，仍须逐文件确认后按实际发行清单执行。第三方素材与上游代码按原声明处理，不能通过打包获得额外再授权权利。

共享源包和未来仅允许成品分发的付费素材存在不同依赖条件。首个社区版本只接收能满足所选分享用途的内容；受限制依赖若无法合法纳入便携包，该发布方式不可用，另走已验证的成品发行路径或替换依赖。

## 10. 客户端与 AI 工作流

本地“素材与作品”面板沿用 AL 的搜索、类型、来源、版本与预览布局。底座详情主要操作为“创建世界”，world 为“游玩/复制创作”，module 为“加入当前世界”，object/scene 为“放入场景”，raw/data 为“选择用途”。兼容性缺项在操作前解释，技术哈希放在展开详情。

创作中增加“保存为可复用内容”流程：选择范围 → 建议类型与依赖 → 设定名称、参数和初始状态 → 检查新实例 → 保存本地版本。保存世界为模板时提供初始状态预览，避免把作者游玩结果作为默认起点。

[玩家产品体验与持续创作计划](PLAYER_PRODUCT_EXPERIENCE_DEVELOPMENT_PLAN.md)细化中文参数面板、修改范围、常用玩法模块和好友试玩入口。参数描述扩展仍由本计划统一定义，作品默认配置、个人设置和实际游玩进度分别处理；试玩复用本计划的导出用途、依赖与初始状态要求，不增加新的包类型或另一套导出系统。

AI 先检索已有资源，再选择直接安装、配置、改造或新建；工具返回紧凑清单与固定引用，按需读取源码。依赖解析、类型与接口校验、实际检查和回执由宿主完成。包内 README、描述和脚本均为待分析内容，不能成为提高工具权限或自动上传的指令。

思考档位、指导文档/Skill 的版本与按需加载、失败升级和效果对照详见 [AI 创作效率与可靠性计划](AI_CREATION_EFFICIENCY_DEVELOPMENT_PLAN.md)。包内说明可作为指导来源，不能自动获得宿主技能信任；是否提速须在相同模块、工具和验收条件下测量。

记录实际复用的版本和变更来源，区分人工包、固定样例与真实模型产物。用户普通创作授权沿用原任务；公开发布使用明确的发布入口和可见范围，不由自动归库、模型总结或一次本地导出触发。

## 11. 存储、故障、迁移与空间保护

复用现有 Rust/SQLite 和 AL 的内容存储，新增包清单、接口、底座登记、安装绑定及导出任务记录；不建立第二套源码历史或资源正文库。类型索引、预览和搜索缓存可重建，manifest 与正文不能仅保存在缓存中。

导入采用流式读取和临时正文，区分压缩大小、解压总量、条目数、嵌套深度、单文件和解码预算。目录穿越、ZIP 重复条目、畸形编码和解压膨胀在登记前拒绝；脚本、模型导入和预览运行在实际隔离进程中，静态检查不能替代执行隔离。

导入/导出任务有耐久阶段、operationId、取消和重试记录；正文完成并校验后才登记可用版本。磁盘满、文件占用、传输中断、旧进程退出和重试必须产生准确结果。垃圾回收只删除已证明无引用的临时内容；正在检查、导出、备份和应用的资源持有保留引用。

旧 `raw/object` 可保留类型；旧 `world-template` 通过新格式适配为 world。旧 `creation` 不能按名称盲转，应根据场景组织、规则和依赖分别转换为 module/object/scene/world，必要时由作者选择。保留原包字节、旧 ID/版本/哈希及新引用映射；旧 Web 脚本不能冒充原生 Godot 脚本。

迁移先在副本完成，生成新记录并验证；失败继续使用旧库。当前备份缺口必须与 VM/AL 先补齐，每个可交付阶段都能恢复已经支持的数据，不能把备份推迟到完整社区上线。

CP2 与 AL3/VM2 是同一条产品链路的不同职责，不要求三个团队先独立完成后再接线；CP3 与 VM4/AL4 同理。阶段编号是依赖分组，不是单线程执行顺序或已承诺工期。

本地试用版先完成 CP0–CP2 和所有已支持类型的备份；七类内容完整开放需 CP3 与 CP5 的基础升级能力。社区试用版可先分发已通过本地验收的类型，未验收类型禁用发布。CP4 的 Windows 独立游戏导出单列交付，不阻挡已可在客户端游玩的世界包分享。

## 13. 验收矩阵与性能测量

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| CP-A01 | 七种类型与错误类型声明 | 必需接口准确检查；后缀或标签不能绕过类型规则 |
| CP-A02 | 包导出到全新离线目录 | 完整依赖、源码、初始状态和许可正文一致，不依赖来源缓存 |
| CP-A03 | 同版不同哈希与不同身份同正文 | 前者冲突；后者仅物理去重，来源不混淆 |
| CP-A04 | 清单自引用、重复 JSON 键、Unicode/排序边界 | 按共同向量得出稳定哈希或明确拒绝，无跨语言差异 |
| CP-A05 | 路径穿越、同名覆盖、链接、ZIP 膨胀 | 不写出临时目录，不产生可安装记录，预算准确生效 |
| CP-A06 | 缺传递依赖、环、同资源不同版本、动态资源缺失 | 完整列出原因，不运行部分包，不自动用 latest |
| CP-A07 | 玩家底座初始化、隐藏、退出、保存失败与重启 | 完整生命周期及准确耐久回执；不假成功切世界 |
| CP-A08 | 未验证底座、未知协议、要求原生扩展 | 不能成为已支持底座或绕过执行器条件 |
| CP-A09 | 背包用于两个已声明底座和一个不兼容底座 | 已验证组合真实运行；不兼容项具体说明缺失接口 |
| CP-A10 | 同一宝箱两个实例，只改一个 | 外观覆盖、开启状态、奖励与 ID 独立 |
| CP-A11 | 场景入口、全局类、UID、输入动作冲突 | 准确列出冲突；结构映射后重新导入检查 |
| CP-A12 | 升级背包/任务/配方，保留当前进度 | 物品和一次性奖励正确；不支持的状态变更拒绝或生成转换副本 |
| CP-A13 | 作者发布新版本与修改介绍 | 旧世界内容不变；运行变更必须新版本 |
| CP-A14 | 安装/应用各持久边界退出及响应丢失 | 重启恢复一致，重复 operationId 不重复安装与奖励 |
| CP-A15 | Fork 世界/底座和保留来源 | 新身份与初始状态正确；不冒用官方身份 |
| CP-A16 | 导出包含凭据、历史私人文件或不完整许可清单 | 发布预检列出具体缺项；默认分享范围符合第 8–9 节 |
| CP-A17 | Windows 独立游戏全新环境运行 | 离开工作台仍能启动、游玩、保存、重启；依赖/许可清单匹配实际产物 |
| CP-A18 | 备份恢复、旧包转换、归档清理 | 历史/正文/选定进度可恢复，原库与受保护引用未破坏 |
| CP-A19 | 甲导底座/模块→乙创作→丙游玩 | 每一步使用真实包和干净数据，保留失败与版本证据 |
| CP-A20 | AI 检索、安装、改造并再导出 | 真实调用记录说明复用了什么；模型不能伪造检查或发布回执 |

CP0/CP1 与 AL 共用真实样本测量压缩/解压体积、1/16/64 MiB 文件、不同依赖深度与文件数；这些是试验档位，不是全部支持承诺。记录打包/导入 P50/P95、内存峰值、取消延迟、临时磁盘占用及冷/热缓存条件，冻结发行预算后再验收。

纯格式、固定作者工程、真实模型和玩家体验分别报告。自动验证遵守 [AGENTS.md](../AGENTS.md)：独立 headless/offscreen 进程及数据目录，初始化禁用 Pointer Lock，不操作真实鼠标键盘、不置前窗口、不使用被禁止的历史输入测试。玩法通过页面脚本、HTTP 和引擎状态接口验证；操作手感留给用户自主试玩。

## 14. 排期、风险与启动任务

先完成格式和最小包的真实技术试验，再按阶段拆任务估算；不根据七个分类推断七天或七轮完成。需要覆盖内容协议、Rust 存储、Godot 适配、客户端界面和验证/发行职责；这是职责分工，不表示已经分配开发者或启动多个 Agent。

主要风险是接口把官方底座写死、资源包遗漏传递依赖、Godot 全局命名冲突、进度迁移误发奖励、独立运行仍依赖工作台、第三方内容无法源文件再分发。对应出口分别为玩家新底座样本、离线干净环境导入、冲突矩阵、状态回归、独立发行测试和实际清单核对。

下一批可执行任务：冻结 schema 与测试向量；把一份官方空白底座适配成包；制作静态素材、配方数据和宝箱的最小夹具；实现无执行导入/导出；与 VM/AL 对齐存储和操作记录；等待可信执行条件满足后，接入宝箱双实例与跨世界样本。每项交付记录实际代码、测试结果、失败范围、迁移/恢复说明及来源声明。
