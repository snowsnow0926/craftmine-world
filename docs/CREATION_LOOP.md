# 创作循环：愿景、实测证据与决策记录

记录日期：2026-09-09。本文是产品讨论的结论记录，**区分"已确认的决策"、"实测得到的事实"和"尚未验证的判断"**。数字全部来自本机真实调用与代码扫描，不是估算。

相关文档：[持续开发路线](CONTINUOUS_DEVELOPMENT.md)、[Harness 开发计划书](HARNESS_DEVELOPMENT_PLAN.md)、[差距评估](HARNESS_GAP_ASSESSMENT.md)、[产品想法](PRODUCT_VISION.md)。

## 1. 产品愿景（用户确认）

**玩家一边玩自己的世界，一边和 Agent 说话让它开发；刷新重新载入看到新版本。**

关键分工：

| 角色 | 负责 |
| --- | --- |
| 玩家 | 判断"好不好玩"，提出需求，一点一点改 |
| Agent | 理解现场、编写真实代码、验证、交付候选 |

**玩家是"好玩"的裁判，Agent 是实现者。** 因此 Agent 不需要懂游戏性，但必须做到：改动快、便宜、可回退、可验证。

长期方向仍是小规模多人共创与分享；单人闭环稳定之前不建服务器平台。

| 决策 | 内容 | 证据 |
| --- | --- | --- |
| 模型后端 | 过渡期从 Codex CLI 改为 **DeepSeek 官方 API**，Codex CLI 保留回退 | §3.1，`app/agent-model.mjs` |

| 验证约束 | 自动验证必须 headless、独立数据目录、禁用 Pointer Lock、不发送真实键鼠 | `AGENTS.md`、`app/browser-tools.mjs` |
| 应用方式 | 后台生成 → 用户点应用 → 重载世界。**不是热更新**，刷新是刻意设计的断点 | `app/store.mjs`、`app/client.js` |

## 3. 实测证据

### 3.1 DeepSeek 官方 API 能力（约 25 次真实调用）

| 项目 | 实测结果 |
| --- | --- |
| 上下文 | 单次 360,033 prompt tokens 返回 200；用户确认上限 1M、输出上限 384K |
| 上下文缓存 | 重复请求 7,808 / 7,812 tokens 命中（约 99%） |
| 严格 JSON Schema | **不可用**（HTTP 400 `This response_format type is unavailable now`） |
| 思考模式 | 默认关闭：思考 token 与答案共用输出预算，会把预算吃光而返回空内容（同任务 194 秒 / 26,362 token）。可用 `CRAFTMINE_THINKING=on` + `CRAFTMINE_REASONING_EFFORT=high` 打开；开启时任务总时限自动放宽到 20 分钟、默认输出上限提到 64,000 |
| 工具调用 | 可用，返回规范 `tool_calls` |
| 端到端 | 真实门需求：候选就绪，源码含 `export function step`，隔离 Worker 验证通过，应用后状态保存 |

### 3.2 规模测量：同一次局部修改，三种世界规模

需求固定为"把 id 为 `obj-7` 的方块高度从 1 米改成 2 米，其他对象不要动"，走完整管线（DeepSeek + 候选 + 隔离验证）：

| 世界对象数 | 提示词大小 | 输入 token | **输出 token** | 耗时 | 结果 |
| --- | --- | --- | --- | --- | --- |
| 6 | 19,415 B | 10,121 | **772** | 2 秒 | 改对 |
| 32 | 26,185 B | 30,033（2 次尝试） | **6,718** | 14 秒 | 改对，其他 0 改动 |
| 128（上限） | 51,057 B | 22,381 | **12,976** | 24 秒 | 改对，其他 0 改动 |

**结论：输入随规模约 2.6 倍，输出约 17 倍；实际改动只有约 50 字节。** 因为模型必须把整个世界重新输出一遍。延迟不是问题（2–24 秒），成本才是。外推：1000 个对象时单次局部修改输出约 10 万 token（未实测）。

→ 这是"局部修改协议"必须现在做的直接依据。

**实施后的复测（同一需求、同一 128 对象世界）：**

| 指标 | 完整场景模式 | 局部修改协议 |
| --- | --- | --- |
| 模型返回 | 整个世界 | `changes`（1 条 `object.patch`） |
| 输出 token | 12,976 | **157**（−98.8%） |
| 耗时 | 24 秒 | **1.0 秒** |
| 改动对象 | 仅 obj-7 | 仅 obj-7（其他 0 改动） |
| 尝试次数 | 1 | 1 |

**输入侧按需读取实施后（同一需求、同一 128 对象世界）：**

| 指标 | 完整场景进提示 | 索引 + 焦点展开 |
| --- | --- | --- |
| 提示词大小 | 51,921 B | **35,172 B**（−32%） |
| 输入 token | 22,722 | **14,129**（−38%） |
| 输出 token | 12,976 | 147 |
| 耗时 | 24 秒 | 1.0 秒 |
| 改动对象 | 仅 obj-7 | 仅 obj-7（其他 0 改动） |

小世界或空世界的收益更大（提示里本来就没有多少对象）："造小镇"任务输入从 18,208 降到 **6,253 token**（−66%）。

实现方式：提示只带**对象索引**（id/名称/位置/包围尺寸/部件数/是否实心/血量），完整定义只展开**焦点对象**（选中对象、需求文字里出现的 id 或名称、玩家 14 米内的对象，上限 12 个）；模型如需其他对象，返回 `read:[id...]`，宿主最多补一次。

### 3.3 宿主引擎能力面扫描（代码扫描，非估算）

内置玩法系统**只有 3 个**：

```
health  生命值（maxHealth / fallDamage / regenPerSecond）
ranged  射击（damage / range / cooldown / magazine / reloadSeconds）
melee   近战（damage / range / cooldown）
```

| 能力 | 现状 |
| --- | --- |
| 射线检测、生命值/伤害 | 有 |
| 背包、物品定义、HUD 面板 | 有（`craftmine.behavior/3`） |
| 重力、冲量 | 有 |
| 敌人/NPC 内置 AI | 无（可用源码自写） |
| 玩家自定义按键 | 有（模块声明 `keys`，宿主派发 `key` 事件） |
| 复活/重置目标血量 | 有（`target.revive`） |
| 音效 | 有（内置 `audio.play`，5 种合成音） |
| 动画/骨骼 | 无 |
| 粒子/特效 | 无 |
| 刚体物理（反弹、摩擦） | 无 |

**重要修正：AI 不必等引擎。** 行为模块每步能读到 `frame.player.position` 并能移动对象，因此"会追你、会打你"的简单 AI 可以用模型写的源码实现；限制是每步最多 32 条命令、150ms 计算预算、不能开计时器。而"有骨骼动画的怪物"做不到。

### 3.4 能力探针结果（4 条真实需求，DeepSeek）

| 探针 | 首轮 | 改进后 | 说明 |
| --- | --- | --- | --- |
| 造 3 间店铺的小镇 | ❌ 3 次全失败 | ✅ **1 次通过** | 首轮失败于"实心对象重叠"，模型自称修好但没修 |
| 会追人的怪物 | ❌ 3 次全失败 | ✅ **1 次通过** | 首轮失败于 JSON 转义、模块字段不符、`object.patch` 缺少字段；改进后源码 `readsPlayer=true / movesObject=true` |
| 后坐力 + 音效 | ✅ 1 次通过 | ✅ **真实音效** | 加入 `audio.play` 内置音效后，模型源码直接调用它（实测 `has audio.play: true`、`has hud.message: false`），不再用文字冒充 |
| 挖洞 | ✅ 1 次通过 | — | 没有体素编辑，模型把实心方块拆重排成带门洞的中空结构 |

**关键结论：两次失败都是"报错信息不足 + 契约过严"造成的机械失败，不是引擎能力不足。** 三处改动之后，两条探针都从"3 次全失败"变成"1 次通过"：

- `app/scene.mjs`：实心重叠报错给出双方对象 ID、重叠区域最小/最大角、尺寸、最小分离轴与建议位移量。
- `app/gameplay.mjs`：字段校验报错列出缺少与多出的键，以及允许的字段列表。
- `app/behavior-contracts.mjs`：`object.patch` 命令允许省略 `position/visible/solid/color`（省略等于"保留原字段"），不再强制写四个 null。

**遗留缺口**（尚未补）：动画/骨骼、粒子、刚体物理（见 §3.3）。

### 3.5 用户实测反馈："刷新怪物一直做不好"

2026-09-09 用户在自己世界里连续尝试"怪物被杀了给我加个刷新键"，任务都显示"已应用"但功能不生效。查 `.craftmine/tasks/` 的真实产物后确认**两个宿主能力缺口**，都不是模型能力问题：

| 现象 | 真实原因 |
| --- | --- |
| 按 R 没反应 | 行为模块**没有按键事件**。模型写了 `(frame.keys||{})[params.respawnKey]`，而 `frame.keys` 根本不存在，条件永远为假；但代码语法/权限/命令全部合法，构建与隔离验证都通过 |
| 改成自动刷新后仍不彻底 | 死掉的怪物 `health===0`，引擎的 `alive()` 判定为假，不再渲染；`object.patch` 的 `visible:true` 无法让已死目标复活，需要**重置目标血量**的能力 |

**已补的能力**：

- 行为定义可声明 `keys`（最多 4 个，只允许引擎未占用的键：G/H/J/K/L/Q/C/V/B/N/M/3–9；W/A/S/D/空格/Shift/1/2/E/F/R/T/Enter/Esc 保留给引擎）。
- 宿主在按键未被引擎占用时派发 `{type:'key',code:'KeyG'}` 事件；提示词明确写出"不存在 frame.keys，不能轮询按键"。
- 新增 `target.revive` 命令（权限 `targets.write`）：把目标血量恢复到上限并重新出现。
- **验证器现在会按一遍模块声明的按键**，并要求至少产生一条命令，否则判定失败——直接堵住"声明了按键却毫无反应"这一类假通过。

**复测**：同一需求（"按 G 复活所有怪物到出生点"）在思考模式开启下 **2 次尝试通过**，源码正确使用 `frame.event.type==='key' && frame.event.code==='KeyG'` 与 `target.revive`；验证报告显示 `declaredKeys:["KeyG"]`、`keyCommands:8`、`events:["key:KeyG"]`。

## 4. 底座评估

判据（不是"哪个更好玩"，而是"哪个更适合 AI 生成"）：

| 判据 | 含义 |
| --- | --- |
| 生成可靠性 | 模型写对的比例 |
| 可验证性 | harness 能否自动证明它真的能跑 |
| 迭代成本 | 一次改动多少 token / 多少秒 |
| 玩家直觉 | 改完能否一眼看懂 |

| 底座 | 生成可靠性 | 可验证性 | 迭代成本 | 玩家直觉 | 引擎复杂度 |
| --- | --- | --- | --- | --- | --- |
| 3D 第一人称方块（当前） | 中 | 中 | 高 | 最高 | 高 |
| **2D 俯视 RPG（星露谷 / RPG Maker）** | **高** | **高** | **低** | 高 | **低** |
| 2D 横版跳跃（泰拉瑞亚） | 中 | 低 | 中 | 最高 | 中 |

**结论：如果从零开始，推荐 2D 俯视 RPG。** 理由：RPG 的核心内容是文本与数据（物品、任务、对话、商店、数值），正是 LLM 最擅长的；网格世界确定性强、可自动验证；单次迭代成本最低；地图还可以用"生成函数"代替逐块枚举。

**但当前不建议换底座。** 3D 底座已跑到 Alpha 0.8（碰撞、物理、候选事务、模块记忆、素材管线、101 项测试），换底座等于重写运行时与行为契约。而且真正值钱的部分（候选事务、模块版本、记忆、验收）**与底座无关**，可以复用。

**决定方式：用真实需求当判据。** 跑"造一个有 3 间店铺的小镇，进店能买东西"，看失败次数、token 成本、误改数量。做得好就继续深耕 3D；吃力就说明 3D 作为 AI 友好底座到顶了。

## 5. 风险清单（"边玩边开发"）

按严重度排序，均已核实到代码或实测。

| 编号 | 风险 | 具体表现 | 现有防护 |
| --- | --- | --- | --- |
| R1 | **新代码 + 旧进度 = 语义漏洞** | 改代码后一次性奖励可重复领取，或进度被当成未完成 | **已有回归测试**：状态版本兼容时不重置已领取状态与背包；不兼容时拒绝应用 |
| R2 | **应用时不校验玩家当前位置** | 生成期间玩家移动，新几何可能把玩家埋进实心方块 | **已修复**：`store.prepare` 用玩家此刻的位置检查新几何，冲突时拒绝并指出对象名 |
| R3 | **成本随世界规模线性增长** | 128 对象世界一次 50 字节改动要 13k 输出 token | **已缓解**：局部修改协议实施后同场景同需求输出 157 token、1.0 秒（§3.2） |
| R4 | Agent 看不到玩家此刻在干什么 | 只拿到任务开始时的快照，无实时视野、无画面 | 任务开始时附带现场快照 |
| R5 | 刷新打断沉浸 | 每次应用都要重载世界（WebGL 初始化 + 素材解码） | 应用是用户主动操作，不会静默替换 |
| R6 | 多人时的同步与权限 | 谁点应用、其他人的客户端怎么同步 | 暂缓，M6 |

## 6. 已确认的设计原则

1. **契约在代码里，文档只是解释。** 模型能做什么由运行契约（`app/behavior-contracts.mjs`、`app/scene.mjs`）强制；skill 文档由契约生成、按需加载，不能反过来当权威。
2. **不要过早抽象多底座。** 在出现第二个底座之前不做抽象层，否则会为想象中的接口写一堆注定要改的代码。
3. **不把未实现的能力做成外观假象。** 做不到的需求必须给出真实缺口，不能拼一个看起来像的东西。
4. **玩家是 fun oracle → 迭代成本与速度是核心指标。**
5. **应用事务与最新进度分离**：应用候选时重新抓取正式世界的最新进度，不用任务起点数据覆盖玩家后来获得的东西。
